# RUNBOOK: логическое декодирование PostgreSQL как CDC

Пошаговый прогон демо к статье про Change Data Capture. Debezium и Kafka не нужны: всё, что
делает CDC-коннектор, здесь видно средствами самой базы.

## Окружение

- PostgreSQL 18.4, локальная установка или контейнер
- Плагин логического декодирования `test_decoding` из стандартной поставки
- Клиент `psql`
- Права суперпользователя или роль с атрибутом REPLICATION

Все адреса в примерах локальные. Если база не на этой же машине, подставьте свой хост в `psql`.

## Шаг 1. Перевести базу в режим логического журналирования

Логическое декодирование выключено по умолчанию: на уровне `replica` в журнале нет данных строк.

```sql
ALTER SYSTEM SET wal_level = 'logical';
```

Перезапустите сервер, параметр читается только при старте. Проверка:

```sql
SHOW wal_level;
```

Должно быть `logical`. Если осталось `replica`, сервер не перезапускался или значение
перекрыто в `postgresql.conf` ниже по файлу.

## Шаг 2. Создать базу для демо

```sql
CREATE DATABASE cdc_demo;
```

Слот репликации привязан к конкретной базе, поэтому отдельная база избавляет от лишнего шума
в потоке событий.

## Шаг 3. Слот репликации и первый поток изменений

```bash
psql -d cdc_demo -f cdc_slot_demo.sql
```

Что должно быть в выводе: `CREATE TABLE`, строка с именем слота и его позицией вида
`(cdc_demo_slot,0/1BE7040)`, дальше `INSERT 0 1`, `UPDATE 1`, `DELETE 1` и таблица из девяти
строк событий. В ней три пары BEGIN и COMMIT, а между ними по одному событию на операцию.

Шаг прошёл, если в событии DELETE видно только колонку `id`. Это не ошибка, а поведение по
умолчанию: база кладёт в журнал лишь первичный ключ удалённой строки.

## Шаг 4. REPLICA IDENTITY FULL

```bash
psql -d cdc_demo -f cdc_replica_identity.sql
```

Что должно быть в выводе: те же три операции, но событие UPDATE теперь содержит блоки
`old-key` и `new-tuple`, а DELETE перечисляет все колонки строки.

Обратите внимание на первую пару BEGIN и COMMIT без событий между ними. Это `ALTER TABLE`:
изменения схемы в потоке видны как пустая транзакция, построчного события у них нет.

## Шаг 5. Отставание слота

```bash
psql -d cdc_demo -f cdc_slot_lag.sql
```

Что должно быть в выводе: `INSERT 0 199998`, затем строка слота с ненулевым `retained_wal`
порядка десятков мегабайт, затем `events_read` около 200000 и `retained_wal` равный `0 bytes`.

Это главный эксплуатационный урок демо. Пока потребитель не подтвердил чтение, база не имеет
права удалить журнал и копит его на диске.

## Уборка

```sql
SELECT pg_drop_replication_slot('cdc_demo_slot');
DROP DATABASE cdc_demo;
```

Удалять слот обязательно. Забытый слот продолжает удерживать WAL и на рабочей базе рано или
поздно заполняет диск.

## Если не так

- **`ERROR: logical decoding requires wal_level >= logical`.** Сервер не перезапущен после
  `ALTER SYSTEM` либо значение перекрыто в `postgresql.conf`.
- **`ERROR: replication slot "cdc_demo_slot" already exists`.** Слот остался от прошлого прогона.
  Скрипт `cdc_slot_demo.sql` удаляет его сам, но при ручном запуске команд удалите слот вручную.
- **`must be superuser or replication role`.** У роли нет атрибута REPLICATION.
- **Поток изменений пустой.** События уже вычитаны: `pg_logical_slot_get_changes` сдвигает
  позицию слота. Для повторного чтения тех же событий существует `pg_logical_slot_peek_changes`.
- **`retained_wal` не падает до нуля.** Между двумя замерами в базе шла ещё какая-то запись.
  На занятой базе метрика никогда не бывает ровно нулевой, смотреть надо на порядок величины.
