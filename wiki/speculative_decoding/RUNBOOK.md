# RUNBOOK: speculative decoding в llama.cpp на CPU

## Окружение

| Что | Версия |
|---|---|
| ОС | Linux x86_64 с AVX2, на прогоне Ubuntu 24.04, 4 vCPU Intel Xeon Platinum 8175M, 15.4 ГиБ RAM (15783 МиБ по `free -m`), без GPU |
| llama.cpp | v0.9.0, сборка b12110 от 2026-11-04, готовый CPU-релиз `llama-b12110-bin-ubuntu-x64.tar.gz` |
| Python | 3.10 и новее, только стандартная библиотека; на прогоне 3.12.3 |
| Ollama | 0.40.13, нужна только чтобы скачать модели |
| Целевая модель | `qwen2.5:7b` (Qwen2.5-7B-Instruct, Q4_K_M), 4.7 ГБ |
| Draft-модель | `qwen2.5:0.5b-instruct-q8_0` (Qwen2.5-0.5B-Instruct, q8_0), 531 МБ |

Нужно около 5.2 ГБ на диске под модели и около 9 ГБ свободной памяти: `llama-server` с целевой
моделью и контекстом 4096 занимал 7.7 ГиБ RSS, вместе с draft-моделью 8.3 ГиБ. Порты 8090 и 8091 на `127.0.0.1` должны быть
свободны. Весь прогон на 4 vCPU шёл 35 минут: `spec_bench.py` 34 минуты, `tie_check.py` 44 секунды.

## Шаг 1. llama.cpp

```bash
./get_llama_cpp.sh
```

Скрипт скачивает архив релиза с GitHub, сверяет sha256 и распаковывает его в `./llama.cpp`. Шаг
прошёл, если в конце напечатана версия:

```
llama-b12110-bin-ubuntu-x64.tar.gz: OK
version: 0.9.0-dev (build 12110, commit cd959bae9)
built with GNU 11.4.0 for Linux x86_64
```

Проверить, что в сборке есть флаги спекуляции:

```bash
llama.cpp/llama-server --help 2>&1 | grep -E -- '--spec-type|--spec-draft-n-max|--model-draft'
```

В выводе должны быть `--spec-draft-n-max N ... (default: 3)`, `--spec-draft-model, -md, --model-draft FNAME`
и `--spec-type none,draft-simple,draft-eagle3,draft-mtp,draft-dflash,draft-dspark,ngram-simple,ngram-map-k,ngram-map-k4v,ngram-mod,ngram-cache`.

## Шаг 2. Модели

```bash
ollama pull qwen2.5:7b
ollama pull qwen2.5:0.5b-instruct-q8_0
./models.sh
```

Ollama хранит веса как файл `blobs/sha256-<хэш>`, и этот файл уже является GGUF. `models.sh` находит его
по манифесту модели и ставит симлинк в `./models`. По умолчанию модели ищутся в `$OLLAMA_MODELS` или в
`~/.ollama/models`. Если Ollama хранит их в другом месте, например в Docker-томе, передайте этот каталог
аргументом: `./models.sh /path/to/ollama/models`. Шаг прошёл, если напечатаны две строки с размерами:

```
models/qwen2.5_7b_instruct_q4_k_m.gguf -> .../blobs/sha256-2bada8a7... (4683073952 байт)
models/qwen2.5_0.5b_instruct_q8_0.gguf -> .../blobs/sha256-48296496... (531068224 байт)
```

## Шаг 3. Замер скорости и приёма черновика

```bash
python3 spec_bench.py
```

Скрипт по очереди поднимает `llama-server` в пяти конфигурациях: `baseline` без спекуляции,
`draft_n_max_3` и `draft_n_max_8` с draft-моделью 0.5B и черновиком до 3 или до 8 токенов,
`ngram_simple` и `ngram_mod`, где черновик берётся из уже увиденного текста, а второй модели нет. В каждой
конфигурации он дважды отправляет оба промпта из `prompts/` с `temperature 0` и `max_tokens 256`. По
каждому запросу печатается строка со скоростью генерации, долей принятых токенов черновика и sha256 ответа:

```
=== draft_n_max_3: сервер поднят за 8.0 с, флаги: --spec-type draft-simple -md qwen2.5_0.5b_instruct_q8_0.gguf --spec-draft-n-max 3
code_rewrite   #1 токенов  256   4.26 ток/с  принято   175/238  sha256 4ed5e720bc49
```

В конце выводится сводка. Ниже она приведена целиком из прогона на 4 vCPU. Скорость на вашей машине
будет другой. Приём черновика и sha256 зависят от арифметики CPU, поэтому сравнивайте колонку
`ответ = baseline` внутри своего прогона:

```
=== СВОДКА (temperature 0, n_predict 256, повторы через /) ===
конфигурация    задача                 ток/с     ускорение           приём ток/проход  ответ = baseline
baseline        code_rewrite     3.57 / 3.49 x1.01 / x0.99               -       1.00  да / да
draft_n_max_3   code_rewrite     4.26 / 4.23 x1.21 / x1.20  0.74 (350/476)       3.16  нет / нет
draft_n_max_8   code_rewrite     2.85 / 2.86 x0.81 / x0.81  0.61 (422/692)       5.69  нет / нет
ngram_simple    code_rewrite     3.90 / 3.89 x1.10 / x1.10   0.72 (92/128)       1.22  нет / нет
ngram_mod       code_rewrite     4.01 / 7.21 x1.14 / x2.04  0.90 (251/280)       1.96  да / нет
baseline        creative_story   3.65 / 3.69 x1.00 / x1.00               -       1.00  да / да
draft_n_max_3   creative_story   3.25 / 3.25 x0.89 / x0.89  0.44 (288/656)       2.29  нет / нет
draft_n_max_8   creative_story   1.20 / 1.21 x0.33 / x0.33 0.17 (292/1728)       2.33  нет / нет
ngram_simple    creative_story   3.68 / 3.71 x1.00 / x1.01               -       1.00  да / да
ngram_mod       creative_story   3.71 / 3.51 x1.01 / x0.96     0.11 (7/64)       1.01  да / нет
```

Как читать колонки:

- `ток/с` берётся из поля `timings.predicted_per_second` ответа `llama-server`, это скорость генерации без чтения промпта;
- `приём` складывается из полей `timings.draft_n_accepted` и `timings.draft_n`, сколько токенов черновика
  целевая модель приняла из скольких предложенных. Та же цифра есть в логе сервера строкой
  `draft acceptance = ... (accepted / generated)`, логи лежат в `outputs/server_<конфигурация>.log`;
- `ток/проход`: сколько токенов в среднем дал один проход целевой модели. Каждый проход добавляет
  принятые токены черновика и один свой, поэтому проходов было `токены - принятые`;
- `ответ = baseline`: совпал ли sha256 ответа с ответом без спекуляции. Тексты ответов лежат в
  `outputs/<конфигурация>_<задача>.txt`, последний повтор.

## Шаг 4. Почему ответ разошёлся при temperature 0

```bash
python3 tie_check.py
```

Без спекуляции целевая модель считает ответ по одному токену, а черновик проверяет батчем из нескольких
токенов. Скрипт дважды поднимает `llama-server` с целевой моделью: с `-ub 512`, когда префикс читается
батчем, как при проверке черновика, и с `-ub 1`, когда он читается строго по одному токену. На префикс
ответа «В ночи, когда море», где ответы с черновиком в 3 токена и с `ngram-mod` разошлись с baseline, печатаются три самых
вероятных следующих токена с logprob:

```
=== префикс читается батчем, -ub 512 ===
'В ночи, когда море' -> ' ш' -1.8488  ' т' -2.0254  ' было' -3.0707

=== префикс читается по одному токену, -ub 1 ===
'В ночи, когда море' -> ' т' -1.8801  ' ш' -2.0045  ' было' -2.9699
```

Шаг прошёл, если в двух режимах первые два кандидата поменялись местами. Это и есть точка, где
greedy-ответ со спекуляцией ушёл в другую сторону.

## Если не так

- **`нет манифеста ...` от `models.sh`**: модель не скачана или Ollama хранит её в другом каталоге. Проверьте
  `ollama list` и передайте каталог моделей аргументом.
- **`llama-server упал при старте`** от `spec_bench.py`: смотрите `outputs/server_<конфигурация>.log`. Чаще
  всего не хватило памяти. Целевой модели нужно около 9 ГБ вместе с draft-моделью (8.3 ГиБ RSS на прогоне), Ollama с загруженной
  моделью рядом может забрать ещё 5 ГБ. Остановите её на время замера.
- **Порт занят**: `spec_bench.py --port 18090`, у `tie_check.py` порт задан константой `PORT` в начале файла.
- **Флаги `--draft-max` и `--draft-min` из старых инструкций** в этой сборке удалены, `llama-server`
  отвечает `the argument has been removed`. Длина черновика задаётся `--spec-draft-n-max`.
- **sha256 не совпали с приведёнными выше.** Их меняет любая разница в арифметике: другая сборка llama.cpp,
  другой набор инструкций CPU (AVX-512 против AVX2), другое число потоков, GPU вместо CPU. Сравнивать
  надо колонку `ответ = baseline` внутри своего прогона, а не хэши с чужой машины.
- **`ngram_mod` во втором повторе быстрее, чем в первом.** Это не ошибка: `ngram-mod` копит n-граммы
  между запросами одного сервера, и второй повтор того же промпта находит в них готовое продолжение.
- **Прогон идёт дольше часа**: уменьшите объём, например `python3 spec_bench.py --repeats 1 --configs baseline,draft_n_max_3`.
