# RUNBOOK: чекпоинтинг в LangGraph

Демо к статье про чекпоинтинг (bigdataschool.ru/wiki/checkpointing/). Показывает два
механизма чекпоинтера LangGraph: восстановление графа после реального падения процесса
и time travel с форком выполнения по другой ветке.

## Окружение

- Python 3.12
- `langgraph` 1.2.11, `langgraph-checkpoint` 4.2.0, `langgraph-checkpoint-sqlite` 3.1.1
- Внешние сервисы не нужны: оба демо работают на локальном SQLite-файле, без Ollama,
  Docker или сетевых вызовов

Установка:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install langgraph langgraph-checkpoint-sqlite
```

## Шаг 1. Аварийное прерывание процесса и resume

```bash
python3 checkpointing_langgraph_crash_resume.py
```

Скрипт сам запускает себя вторым процессом (`subprocess`) в режиме `--worker --crash`:
граф доходит до узла `step3` и убивает процесс через `os._exit(137)`, как будто его
убили снаружи (`kill -9`), а не поймал исключение. Дальше скрипт читает состояние
чекпоинтера напрямую, запускает новый процесс с тем же `thread_id` и показывает,
что граф продолжился с последнего сохранённого шага, а не начал сначала.

Что должно быть в выводе:

```
=== Попытка 1: запускаем граф, step3 аварийно убьёт процесс ===
процесс упал с кодом 137 (137 = убит сигналом, не поймано)

=== Что реально сохранилось в чекпоинтере после падения ===
сохранённые шаги: ['step1', 'step2']
следующий узел к выполнению: ('step3',)

=== Попытка 2: новый процесс, тот же thread_id ===
узел step4 отработал, процесс завершается штатно
процесс завершился кодом 0

=== Итоговое состояние после resume ===
шаги: ['step1', 'step2', 'step3', 'step4']

=== Лог внешнего эффекта step3 (побочный эффект не под чекпоинтом) ===
внешний вызов из step3, попытка №1
внешний вызов из step3, попытка №2
```

Как понять, что шаг прошёл: `сохранённые шаги` после падения — ровно `['step1', 'step2']`
(узел `step3` не успел зафиксироваться), а итоговые шаги после второго запуска — все
четыре по порядку. В логе внешнего эффекта две строки: узел `step3` реально выполнился
дважды, потому что чекпоинтер гарантирует консистентное состояние графа, а не
идемпотентность побочных эффектов внутри самого узла.

## Шаг 2. Time travel и форк выполнения

```bash
python3 checkpointing_langgraph_time_travel.py
```

Граф `a -> b -> (c_main | c_alt) -> d`, ветвление после `b` зависит от поля `path` в
состоянии. Скрипт прогоняет граф целиком по основной ветке, откатывается к чекпоинту
сразу после узла `b`, форкает выполнение с `path="alt"` и показывает, что форк идёт
через `c_alt`, а исходный чекпоинт с веткой `c_main` остаётся доступен по своему
`checkpoint_id` без изменений.

Что должно быть в выводе:

```
=== Основной прогон: a -> b -> c_main -> d ===
финальный лог основной ветки: ['a', 'b', 'c_main', 'd']

=== Форк: та же точка отката, другая ветка через смену 'path' ===
финальный лог форкнутой ветки: ['a', 'b', 'c_alt', 'd']

=== Исходная ветка осталась доступна по своему checkpoint_id ===
лог исходного финального чекпоинта: ['a', 'b', 'c_main', 'd']

=== У треда теперь два независимых финальных чекпоинта ===
исходный конечный checkpoint_id всё ещё в истории: True
```

Как понять, что шаг прошёл: у форкнутой ветки в логе `c_alt` вместо `c_main`, а
запрос состояния по исходному `checkpoint_id` по-прежнему возвращает `c_main` —
форк не переписал историю, а добавил в неё новую ветку.

## Если не так

- **`ModuleNotFoundError: No module named 'langgraph.checkpoint.sqlite'`** — не
  поставлен отдельный пакет `langgraph-checkpoint-sqlite`, он не входит в `langgraph`
  напрямую.
- **После `os._exit(137)` в выводе видно, что `step3` всё же попал в сохранённые
  шаги** — значит `durability="sync"` в вызове `app.invoke(...)` пропущен или
  заменён на дефолтное значение `"async"`: тогда запись чекпоинта уходит в фоновый
  поток и может не долететь до диска к моменту падения.
- **В файле вывода (при перенаправлении `> run_output.txt` вместо вывода
  в терминал) строки от дочернего процесса появляются раньше строк
  родительского скрипта, хотя по логике должны идти позже** — это буферизация
  `stdout`: при выводе в файл Python буферизует блоками, а не по строкам, как в
  терминале. Лечится явным `sys.stdout.flush()` перед каждым `subprocess.run(...)`
  в родительском процессе (уже сделано в демо-файле).
