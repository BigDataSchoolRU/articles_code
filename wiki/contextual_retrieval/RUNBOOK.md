# RUNBOOK: Contextual Retrieval на локальной модели

Демо к статье https://bigdataschool.ru/wiki/contextual_retrieval/

Что показываем: к каждому чанку синтетических квартальных отчётов локальная LLM дописывает
короткий контекст (компания, отчёт, квартал), и доля неудачных извлечений падает у векторного
поиска, у BM25 и у гибрида с RRF. Отдельно видно, как кэш префикса Ollama удешевляет вызовы
для второго и следующих чанков одного документа.

## Окружение

| Компонент | Версия |
|---|---|
| ОС | Ubuntu 24.04, x86_64, 4 vCPU, 16 ГБ RAM, без GPU (подойдёт любая машина с Docker) |
| Docker / Compose | 29.1 / 2.40 |
| Ollama | 0.40.13 в контейнере `ollama/ollama:0.40.13` |
| Модели | `qwen2.5:7b` (контекст к чанкам, около 4.7 ГБ), `nomic-embed-text` (эмбеддинги, около 0.3 ГБ) |
| Python | 3.12, пакеты в `requirements.txt`: bm25s 0.3.16, PyStemmer 3.1.0, numpy 2.5.4 |

Нужно: около 6 ГБ свободного диска под модели, 8 ГБ свободной памяти, свободный порт
`127.0.0.1:11434`. Если Ollama у вас уже стоит на хосте и слушает этот порт, контейнер не нужен:
пропустите шаг 1 и подтяните модели своей Ollama. Другой адрес задаётся переменной
`OLLAMA_URL`, например `export OLLAMA_URL=http://localhost:11500`.

## Шаг 1. Поднять Ollama и скачать модели

```bash
cd contextual_retrieval
docker compose up -d
docker exec contextual-retrieval-ollama ollama pull qwen2.5:7b
docker exec contextual-retrieval-ollama ollama pull nomic-embed-text
curl -s http://localhost:11434/api/tags | python3 -m json.tool | grep '"name"'
```

В выводе должны быть `qwen2.5:7b` и `nomic-embed-text:latest`. Модели лежат в `./ollama`
рядом с кодом и переживают пересоздание контейнера.

## Шаг 2. Окружение Python

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python corpus.py
```

Ожидаемо: `документов: 6, чанков: 24, запросов: 12` и пример чанка, в котором нет ни названия
компании, ни квартала.

## Шаг 3. Контекст к каждому чанку

```bash
.venv/bin/python -u contextualize.py
```

Скрипт по очереди отправляет в `qwen2.5:7b` промпт из первоисточника Anthropic: документ
целиком, затем чанк, затем просьбу дать короткий контекст. На каждый чанк печатается строка:
сколько токенов в промпте, сколько из них Ollama взяла из кэша, сколько секунд ушло на чтение
промпта и на генерацию. Результат пишется в `contexts.json`.

Как понять, что шаг прошёл: в конце есть сводка `токенов промпта: ..., из них из кэша: ...`
и пример контекста для чанка про выручку Northwind Logistics. У второго и следующих чанков
документа в колонке «из кэша» стоит почти весь документ, а чтение промпта в разы короче,
чем у первого чанка.

Время: на CPU (4 vCPU, без GPU) от 16 до 41 с на чанк, весь корпус около 10.5 минут; больше
всего занимает генерация ответа, около 2.5 токена в секунду. На GPU в разы быстрее.

## Шаг 4. Поиск до и после

```bash
.venv/bin/python evaluate.py
```

Скрипт строит два набора индексов (векторный на nomic-embed-text, BM25, гибрид через
Reciprocal Rank Fusion): один над голыми чанками, второй над чанками с дописанным контекстом.
Для 12 запросов считается доля неудачных извлечений, то есть случаев, когда эталонного чанка
нет в top-k, при k = 1, 3, 5.

Как понять, что шаг прошёл: таблица из девяти строк (три способа поиска на три значения k),
в колонке «с контекстом» число неудач у BM25 и гибрида меньше, чем в колонке «голые чанки».
Ниже три диагностических блока:

- контексты, в которых модель не назвала компанию или квартал, и их число из 24;
- запросы, на которых гибрид с контекстом всё ещё не нашёл эталон в top-3;
- разбор одного запроса: какие чанки гибрид ставит в top-3 до и после.

Обычно промахи совпадают с контекстами из первого блока: если модель пересказала цифры
документа вместо того, чтобы назвать компанию и период, чанк остаётся таким же безымянным, как
был. Таблица у отдельного способа поиска может и ухудшиться на одном-двух запросах, особенно у
векторного при k=5: на корпусе из 24 чанков один запрос это 8 процентных пунктов.

## Если не так

- **`Connection refused` на `localhost:11434`.** Контейнер не поднят или порт занят другой
  Ollama: `docker ps`, `docker logs contextual-retrieval-ollama`.
- **`model "qwen2.5:7b" not found`.** Модель не скачана в тот каталог, который смонтирован в
  контейнер: повторите `ollama pull` из шага 1.
- **HTTP 500 на первом вызове.** Не хватило памяти на загрузку 7B модели. Проверьте
  `free -g`, закройте другие модели или уменьшите их число переменной
  `OLLAMA_MAX_LOADED_MODELS` в `docker-compose.yml`. При значении `1` модель эмбеддингов будет
  выгружать `qwen2.5:7b`, это медленнее, но работает.
- **Первый вызов идёт несколько минут.** Это загрузка модели с диска в память, следующие
  вызовы быстрее.
- **Контексты от прогона к прогону немного разные.** `temperature 0` и `seed 42` на CPU не
  гарантируют одинаковый текст ответа, поэтому и цифры в таблице могут сдвинуться на
  один-два запроса. Чтобы гонять `evaluate.py` на одних и тех же контекстах, не перезапускайте
  `contextualize.py`: он перезаписывает `contexts.json`.
- **В колонке «из кэша» у первого чанка документа не ноль.** Ollama держит в кэше несколько
  прошлых промптов, и общий префикс (служебный шаблон чата, а при повторном запуске и сам
  документ) берётся оттуда. Чтобы снова увидеть холодный первый чанк, перезапустите контейнер:
  `docker restart contextual-retrieval-ollama`. Заодно учтите, что на CPU текст ответа для
  промпта с префиксом из кэша и без него может отличаться в нескольких словах.

## Уборка

```bash
docker compose down
```

Модели остаются в `./ollama`. Удалите каталог, если они больше не нужны.
