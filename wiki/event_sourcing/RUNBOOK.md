# RUNBOOK: Event Sourcing на PostgreSQL 18

Пошаговый прогон демо к статье [Event Sourcing](https://bigdataschool.ru/wiki/event_sourcing/).
Один контейнер PostgreSQL 18.6 и пять сценариев: запись и восстановление состояния, конфликт двух
писателей, проекция с пересборкой, снапшот и апкастер. Хранилище событий написано руками на одной
таблице, без фреймворка. Шаги с двумя сессиями идут с явным чередованием в одном процессе Python,
поэтому результат не зависит от таймингов.

## Окружение

| Компонент | Версия |
|---|---|
| PostgreSQL | 18.6, образ `postgres:18.6` |
| Python | 3.10 или новее, проверено на 3.12.3 |
| psycopg | 3.3.8, `psycopg[binary]` с встроенной libpq 18 |
| Docker | с плагином Compose |

Сервер слушает `127.0.0.1:55437`, пользователь, пароль и база `demo`/`demo`/`es`. Если порт
занят, поменяйте его в `docker-compose.yml` и задайте строку подключения:
`export ES_DSN="postgresql://demo:demo@127.0.0.1:<порт>/es"`.

Весь прогон занимает около 10 секунд. Номера транзакций и миллисекунды у вас будут другими,
версии потоков, позиции и суммы совпадут, если сценарии идут по порядку на чистом томе.

## Шаг 1. Поднять сервер и окружение Python

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
docker compose up -d --wait
docker compose exec -T pg psql -U demo -d es -XAtc "\dt"
```

Ожидаемо: `Container event-sourcing-pg  Healthy` и четыре таблицы из `schema.sql`:

```
public|events|table|demo
public|order_summary|table|demo
public|projection_checkpoints|table|demo
public|snapshots|table|demo
```

Схема применяется только при первом старте на пустом томе. Если таблиц нет, том остался от
прошлого запуска: `docker compose down -v` и снова `up`.

Все сценарии разом запускает `.venv/bin/python es_demo.py all`, по одному
`es_demo.py append`, `conflict` и так далее. Проекция в шаге 4 строится по потокам из шагов 2 и 3,
поэтому по одному сценарии запускайте по порядку.

## Шаг 2. Запись событий и восстановление состояния

```bash
.venv/bin/python es_demo.py append
```

Обработчик команды читает поток, сворачивает его в состояние, проверяет инвариант и дописывает
событие с ожидаемой версией. Ожидаемо, журнал потока `order-1001`:

```
  pos=1   v=1 OrderCreated  schema=v1 {"customer": "alice"}
  pos=2   v=2 ItemAdded     schema=v2 {"qty": 2, "sku": "book", "price": "1290.00", "currency": "RUB"}
  pos=3   v=3 ItemAdded     schema=v2 {"qty": 1, "sku": "lamp", "price": "3490.00", "currency": "RUB"}
  pos=4   v=4 ItemRemoved   schema=v1 {"sku": "lamp"}
  pos=5   v=5 ItemAdded     schema=v2 {"qty": 3, "sku": "pen", "price": "150.00", "currency": "RUB"}
  pos=6   v=6 OrderPaid     schema=v1 {"amount": "3030.00"}
  pos=7   v=7 OrderShipped  schema=v1 {"carrier": "cdek"}
```

Затем состояние сейчас и на прошлых версиях, свертка первых N событий:

```
  состояние сейчас (свертка 7 событий): версия 7, статус shipped, позиции [book×2 по 1290.00, pen×3 по 150.00], сумма 3030.00
  состояние на версии 3 (свертка первых 3): версия 3, статус new, позиции [book×2 по 1290.00, lamp×1 по 3490.00], сумма 6070.00
  состояние на версии 4 (после удаления lamp): версия 4, статус new, позиции [book×2 по 1290.00], сумма 2580.00
```

Команда против инварианта отклоняется до записи, а попытки поменять журнал ловит триггер:

```
  отклонено до записи: заказ в статусе shipped, позиции менять нельзя
  UPDATE: 23001 журнал событий только на добавление: UPDATE запрещён
  DELETE: 23001 журнал событий только на добавление: DELETE запрещён
  TRUNCATE: 23001 журнал событий только на добавление: TRUNCATE запрещён
  событий в потоке после попыток: 7
```

Шаг прошёл, если состояние на версии 3 содержит `lamp`, а на версии 7 нет, и в потоке осталось
7 событий.

## Шаг 3. Конфликт двух писателей

```bash
.venv/bin/python es_demo.py conflict
```

Два соединения читают поток на одной версии и пишут событие с одной и той же ожидаемой версией.
Первый проходит, второй упирается в уникальный индекс `(stream_id, stream_version)`. Ожидаемо:

```
Пара А: два писателя добавляют разные позиции
  писатель 1 прочитал версию 2, писатель 2 прочитал версию 2
  писатель 1 записал ItemAdded(lamp) с ожидаемой версией 2 -> версия 3
  писатель 2: 23505 UniqueViolation: поток order-2002: ожидали версию 2, она уже занята
  писатель 2 перечитал поток: версия 3, позиции ['book', 'lamp']
  писатель 2 повторил команду -> версия 4
Пара Б: писатель 1 оплачивает, писатель 2 в это время добавляет позицию
  оба прочитали версию 4
  писатель 1 записал OrderPaid -> версия 5
  писатель 2: 23505 UniqueViolation: поток order-2002: ожидали версию 4, она уже занята
  писатель 2 перечитал поток: версия 5, статус paid
  повтор команды отклонён инвариантом: заказ в статусе paid, позиции менять нельзя
```

В паре Б видно, зачем повтор идёт через повторную загрузку состояния, а не через простое
увеличение версии: после оплаты добавлять позиции нельзя.

## Шаг 4. Проекция, повторная доставка и пересборка

```bash
.venv/bin/python es_demo.py projection
```

Проектор читает журнал после чекпойнта и обновляет таблицу `order_summary` в той же транзакции,
что и чекпойнт. Ожидаемо:

```
Первый проход: прочитано 14, применено 14
Второй проход без новых событий: прочитано 0, применено 0
Модель чтения order_summary:
  order-1001 alice  shipped  позиций=5 сумма=3030.00 версия=7
  order-2002 bob    paid     позиций=4 сумма=5080.00 версия=5
  order-3003 carol  new      позиций=2 сумма=6980.00 версия=2
Чекпойнт сброшен, модель оставлена (повторная доставка всего журнала): прочитано 14, применено 0
Пересборка с нуля (TRUNCATE модели и чекпойнта): прочитано 14, применено 14, модель совпала с прежней: True
```

Повторно доставленные события отсекаются по версии потока, записанной в модели. Пересборка с
нуля даёт ту же модель, потому что источник истины это журнал.

Вторая часть сценария показывает ловушку глобальной позиции. Позицию выдаёт последовательность
в момент INSERT, а видимым событие становится в момент COMMIT. Транзакция A взяла позицию 17 и
держится открытой, транзакция B взяла 18 и зафиксировалась:

```
  A: вставил OrderCreated(order-4004), позиция 17, транзакция открыта
  B: вставил OrderCreated(order-5005), позиция 18, COMMIT
  опрос 1, A ещё открыта: наивный прочитал [18], чекпойнт 18; по горизонту прочитал []
  A: COMMIT
  опрос 2, обе зафиксированы: наивный прочитал [], чекпойнт 18; по горизонту прочитал [17, 18]
  опрос 3: наивный прочитал [], чекпойнт 18; по горизонту прочитал []
  итог: наивный проектор увидел [18], пропущена позиция 17: True; по горизонту увидел [17, 18]
```

Наивный проектор читает `global_position > чекпойнт` и навсегда теряет событие 17. Проектор по
горизонту читает только события транзакций с `transaction_id < pg_snapshot_xmin(pg_current_snapshot())`,
то есть заведомо завершённых, в порядке `(transaction_id, global_position)`. Пока A открыта, он
ждёт, после её фиксации получает оба события.

## Шаг 5. Снапшот против полной свертки

```bash
.venv/bin/python es_demo.py snapshot
```

В поток пишется 10 000 событий одной транзакцией, сохраняется снапшот на версии 10 000,
дописывается хвост из 20 событий. Восстановление замеряется 7 раз, берётся медиана. Ожидаемо
(миллисекунды зависят от машины):

```
Записано 10000 событий одной транзакцией за 459 мс
Снапшот сохранён на версии 10000
Полная свертка 10020 событий: медиана 98.7 мс из 7 запусков
Снапшот на версии 10000 плюс хвост 20 событий: медиана 1.1 мс
Ускорение: 92×, состояния совпали: True
```

Шаг прошёл, если состояния совпали. Снапшот это кэш: таблицу `snapshots` можно очистить, и
агрегат восстановится полной сверткой.

## Шаг 6. Апкастер старой версии события

```bash
.venv/bin/python es_demo.py upcast
```

В поток `order-7007` пишется событие `ItemAdded` в старой схеме v1 (цена целым числом рублей) и
новое в схеме v2 (цена строкой плюс валюта). Апкастер поднимает v1 до v2 при чтении. Ожидаемо:

```
В журнале как записано:
  v=1 OrderCreated  schema=v1 {"customer": "grace"}
  v=2 ItemAdded     schema=v1 {"qty": 2, "sku": "book", "price": 1290}
  v=3 ItemAdded     schema=v2 {"qty": 3, "sku": "pen", "price": "150.50", "currency": "RUB"}
После чтения через апкастер:
  v=1 OrderCreated  schema=v1 {'customer': 'grace'}
  v=2 ItemAdded     schema=v2 {'sku': 'book', 'qty': 2, 'price': '1290.00', 'currency': 'RUB'}
  v=3 ItemAdded     schema=v2 {'qty': 3, 'sku': 'pen', 'price': '150.50', 'currency': 'RUB'}
  состояние: версия 3, статус new, позиции [book×2 по 1290.00, pen×3 по 150.50], сумма 3031.50
ItemAdded по версиям схемы в журнале до чтения [(1, 1), (2, 1)], после [(1, 1), (2, 1)], журнал не изменился: True
```

## Шаг 7. Уборка

```bash
docker compose down -v
```

Ключ `-v` удаляет том с данными, следующий `up` создаст схему заново.

## Если не так

- **`relation "events" does not exist`.** Схема не применилась, потому что том уже был.
  `docker compose down -v`, затем `docker compose up -d --wait`.
- **`FATAL: the database system is shutting down` сразу после `up`.** Healthcheck без `-h`
  отвечает «готов» во время initdb. В `docker-compose.yml` он уже пишется с `-h 127.0.0.1`,
  не убирайте этот ключ.
- **`connection refused` на порту 55437.** Контейнер не поднялся или порт другой: проверьте
  `docker compose ps` и переменную `ES_DSN`.
- **Позиции и версии в выводе сдвинуты.** Сценарии запускались не по порядку или не на чистом
  томе. Механика от этого не меняется, но для сверки с выводом выше начните с `down -v`.
- **`UniqueViolation` или `заказ ... уже создан` при повторном запуске.** Сценарий уже
  запускался на этом томе и пишет тот же поток с версии 1. Нужен чистый том.
