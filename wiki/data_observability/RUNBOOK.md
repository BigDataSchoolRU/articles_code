# Наблюдаемость данных: демо на Soda Core и PostgreSQL

Демо показывает разницу между жёстким правилом и базовой линией. Витрина заказов проходит
три состояния: нормальный день, день с провалом объёма и просроченной свежестью, день со
сменой схемы. На каждом состоянии прогоняется скан Soda Core, метрики уходят в историю,
а отдельный детектор ищет отклонение от базовой линии.

## Окружение

| Компонент | Версия |
|---|---|
| Python | 3.12.13 |
| soda-core, soda-core-postgres | 3.5.6 |
| psycopg | 3.3.4 |
| PostgreSQL | 18.4 |

Что должно быть доступно: запущенный PostgreSQL на `localhost:5432` и право создавать базы.
Имя пользователя, хост и порт подставьте свои в `configuration.yml`.

## Шаг 1. Зависимости

```bash
python3 -m venv .venv
./.venv/bin/python3 -m pip install soda-core-postgres==3.5.6 psycopg[binary]==3.3.4
```

В выводе должно быть `Successfully installed soda-core-3.5.6 soda-core-postgres-3.5.6`.
Проверка: `./.venv/bin/python3 -c "from soda.scan import Scan; print('ok')"` печатает `ok`.

## Шаг 2. Подключение

Откройте `configuration.yml` и поставьте свои `host`, `port`, `username`, при необходимости
`password`. Имя источника `orders_demo` менять не нужно: на него ссылаются скрипты.

## Шаг 3. Демо-данные

```bash
./.venv/bin/python3 demo_setup.py
```

Скрипт пересоздаёт базу `observability_demo`, заводит таблицы `orders` и `metric_history`
и наполняет тридцать дней ровной истории плюс текущий день. В выводе:

```
загружено строк за 30 дней: 14985
текущий день: 498 строк, последняя запись 25 мин назад
всего строк в orders: 15483
```

Шаг прошёл, если последняя строка показывает около пятнадцати тысяч строк.

## Шаг 4. Три скана

```bash
./.venv/bin/python3 demo_scan.py
```

Скрипт трижды прогоняет один и тот же набор правил из `checks.yml`, между прогонами ломая
витрину. Что должно быть в выводе:

- скан 1: `5/5 checks PASSED`, код возврата 0;
- скан 2: провал `freshness(created_at) < 1h`, код возврата 2, при этом правило
  `row_count > 100` проходит, хотя объём упал с пятисот строк до ста двадцати;
- скан 3: провал проверки схемы со строкой
  `fail_column_type_mismatch[amount] expected(numeric) actual(text)`.

Ключевая деталь второго скана: правило по объёму молчит. Именно поэтому нужен следующий шаг.

## Шаг 5. Базовая линия

```bash
./.venv/bin/python3 demo_baseline.py
```

Детектор берёт тридцать дней истории, считает медиану и медианное абсолютное отклонение и
сравнивает с ними текущий день. Ожидаемый вывод:

```
базовая линия (медиана дневного объёма): 500 строк
текущий день: 121 строк
отклонение от базовой линии: -75.8%
устойчивая z-оценка: -25.6 при пороге 3.5
правило row_count > 100 говорит: всё в порядке
детектор базовой линии говорит: АНОМАЛИЯ
затронуто потребителей вниз по потоку: 5
```

Шаг прошёл, если z-оценка по модулю заметно больше порога, а жёсткое правило при этом
считает день нормальным.

## Если не так

**Скан висит, а следующий шаг не начинается.** Soda Core оставляет подключение к источнику
открытым в состоянии `idle in transaction`, и `ALTER TABLE` по той же таблице ждёт снятия
блокировки. В `demo_scan.py` подключения закрываются вручную функцией
`close_scan_connections`. Штатный `close_all_connections` в версии 3.5.6 не помогает: он
обходит пустой словарь, реальные подключения лежат на объектах источников.

**`function avg(text) does not exist`.** Это последствие третьего скана: колонка `amount`
стала текстовой, и сборщик метрик падает вместе с витриной. В демо приведение типа стоит
явно, в жизни такой запрос ломается молча в ночном расчёте.

**`connection to server on socket failed`.** PostgreSQL не запущен либо слушает другой порт.
Проверьте `pg_isready` и правьте `configuration.yml`.

**Проверка схемы проходит там, где ждали провала.** SodaCL сравнивает состав колонок с тем,
что перечислено в `checks.yml`. Если вы правили список колонок, сверьте имена: переименование
ловится как отсутствие обязательной колонки, смена типа как несовпадение типа.
