# RUNBOOK: минимальный харнесс оценки LLM

Демо к статье про LLM Evaluation. Показывает три независимых слоя оценки одного и того же
ответа модели (детерминированный автотест, эмбеддинг-сходство, модель-судья) и отдельно —
нестабильность и относительную стоимость слоя "модель-судья".

## Окружение

- Python 3.12+
- [Ollama](https://ollama.com/) запущен локально и слушает `http://localhost:11434`
- Модели загружены заранее:
  ```bash
  ollama pull qwen2.5:7b
  ollama pull llama3.1:8b
  ollama pull nomic-embed-text
  ```
- Python-пакет `ollama` (клиент, не сам сервер):
  ```bash
  pip install ollama
  ```

Свой адрес Ollama (если не localhost) подставляется переменной окружения `OLLAMA_HOST` перед
запуском — клиент читает её сам, в коде демо ничего менять не нужно.

## Шаг 1. Проверить, что Ollama отвечает и модели на месте

```bash
curl -s -m 5 http://localhost:11434/api/tags | grep -o '"name":"[^"]*"'
```

В выводе должны быть строки с `qwen2.5:7b`, `llama3.1:8b` и `nomic-embed-text`. Если команда
зависла или вернула пусто — Ollama не запущен (`ollama serve`) или модели не скачаны.

## Шаг 2. Прогнать полный харнесс

```bash
python3 eval_harness.py
```

Скрипт берёт вопросы из `dataset.jsonl`, генерирует ответ моделью-кандидатом (`qwen2.5:7b`) на
каждый вопрос и оценивает его тремя слоями. В конце печатается таблица по всем кейсам и, если
слои разошлись во мнении, отдельная строка про расхождение.

**Как понять, что шаг прошёл:** для каждого вопроса напечатан блок с ответом кандидата и тремя
строками результата слоёв, в конце — таблица `=== Итоговый отчёт ===` с непустыми значениями
similarity (число от -1 до 1) и score (целое 1-5) в каждой строке. На первом прогоне на новой
машине (модели ещё не в памяти) первый вызов каждой модели заметно медленнее последующих.

## Шаг 3. Прогнать демо нестабильности и стоимости

```bash
python3 judge_stability_cost.py
```

Один и тот же вход отправляется судье 5 раз подряд при `temperature=0`, затем ещё 5 раз при
`temperature=0.7`, и печатается разброс баллов. Дальше три слоя оценки замеряются по времени на
одном и том же кейсе.

**Как понять, что шаг прошёл:** пять строк `прогон N: score=...` в каждом из двух блоков и
итоговая строка "разброс (max-min): ...". В блоке стоимости — три строки со временем слоёв и
множитель "судья дороже эмбеддинга в N раза".

## Если не так

- **`ConnectionError` / долгое зависание на первом запросе.** Ollama не запущен или запущен на
  другом порту. Проверить `ollama serve` в отдельном терминале и переменную `OLLAMA_HOST`.
- **`model not found` в ошибке.** Модель не скачана — `ollama pull <имя модели>` из шага
  "Окружение".
- **`score=None` в выводе судьи.** Судья ответил не в формате `SCORE: <1-5>` первой строкой —
  обычно разовый сбой формата у локальной модели. Ошибку не подавляет: сырой ответ модели можно
  посмотреть, если временно распечатать поле `raw` из `judge_score()` / `judge_once()`.
- **Разброс баллов у судьи всегда 0.** Ожидаемо на простых, однозначных парах вопрос-ответ —
  нестабильность модели-судьи заметнее на пограничных, спорных кейсах, а не на явно правильных
  или явно неправильных ответах.
- **Автотест не проходит почти всегда.** Проверьте формулировку вопроса: без явного ограничения
  длины в самом промпте локальная модель обычно отвечает развёрнутым списком, а не короткой
  фразой, и упирается в `max_words` из `dataset.jsonl`. Это ограничение промпта, а не баг
  харнесса.
