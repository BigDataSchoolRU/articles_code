# Контракт данных на таблицу PostgreSQL: воспроизведение демо

Демо показывает полный цикл контракта данных: документ ODCS 3.1.0 рядом с кодом, проверка
документа (`lint`), проверка живой таблицы против документа (`test`), генерация DDL из
контракта (`export`) и падение проверки, когда продюсер несовместимо меняет схему.

## Окружение

| Компонент | Версия |
|---|---|
| Python | 3.12 |
| datacontract-cli | 1.1.1 (экстра `postgres`) |
| open-data-contract-standard | 3.1.2 (схема ODCS 3.1.0) |
| PostgreSQL | 18.x, локальный |

Что должно быть доступно: работающий сервер PostgreSQL на `localhost:5432` и пользователь,
которому разрешено создать базу. Все адреса и имена в файлах локальные, подставьте свои.

## Шаг 1. Поставить инструмент

```bash
python3 -m venv .venv
./.venv/bin/python3 -m pip install "datacontract-cli[postgres]"
./.venv/bin/datacontract --version
```

В выводе должна быть версия `1.1.1`. Экстра `postgres` тянет `psycopg` и драйвер ibis, без неё
команда `test` откажется подключаться к базе.

## Шаг 2. Указать учётные данные

CLI читает их только из переменных окружения, в самом контракте паролей нет и быть не должно.

```bash
export DATACONTRACT_POSTGRES_USERNAME=<ваш_пользователь>
export DATACONTRACT_POSTGRES_PASSWORD=<ваш_пароль>
```

Пустая строка считается незаданным значением. Если сервер настроен на доверительную
аутентификацию и пароля нет, всё равно положите в переменную любую непустую заглушку, иначе
`test` завершится ошибкой `Required configuration DATACONTRACT_POSTGRES_PASSWORD is not set`.

## Шаг 3. Поднять демо-базу

```bash
./.venv/bin/python3 db_setup.py
```

Ожидаемый вывод: создание базы `contract_demo` и строка `таблица orders пересоздана, строк: 5000`,
следом список колонок с типами. Скрипт идемпотентный, гоняйте сколько нужно.

## Шаг 4. Проверить сам документ

```bash
./.venv/bin/datacontract lint orders_contract.yaml
```

Ожидаемый вывод: `🟢 data contract is valid. Run 1 checks.` Это проверка синтаксиса по JSON
Schema стандарта, к базе она не ходит и занимает доли секунды. Именно её вешают на pre-commit.

## Шаг 5. Проверить живую таблицу

```bash
./.venv/bin/datacontract test orders_contract.yaml
```

Ожидаемый вывод: таблица результатов, где все строки `passed`, и итог
`🟢 data contract is valid. Run 19 checks.` Девятнадцать проверок инструмент собрал из документа
сам: наличие каждой колонки, совпадение физического типа с типом в каталоге PostgreSQL,
отсутствие пропусков в обязательных полях, уникальность первичного ключа плюс три правила из
блоков `quality`.

## Шаг 6. Сгенерировать DDL из контракта

```bash
./.venv/bin/datacontract export sql --dialect postgres orders_contract.yaml
```

Ожидаемый вывод: готовый `CREATE TABLE orders (...)`. Контракт тут первичен, таблица вторична.

Про предупреждение `Cannot map type to postgres SQL type for field 'created_at'`: конвертер не
знает, во что переводить пару `logicalType: date` и `physicalType: timestamp with time zone`,
и в этом случае честно копирует физический тип как есть. На результат это не влияет,
`timestamp with time zone` в DDL попадает.

## Шаг 7. Сломать схему и убедиться, что проверка падает

```bash
./.venv/bin/python3 break_schema.py
./.venv/bin/datacontract test orders_contract.yaml
echo "код возврата: $?"
```

Скрипт переводит `order_amount` из `numeric(10,2)` в `text` и переименовывает `status` в
`order_status`. Данные остаются на месте, счётчик строк не меняется, поэтому глазами такое
изменение не ловится.

Ожидаемый вывод: `🔴 data contract is invalid` и пять провалившихся проверок — несовпадение
физического типа `order_amount`, отсутствие колонки `status` и три проверки, которые без неё не
выполняются. Код возврата `1`, и это тот самый признак, по которому падает шаг CI.

## Шаг 8. Вернуть схему

```bash
./.venv/bin/python3 db_setup.py
```

Таблица пересоздаётся в исходном виде, и `test` снова зелёный.

## Как повесить это на CI

Отдельной команды тут ровно одна:

```bash
datacontract ci orders_contract.yaml
```

Она делает то же, что `test`, но дополнительно печатает аннотации GitHub Actions и сводку в
step summary. Ненулевой код возврата валит шаг, а значит и сборку.

## Если не так

- **`Required configuration DATACONTRACT_POSTGRES_PASSWORD is not set`.** Переменная пустая.
  Смотрите шаг 2, пустая строка для CLI это то же самое, что незаданная переменная.
- **`Install the extra datacontract-cli[postgres]`.** Инструмент поставлен без экстры. Ставьте
  строго `"datacontract-cli[postgres]"`, кавычки нужны, иначе оболочка съест скобки.
- **`connection refused` на localhost:5432.** Сервер не запущен либо слушает другой порт.
  Проверьте `psql -c "select 1"` тем же пользователем, что положили в переменные окружения.
- **Все проверки типов провалились разом.** Значит, `physicalType` в контракте написан не так,
  как тип называется в каталоге вашей СУБД. Инструмент сравнивает строки с
  `information_schema`, поэтому пишите `timestamp with time zone`, а не `timestamptz`.
- **Проверки `quality` молча не выполняются.** У правила нет порога (`mustBe`, `mustBeGreaterThan`
  и подобных) либо у `invalidValues` не заданы `arguments.validValues`. CLI пишет об этом
  предупреждением в лог и просто пропускает правило, тест при этом остаётся зелёным.
