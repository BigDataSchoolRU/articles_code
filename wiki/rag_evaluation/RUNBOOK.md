# RUNBOOK: метрики поиска и генерации RAG на локальной модели с Ragas

## Окружение

| Что | Версия |
|---|---|
| Python | 3.12 |
| Ragas | `ragas` 0.4.3, Collections API (`ragas.metrics.collections`) |
| Зависимости Ragas с пином | `langchain-community` 0.3.31, `langchain-core` 1.7.6, `langchain-openai` 1.1.9 |
| Клиент LLM | `openai` 1.109.1, `instructor` 1.3.2 (ставится зависимостью Ragas) |
| Ollama | 0.40.13, локальная установка или Docker из этой папки |
| Генератор и судья | `qwen2.5:7b` (4.7 ГБ, ID 845dbda0ea48, Q4_K_M) |
| Модель эмбеддингов | `nomic-embed-text` (274 МБ, ID 0a109f422b47, 768 измерений) |

Ответы генерируются с `temperature 0` и `seed 42`, судья работает с `temperature 0`. Вывод ниже
снят на Ubuntu 24.04, 4 vCPU без GPU, Ollama в Docker. На такой машине первое демо идёт
несколько секунд, а второе около 45 минут: на каждый из 10 примеров уходит ответ модели и две
метрики, и каждая метрика это два-три вызова судьи со структурированным выводом. На GPU или с
облачной моделью-судьёй то же самое идёт за минуты.

Скрипты обращаются к Ollama по адресу `http://localhost:11434` и читают `corpus.jsonl` и
`dataset.jsonl` из текущего каталога. Запускать их нужно из этой папки.

## Шаг 1. Пакеты

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/pip check
.venv/bin/python -c "import ragas; print(ragas.__version__)"
```

Шаг прошёл, если `pip check` пишет `No broken requirements found.`, а последняя команда
печатает `0.4.3`.

## Шаг 2. Ollama и две модели

Если Ollama стоит локально:

```bash
ollama pull qwen2.5:7b
ollama pull nomic-embed-text
ollama list
```

Если Ollama нет, её можно поднять в Docker из этой папки:

```bash
docker compose up -d
docker exec rag-evaluation-ollama ollama pull qwen2.5:7b
docker exec rag-evaluation-ollama ollama pull nomic-embed-text
docker exec rag-evaluation-ollama ollama list
```

Шаг прошёл, если в списке есть обе модели:

```
NAME                       ID              SIZE
nomic-embed-text:latest    0a109f422b47    274 MB
qwen2.5:7b                 845dbda0ea48    4.7 GB
```

В `docker-compose.yml` стоит `OLLAMA_MAX_LOADED_MODELS: "2"`: генератор и модель эмбеддингов
держатся в памяти одновременно, иначе каждый эмбеддинг вопроса выгружал бы 7B модель.

## Шаг 3. Метрики поиска без LLM

```bash
.venv/bin/python retrieval_metrics.py
```

Скрипт строит эмбеддинги 12 фрагментов и 5 вопросов, ранжирует фрагменты по косинусной
близости и считает метрики для двух срезов одного ранжирования: top-3 и top-1. Вывод
детерминирован, он должен совпасть с этим:

```
вопрос | эталон | top-3 по близости
q1 | k02,k03 | k02,k03,k11
q2 | k05,k06 | k06,k05,k01
q3 | k07,k08 | k07,k08,k09
q4 | k10,k11 | k03,k02,k11
q5 | k09,k12 | k03,k02,k09

retriever нормальный top-3
  hit_rate@3 = 1.00
  recall@3   = 0.80
  MRR@3      = 0.73
  nDCG@3     = 0.72
  по вопросам recall: q1=1.00 q2=1.00 q3=1.00 q4=0.50 q5=0.50

retriever испорченный top-1
  hit_rate@1 = 0.60
  recall@1   = 0.30
  MRR@1      = 0.60
  nDCG@1     = 0.60
  по вопросам recall: q1=0.50 q2=0.50 q3=0.50 q4=0.00 q5=0.00
```

Шаг прошёл, если у top-3 `recall@3 = 0.80`, а у top-1 `recall@1 = 0.30`. Сравните строки
таблицы: у q4 и q5 первыми идут нерелевантные `k03` и `k02`, так `nomic-embed-text`
ранжирует этот корпус, а не ошибка разметки.

## Шаг 4. Faithfulness и Context Recall в Ragas

```bash
.venv/bin/python -W ignore::DeprecationWarning ragas_eval.py qwen2.5:7b
```

Судья подключается к Ollama через её OpenAI-совместимый API:

```python
client = AsyncOpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
judge = llm_factory("qwen2.5:7b", client=client, temperature=0, max_tokens=1024)
```

По каждому вопросу скрипт печатает найденные фрагменты, ответ модели, две метрики и время
каждого шага, в конце итог по каждому retriever'у. Пример вывода:

```
### retriever нормальный top-3
q1 контекст=k02,k03,k11
   ответ: Чтобы сохранить порядок событий одного заказа в Kafka, следует использовать один и тот же ключ для всех сообщений этого заказа. Это обеспечит, что все сообщения заказа попадут в одну и ту же партицию и будут обработаны в правильном порядке.
   faithfulness=1.00 context_recall=0.50  (генерация 38 с, faithfulness 136 с, context_recall 212 с)
q2 контекст=k06,k05,k01
   ответ: При настройке acks=all, если синхронных реплик становится меньше, чем значение min.insync.replicas, запись будет отклонена с ошибкой NotEnoughReplicas, так как брокер подтверждает запись только после получения подтверждения от всех реплик из списка ISR.
   faithfulness=0.67 context_recall=1.00  (генерация 42 с, faithfulness 175 с, context_recall 100 с)
q3 контекст=k07,k08,k09
   ответ: Добавление потребителей в группу не ускорит чтение, так как каждый потребитель читает только одну партицию. Предел здесь определяется количеством партиций в топике: если потребителей больше, чем партиций, лишние потребители будут простаивать.
   faithfulness=0.75 context_recall=1.00  (генерация 40 с, faithfulness 159 с, context_recall 94 с)
q4 контекст=k03,k02,k11
   ответ: Kafka хранит все сообщения для каждого ключа, но при настройке cleanup.policy=compact можно оставить только последнее значение каждого ключа, а более старые записи с тем же ключом будут удаляться фоновой очисткой.
   faithfulness=0.67 context_recall=0.50  (генерация 32 с, faithfulness 131 с, context_recall 84 с)
q5 контекст=k03,k02,k09
   ответ: Kafka хранит смещения потребителей в топике __consumer_offsets, а метаданные кластера хранятся внутри самого Kafka.
   faithfulness=0.50 context_recall=1.00  (генерация 19 с, faithfulness 75 с, context_recall 106 с)
ИТОГ нормальный top-3: faithfulness=0.72 context_recall=0.80

### retriever испорченный top-1
q1 контекст=k02
   ответ: Чтобы сохранить порядок событий одного заказа в Kafka, нужно разместить все сообщения, относящиеся к одному заказу, в одну и ту же партицию топика. Таким образом, благодаря гарантии порядка внутри партиции, сообщения будут обрабатываться в том же порядке, в котором они были отправлены.
   faithfulness=0.50 context_recall=1.00  (генерация 33 с, faithfulness 134 с, context_recall 77 с)
q2 контекст=k06
   ответ: Если синхронных реплик осталось меньше, чем значение параметра min.insync.replicas при acks=all, запись будет отклонена с ошибкой NotEnoughReplicas.
   faithfulness=1.00 context_recall=0.50  (генерация 20 с, faithfulness 93 с, context_recall 98 с)
q3 контекст=k07
   ответ: Добавление потребителей в группу может ускорить чтение, так как увеличивает параллельность обработки данных. Однако есть предел, связанный с нагрузкой на брокеры и эффективностью работы системы в целом.
   faithfulness=0.20 context_recall=0.50  (генерация 25 с, faithfulness 163 с, context_recall 85 с)
q4 контекст=k03
   ответ: По контексту нельзя точно определить, сколько времени Kafka хранит сообщения. Что касается хранения только последнего значения каждого ключа, то это возможно с помощью конфигурации топиков в Kafka, настроив их так, чтобы они хранили только последнее сообщение с каждым ключом.
   faithfulness=0.67 context_recall=1.00  (генерация 34 с, faithfulness 142 с, context_recall 66 с)
q5 контекст=k03
   ответ: По контексту не указано, где Kafka хранит смещения потребителей и метаданные кластера.
   faithfulness=0.00 context_recall=1.00  (генерация 13 с, faithfulness 53 с, context_recall 83 с)
ИТОГ испорченный top-1: faithfulness=0.47 context_recall=0.80
```

Шаг прошёл, если скрипт дошёл до двух строк `ИТОГ` без `nan`. Ответы и оценки судьи от
прогона к прогону могут немного расходиться: даже при `temperature 0` и `seed 42` генерация
qwen2.5:7b на CPU не воспроизводится побайтно.

Как читать результат. Recall по разметке из шага 3 падает с 0.80 до 0.30, а Context Recall от
судьи qwen2.5:7b остаётся 0.80 у обоих retriever'ов: на q4 и q5 судья ставит 1.00 контексту из
одного нерелевантного фрагмента `k03`. В разметке утверждений, которую судья возвращает вместе
с оценкой, обоснование звучит как «упоминается в ответе»: модель сверяет эталон сам с собой, а
не с найденным контекстом. Faithfulness при этом падает с 0.72 до 0.47: получив бедный контекст,
генератор достраивает ответ из собственных знаний (q3 у top-1), а честный отказ «по контексту не
указано» Ragas засчитывает как неподтверждённое утверждение (q5 у top-1, 0.00). Метрика от
LLM-судьи хороша ровно настолько, насколько хорош судья, поэтому её стоит сверять с
детерминированной метрикой на размеченной выборке.

## Если не так

- **`ModuleNotFoundError: No module named 'langchain_community.chat_models.vertexai'` при
  `import ragas`.** В venv встал `langchain-community` 0.4.x, где этого модуля уже нет, а Ragas
  0.4.3 импортирует его безусловно. Поставьте пин из `requirements.txt`:
  `.venv/bin/pip install "langchain-community==0.3.31"`.
- **`openai.APIConnectionError` или `Connection refused`.** Ollama не запущена или слушает другой
  адрес. Проверьте `curl http://localhost:11434/api/version`.
- **`model "qwen2.5:7b" not found`.** Модель не скачана в тот экземпляр Ollama, к которому идёт
  запрос. Повторите шаг 2.
- **Метрика возвращает `nan`.** Судья не извлёк из ответа ни одного утверждения или вернул JSON
  не по схеме. Чаще так бывает с маленькими моделями-судьями. Возьмите судью крупнее или
  поднимите `max_tokens`.
- **Context Recall одинаковый у хорошего и плохого retriever'а.** Это ограничение судьи, а не
  ошибка кода: 7B модель плохо отличает «утверждение есть в контексте» от «утверждение есть в
  эталоне». Сверьте с recall из шага 3 и возьмите судью крупнее.
- **Второе демо идёт очень долго.** На CPU это нормально, ориентир 1.5-6 минут на один пример.
  Для пробного запуска оставьте в `dataset.jsonl` один вопрос.
