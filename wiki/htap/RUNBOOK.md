# RUNBOOK: конфликт нагрузок OLTP и OLAP и колоночная реплика

Демо к статье про HTAP. Показывает две вещи на одних и тех же данных: во что
превращается латентность точечных UPDATE, когда по той же таблице идёт
аналитика, и что меняется, если аналитику увести в колоночную копию.

Это не HTAP-система, а её ручная сборка из двух движков. Внутри TiDB с TiFlash
или AlloyDB происходит то же самое, только репликация встроена и идёт из журнала,
а не через выгрузку в файл.

## Окружение

| Что | Версия | Зачем |
|---|---|---|
| PostgreSQL | 18.x | строковое хранилище, транзакционная нагрузка |
| DuckDB | 1.5.5 | колоночное хранилище для аналитики |
| Python | 3.12 | обвязка и замеры |
| psycopg | 3.3.x | драйвер PostgreSQL |
| pytz | любая свежая | нужен DuckDB для колонок `TIMESTAMPTZ` |

Понадобится около 2 ГБ на диске: таблица на 12 млн строк, CSV-снимок и колоночный
файл. Полный прогон занимает около четырёх минут, из них почти минута уходит на
первичное наполнение таблицы.

## Шаг 1. Поставить зависимости

```bash
python3 -m venv .venv
./.venv/bin/python3 -m pip install "psycopg[binary]" duckdb pytz
```

Проверка: обе библиотеки импортируются и печатают версии.

```bash
./.venv/bin/python3 -c "import duckdb, psycopg; print(duckdb.__version__, psycopg.__version__)"
```

Ожидаемый вывод вида `1.5.5 3.3.4`.

## Шаг 2. Поднять PostgreSQL и создать базу

Запуск сервера зависит от способа установки. Дальше нужна только пустая база
`htap_demo` и доступ к ней без пароля с локальной машины.

```bash
createdb htap_demo
psql -d htap_demo -c "select version()"
```

Шаг прошёл, если `psql` напечатал строку с версией PostgreSQL 18.

Если сервер слушает не локально или требует логин, подставьте свою строку
подключения через переменную окружения, она читается обоими скриптами:

```bash
export HTAP_DSN="host=ВАШ_ХОСТ port=5432 dbname=htap_demo user=ВАШ_ПОЛЬЗОВАТЕЛЬ"
```

## Шаг 3. Демо 1: транзакции под аналитикой

```bash
./.venv/bin/python3 oltp_under_analytics.py
```

Первый запуск сам создаёт таблицу `orders` и наполняет её двенадцатью миллионами
строк, это занимает около минуты. Дальше скрипт делает два замера по 300 точечных
UPDATE: сначала в тишине, потом под шестью параллельными соединениями, которые
крутят агрегацию по всей таблице.

В выводе должны быть обе фазы и итоговое сравнение:

```
--- фаза 1: только транзакционная нагрузка ---
[тишина] UPDATE x300: p50 ... мс, p95 ... мс
--- фаза 2: те же UPDATE под 6 параллельными агрегациями ---
[под нагрузкой] UPDATE x300: p50 ... мс, p95 ... мс
```

Шаг прошёл, если аналитический запрос под конкурентами идёт заметно дольше, чем в
одиночку, а хвост латентности UPDATE (p95) подрос. На быстром SSD медиана точечных
UPDATE почти не меняется: первым страдает не она, а предсказуемость времени ответа
аналитики. Это и надо увидеть.

## Шаг 4. Демо 2: колоночная реплика

```bash
./.venv/bin/python3 columnar_replica.py
```

Скрипт выгружает таблицу в CSV, заливает в DuckDB, гоняет там тот же самый SQL
и меряет четыре вещи: цену первичной заливки, время запроса в двух хранилищах,
латентность UPDATE, пока аналитика идёт в реплике, и окно рассинхрона после
вставки двадцати тысяч новых заказов.

Шаг прошёл, если в выводе есть все четыре блока «шаг 1» — «шаг 4», колоночный
файл заметно меньше таблицы в PostgreSQL, а запрос в колоночном хранилище идёт
быстрее.

## Если не так

**`psql: command not found`.** Бинарники PostgreSQL могут быть не в `PATH`,
особенно у сборок из пакетных менеджеров. Добавьте каталог `bin` вашей установки
в `PATH` или зовите `psql` полным путём.

**`connection failed` при запуске скриптов.** Скрипты по умолчанию идут в
`dbname=htap_demo` через локальный сокет. Любое другое подключение задаётся
переменной `HTAP_DSN`, править код не нужно.

**`Required module 'pytz' failed to import`.** DuckDB просит `pytz`, когда
отдаёт значения `TIMESTAMPTZ` в Python. Поставьте пакет в то же окружение,
из которого запускаете скрипт.

**Разница между хранилищами почти нулевая.** Скорее всего таблица целиком
поместилась в кэш, так бывает при уменьшении `ROWS`. Колоночное хранение
выигрывает на объёме, которого нет в оперативной памяти, поэтому уменьшать
размер таблицы для ускорения прогона смысла нет.

**Прогон надо повторить с нуля.** Удалите базу и файлы реплики, следующий запуск
пересоздаст всё сам:

```bash
dropdb htap_demo && rm -f orders_columnar.duckdb orders_snapshot.csv
```
