# RUNBOOK: LevelDB через plyvel

Окружение, на котором проверялись примеры:

- macOS (arm64), Homebrew
- LevelDB 1.23 (пакет Homebrew `leveldb`, тянет `snappy`)
- Python 3.12, пакет `plyvel` 1.5.1

Ничего кроме локальных пакетов не требуется — LevelDB работает как embedded-библиотека
внутри процесса, отдельный сервер поднимать не нужно.

## 1. Установка LevelDB и заголовков

```bash
brew install leveldb snappy
```

Проверка: `brew list --versions leveldb` должен показать установленную версию (например,
`leveldb 1.23_2`).

## 2. Установка plyvel

**Важно.** Начиная с версии 1.23 LevelDB собирается без RTTI (Run-Time Type Information), а
`plyvel` по умолчанию собирает свою C++-обвязку с RTTI и падает на импорте с ошибкой вида
`symbol not found in flat namespace '__ZTIN7leveldb10ComparatorE'`. Обычная установка
`pip install plyvel` эту проблему не покажет на этапе сборки — она проявится только при
попытке импортировать модуль. Собирайте `plyvel` с явно выключенным RTTI и явными путями к
заголовкам/библиотекам Homebrew:

```bash
CXXFLAGS="-I$(brew --prefix leveldb)/include -I$(brew --prefix snappy)/include -fno-rtti" \
LDFLAGS="-L$(brew --prefix leveldb)/lib -L$(brew --prefix snappy)/lib" \
pip install --force-reinstall --no-cache-dir --no-build-isolation plyvel
```

Проверка:

```bash
python3 -c "import plyvel; print(plyvel.__version__)"
```

В выводе должна появиться версия `plyvel` без трассировки ошибок импорта.

## 3. Базовые операции: Put/Get/Delete, batch, снапшот, итерация

```bash
python3 basic_operations.py
```

В выводе должно быть видно:
- значение, записанное через `Put`, читается через `Get`;
- после атомарного `write_batch()` одна запись появилась, другая (удалённая в том же
  батче) пропала;
- снапшот, снятый до очередной записи, не видит эту запись, хотя текущая ручка `db` —
  видит;
- итератор по диапазону ключей возвращает пары в отсортированном порядке, ключ на границе
  `stop` не включён.

## 4. Compaction между уровнями и восстановление после сбоя

```bash
python3 compaction_and_recovery.py
```

Первая часть вывода — запись около 10 МБ данных с уменьшенным `write_buffer_size`, чтобы
compaction прошёл в пределах секунд, а не гигабайт. В выводе будет видно, на каком уровне
(`leveldb.num-files-at-levelN`) физически осели SSTable-файлы, и построчный список файлов с
диапазонами ключей (`leveldb.sstables`) — это и есть картина уровней LSM-дерева на диске.

Вторая часть запускает отдельный процесс-писатель, убивает его `SIGKILL` через секунду
(не дав вызвать `close()`), затем открывает ту же базу заново. В выводе будет видно, сколько
записей из уже отправленных `Put()` восстановилось — LevelDB проигрывает log-файл заново при
открытии базы после нечистого закрытия.

**Числа не воспроизводятся один в один.** Момент, на котором `SIGKILL` прервёт писатель, и
итоговое число уровней/файлов зависят от скорости диска и планировщика ОС — сам механизм
(данные из log-файла переживают убийство процесса) воспроизводится стабильно, точное число
записей и файлов — нет.

## Если не так

- **`fatal error: 'leveldb/db.h' file not found`** при установке `plyvel` — заголовки
  Homebrew не попали в путь компилятора. Убедитесь, что `CXXFLAGS`/`LDFLAGS` из шага 2 заданы
  в той же команде, что и `pip install`.
- **`symbol not found in flat namespace '__ZTIN7leveldb10ComparatorE'`** при импорте
  `plyvel` — plyvel собран без флага `-fno-rtti` против LevelDB 1.23+. Переустановите по шагу
  2, обязательно с `--force-reinstall --no-cache-dir --no-build-isolation`, иначе pip отдаст
  уже собранное (сломанное) колесо из кэша.
- **`IOError: lock ... already held by process`** — предыдущий запуск не закрыл базу
  корректно (например, прерван вручную). Файл `LOCK` внутри каталога базы держится только
  живым процессом; после его завершения блокировка снимается сама. Если процесс завис,
  завершите его и повторите запуск.
- **`compaction_and_recovery.py` показывает 0 восстановленных записей** — писатель не успел
  сделать ни одного `Put()` до `SIGKILL` (слишком медленный старт процесса на медленной
  машине). Увеличьте паузу перед `os.kill()` в скрипте.
