# RUNBOOK: три типа окон в Spark Structured Streaming

Стенд для статьи https://bigdataschool.ru/wiki/windowing/ . Поднимается одной командой, внешних
сервисов, Kafka и ключей не нужно: поток имитирует файловый источник, который читает по одному
файлу за микробатч.

## Окружение

| Компонент | Версия | Откуда |
|---|---|---|
| Apache Spark (PySpark) | 4.0.4, Scala 2.13, Java 17 | образ `apache/spark:4.0.4-scala2.13-java17-python3-ubuntu`, 2.1 ГБ |
| Python внутри образа | 3.10.12 | образ |
| Docker / Compose | 29.1 / 2.40 | любой Docker с Compose v2 |

Нужно: около 3 ГБ свободной памяти (`mem_limit: 3g` в `compose.yaml`), 2.1 ГБ диска под образ.
Ниже `/path/to/windowing` это ваша папка проекта.

## Шаг 1. Образ Spark

```bash
docker pull apache/spark:4.0.4-scala2.13-java17-python3-ubuntu
docker run --rm --entrypoint /opt/spark/bin/spark-submit \
  apache/spark:4.0.4-scala2.13-java17-python3-ubuntu --version 2>&1 | grep "version 4"
```

В выводе строка с `version 4.0.4`. Шаг прошёл, если образ скачан и версия совпала.

## Шаг 2. Входные данные

```bash
cd /path/to/windowing
wc -l events.jsonl
```

Ожидаемо `17 events.jsonl`. Пользователь `a` пишет плотно с 12:01 до 12:16, затем пауза до
12:31; у `b` паузы 12:02 → 12:09 и 12:11 → 12:24. Событие `e15` с временем 12:05 приходит в
пятом микробатче, когда поток уже ушёл к 12:33, и должно быть отброшено как опоздавшее.

## Шаг 3. Прогон

```bash
docker compose run --rm spark
```

Скрипт кладёт события в `/tmp/windowing/input` внутри контейнера, по файлу на микробатч, и
запускает три запроса с `trigger(availableNow=True)` и `maxFilesPerTrigger=1`.

Что должно быть в выводе:

1. Сколько окон получает одно событие:

   ```
   tumbling: окон на событие -> событий [(1, 17)]
   sliding: окон на событие -> событий [(2, 17)]
   e01 12:01 в sliding-окнах: [11:55, 12:05), [12:00, 12:10)
   в физическом плане sliding-агрегации: ['Expand ']
   ```

   В sliding-окне 10 минут с шагом 5 каждое событие попадает в 10 / 5 = 2 окна; оператор
   `Expand` в плане и есть это размножение строк.

2. Для каждого типа окна таблица микробатчей: watermark, сколько окон в состоянии, сколько
   выдано, сколько строк отброшено как опоздавшие. В батче 4 (watermark 12:28) событие `e15`
   отбрасывается: у tumbling и session `отброшено_опоздавших` равно 1, у sliding 2, потому что
   опоздавшее событие к этому моменту уже размножено на два окна. Последний батч 5 приходит без
   данных: Spark сам запускает его, чтобы сдвинуть watermark до 12:41 и закрыть окна.

3. Закрытые окна. Session-окна у пользователя `a`:

   ```
   a  [12:01, 12:21)  cnt=6  e01,e03,e04,e07,e08,e09
   a  [12:31, 12:38)  cnt=2  e13,e14
   ```

4. Сводка:

   ```
   тип        окон_выдано  сумма_cnt  окон_осталось_в_состоянии
   tumbling             6         14                          2
   sliding             14         28                          4
   session              5         14                          2
   ```

   Из 17 событий одно отброшено, а два последних (12:44 и 12:46) сидят в ещё открытых окнах:
   новых событий нет, watermark не двигается, и эти окна не закроются, пока поток не продолжится.

Шаг прошёл, если цифры сводки совпали. Холодный запуск около минуты.

## Если не так

- **`Permission denied` при записи в папку проекта.** Образ `apache/spark` работает от uid 185, а
  папка смонтирована только на чтение. Скрипт пишет всё в `/tmp/windowing` контейнера; если вы
  поменяли `WORK` на путь в папке проекта, верните `/tmp`.
- **Окна не выдаются вообще.** Режим append выдаёт окно только после того, как watermark прошёл
  его конец. Без `withWatermark` агрегация по окну в append не запустится вовсе:
  `AnalysisException [STREAMING_OUTPUT_MODE.UNSUPPORTED_OPERATION] Invalid streaming output mode: append`.
  Со слишком большим запаздыванием окна копятся в состоянии и выходят позже.
- **`Invalid streaming output mode: update` на session-окнах.** Агрегация по `session_window`
  не поддерживает режим update, демо работает в append с watermark.
- **Сдвиг окон на часы.** Время событий без смещения трактуется в часовом поясе сессии. Скрипт
  ставит `spark.sql.session.timeZone=UTC`; без этого границы окон съедут на ваш пояс.
- **Батчи пришли не по порядку.** Файловый источник выбирает файлы по времени изменения; скрипт
  проставляет его явно через `os.utime`. Если копируете файлы руками, порядок микробатчей может
  смешаться, и опоздавшим станет другое событие.
- **Контейнер убит по памяти.** Поднимите `mem_limit` в `compose.yaml` или уменьшите `local[2]`
  до `local[1]`.
