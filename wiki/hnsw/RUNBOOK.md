# RUNBOOK: HNSW на hnswlib и FAISS

Пошаговый прогон демо к статье [HNSW](https://bigdataschool.ru/wiki/hnsw/). Индекс строится
на 100 000 синтетических векторов размерности 128 двумя реализациями: эталонной hnswlib от
авторов алгоритма и FAISS `IndexHNSWFlat`, которая открывает доступ к уровням графа и счётчику
вычисленных расстояний. Пять сценариев: уровни графа, компромисс `ef`, цена `M`, фильтрация,
удаление пометкой. Эталон для recall считается точным перебором.

## Окружение

| Компонент | Версия |
|---|---|
| Python | 3.12 или новее (этого требует numpy 2.5.4), проверено на 3.12.3 |
| hnswlib | 0.8.0, под Python 3.12 собирается из исходников, нужен компилятор C++ |
| faiss-cpu | 1.15.1 |
| numpy | 2.5.4 |
| Железо | проверено на 4 vCPU Intel Xeon Platinum 8175M, 15.7 ГБ RAM, без GPU |

Пик памяти одного сценария около 420 МБ, весь прогон идёт около 4.5 минут. Миллисекунды и
секунды сборки у вас будут другими: они зависят от процессора. Распределение по слоям в
сценарии `levels` и строки сценария `filter` совпадут, recall у hnswlib может отличаться в
третьем знаке, потому что сборка в несколько потоков даёт немного разный граф.

Данные синтетические, их генерирует `data.py` с seed 42: смесь 200 гауссовых кластеров во
внутреннем пространстве из 32 измерений, развёрнутая в 128 с небольшим шумом. Равномерный шум
не берём: в 128 измерениях это худший случай для графового индекса и на эмбеддинги он не похож.
Цифры recall на реальных эмбеддингах будут другими, форма кривых останется той же.

## Шаг 1. Окружение Python

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m pip list | grep -Ei "^(hnswlib|faiss-cpu|numpy) "
```

Ожидаемо: три строки `faiss-cpu 1.15.1`, `hnswlib 0.8.0`, `numpy 2.5.4`. Колесо hnswlib pip
собирает на месте, в логе будет `Building wheel for hnswlib (pyproject.toml)`.

## Шаг 2. Данные и эталон

```bash
.venv/bin/python data.py
```

Ожидаемо:

```
эталон точным перебором numpy: 1000 запросов по 100000 векторов за 1.1 с
{'base': (100000, 128), 'queries': (1000, 128), 'category': (100000,), 'gt': (1000, 10)}
```

Рядом появится `data_cache.npz` около 50 МБ. Следующие запуски берут данные из него. Чтобы

## Шаг 3. Уровни графа

```bash
.venv/bin/python hnsw_demo.py levels
```

FAISS строит граф с `M=16` и печатает, на каком верхнем слое живёт каждый вектор. Уровень
выбирается случайно, вероятность оказаться выше падает в `M` раз на каждый слой, поэтому
ожидание считается как `(1-1/M)*M^-l`. Ожидаемо:

```
соседей на слое 0: 32, на слоях выше: 16
верхний слой графа max_level = 4, точка входа: вектор 20288, его верхний слой 4
верхний слой | векторов | доля     | ожидание (1-1/M)*M^-l | есть на слое (снизу вверх)
           0 |    93626 |  0.93626 |               93750.0 | 100000
           1 |     6003 |  0.06003 |                5859.4 | 6374
           2 |      351 |  0.00351 |                 366.2 | 371
           3 |       19 |  0.00019 |                  22.9 | 20
           4 |        1 |  0.00001 |                   1.4 | 1
efSearch | recall@10 | расстояний на запрос | доля базы | мс/запрос
      16 |    0.8810 |                  480 |    0.0048 | 0.081
      40 |    0.9678 |                  854 |    0.0085 | 0.154
     160 |    0.9992 |                 2460 |    0.0246 | 0.488
```

Как понять, что шаг прошёл: на нулевом слое соседей вдвое больше, чем на верхних; доли по слоям
близки к ожиданию; при `efSearch=40` поиск считает расстояния меньше чем до 1% базы.

## Шаг 4. Recall и латентность при росте ef

```bash
.venv/bin/python hnsw_demo.py ef_sweep
```

hnswlib с `M=16`, `ef_construction=200`. Поиск идёт в один поток, рядом для сравнения точный
перебор FAISS `IndexFlatL2` по одному запросу. Ожидаемо (миллисекунды у вас другие):

```
точный перебор IndexFlatL2: recall@10 = 1.0000, 5.872 мс/запрос
ef  | recall@10 | мс/запрос | быстрее перебора
 10 |    0.7906 |     0.055 |  106.4x
 20 |    0.9045 |     0.083 |   70.5x
 40 |    0.9644 |     0.136 |   43.1x
 80 |    0.9921 |     0.234 |   25.1x
160 |    0.9982 |     0.428 |   13.7x
320 |    1.0000 |     0.825 |    7.1x
```

Как понять, что шаг прошёл: recall растёт с `ef` и выходит к 1.0, латентность растёт медленнее `ef`:
при росте `ef` в 32 раза, с 10 до 320, она выросла примерно в 15 раз.

## Шаг 6. Фильтр после поиска и фильтр внутри обхода

```bash
.venv/bin/python hnsw_demo.py filter
```

У каждого вектора есть атрибут `category` от 0 до 99, фильтр `category == 0` пропускает около 1%
базы. Эталон считается перебором только по подходящим векторам. Сравниваются отбор после
поиска (индекс отдаёт `ef` кандидатов, фильтр выкидывает лишнее), фильтр внутри обхода
(параметр `filter` у `knn_query` в hnswlib) и точный перебор по подходящим векторам без графа.
Ожидаемо:

```
фильтр category == 0: подходит 1078 из 100000 (1.08%)
стратегия                         | ef   | строк из 10, среднее | запросов с 10 | recall@10 | мс/запрос
после поиска, взять ef кандидатов  |   40 |                 0.47 |             0 |    0.0470 | 0.137
после поиска, взять ef кандидатов  |  400 |                 4.36 |            12 |    0.4355 | 1.058
после поиска, взять ef кандидатов  | 2000 |                10.00 |           998 |    0.9990 | 5.034
внутри обхода (filter=)           |   40 |                10.00 |          1000 |    1.0000 | 8.610
внутри обхода (filter=)           |  400 |                10.00 |          1000 |    1.0000 | 49.495
предфильтр: перебор 1078 подходящих | —    |                10.00 |          1000 |    1.0000 | 0.029
цена колбэка при ef=40: без фильтра 0.144 мс, filter=lambda: True 0.180 мс на запрос
```

Как понять, что шаг прошёл: при `ef=40` отбор после поиска возвращает меньше одной строки из
десяти; фильтр внутри обхода всегда отдаёт 10 строк, но медленно; перебор по подходящим
векторам быстрее всех. Последняя строка показывает, что сам вызов функции Python почти ничего
не стоит: время уходит на то, что обход идёт по графу далеко, пока не наберёт 10 подходящих.

## Шаг 7. Удаление пометкой

```bash
.venv/bin/python hnsw_demo.py delete
```

Каждый десятый вектор помечается удалённым через `mark_deleted`, затем 10 000 новых векторов
добавляются с `replace_deleted=True`. Индекс создан с `allow_replace_deleted=True`. Ожидаемо:

```
помечено удалёнными: 10000; удалённых в выдаче: 0 из 10000
recall@10 по живым векторам: 0.9686
элементов в индексе: 100000, размер 63.0 -> 63.0 МБ
после add_items(replace_deleted=True) на 10000 новых: элементов 100000, max_elements 100000, размер 63.0 МБ
```

Как понять, что шаг прошёл: помеченные векторы в выдачу не попадают, но размер индекса после
пометки не меняется; новые векторы занимают слоты помеченных, и индекс не растёт.

## Если не так

- **pip падает на `Building wheel for hnswlib`.** Скорее всего, нет компилятора C++.
  На Ubuntu и Debian: `sudo apt install build-essential`, на macOS: `xcode-select --install`.
- **`RuntimeError: Cannot return the results in a contiguous 2D array`.** hnswlib не набрал `k`
  результатов: `ef` меньше `k` либо фильтр пропускает меньше `k` векторов. Поднимите `ef` через
  `set_ef` или ослабьте фильтр.
- **`RuntimeError: Replacement of deleted elements is disabled in constructor`.** Индекс создан
  без `allow_replace_deleted=True`, а `add_items` вызван с `replace_deleted=True`.
- **Латентность сильно выше, чем в таблицах.** Проверьте, что на машине нет другой нагрузки:
  поиск идёт в один поток и чувствителен к соседям по CPU. Кэш `data_cache.npz` от другой
  версии `data.py` удалите, данные пересоберутся.
- **Recall у hnswlib отличается в третьем знаке.** Сборка идёт в `BUILD_THREADS` потоков, порядок
  вставки между потоками недетерминирован, граф выходит немного разным. Для повторяемого графа
  поставьте `BUILD_THREADS = 1`, сборка станет медленнее в несколько раз.
