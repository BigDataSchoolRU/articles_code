# RUNBOOK: LSM-Tree на LevelDB

Демо показывает механику LSM-дерева (memtable, WAL, SST-файлы, уровни, компакция,
write/read amplification) на встроенной библиотеке LevelDB через Python-обвязку
plyvel. Внешние сервисы не нужны — вся работа идёт внутри одного процесса.

## Окружение

- macOS, Homebrew.
- `leveldb` 1.23_2, `snappy` 1.2.2 (нужна как зависимость LevelDB, сама демо-код не
  использует напрямую).
- Python 3.12, пакет `plyvel` 1.5.1.
- Свободное место во временном каталоге (`/tmp`) — демо создаёт и удаляет свои базы
  само, около 5-10 МБ на прогон.

Подставьте свои значения там, где ниже написано `<...>`.

## Шаг 1. Установка зависимостей

```bash
brew install leveldb snappy
python3 -m venv <ваш_venv>
source <ваш_venv>/bin/activate
CXXFLAGS="-I$(brew --prefix leveldb)/include -I$(brew --prefix snappy)/include -fno-rtti" \
LDFLAGS="-L$(brew --prefix leveldb)/lib -L$(brew --prefix snappy)/lib" \
pip install --no-cache-dir --no-build-isolation plyvel==1.5.1
```

**Почему `-fno-rtti` обязателен.** Начиная с LevelDB 1.23 библиотека собирается без
RTTI, а `plyvel` по умолчанию собирает свою C++-обвязку с RTTI. Обычная установка
(`pip install plyvel`) пройдёт без ошибок на этапе сборки, но упадёт при первом
`import plyvel`:

```
ImportError: dlopen(...): symbol not found in flat namespace '__ZTIN7leveldb10ComparatorE'
```

Что должно быть в выводе: пакет `plyvel` ставится без ошибок, `pip show plyvel`
показывает версию `1.5.1`.

Проверка:

```bash
python3 -c "import plyvel; print(plyvel.__version__)"
```

Ожидаемый вывод: `1.5.1`.

## Шаг 2. Путь записи, путь чтения, уровни

```bash
python3 write_read_path.py
```

Что должно быть в выводе:

- три строки вида `после N записей: WAL=[...], SST-файлов=..., L0=..., L1=...` —
  видно, как растёт число файлов уровня L0 по мере флашей memtable;
- блок `leveldb.sstables` со списком файлов по уровням и диапазонами ключей в каждом
  — обратите внимание, что диапазоны файлов level 0 могут пересекаться, а на level 1
  и ниже не пересекаются;
- строка `Отношение (до/после): N.NNx` — во сколько раз ускорился `Get` после того,
  как фоновая компакция слила файлы L0 в L1.

Как понять, что шаг прошёл: скрипт завершается без трассировки исключения и печатает
финальную строку с отношением времени чтения.

## Шаг 3. Write amplification и space amplification компакции

```bash
python3 write_amplification.py
```

Что должно быть в выводе: таблица `leveldb.stats` по уровням, строка `Write
amplification: N.NNx` и строка с итоговым отношением объёма на диске к логически
записанному объёму (меньше 1.0 — компакция выбросила устаревшие версии
перезаписанных ключей).

Как понять, что шаг прошёл: обе строки с отношениями напечатаны, скрипт завершился
без исключения.

## Если не так

- **`ImportError` / `symbol not found in flat namespace`** при `import plyvel` —
  значит `plyvel` собрался с RTTI против LevelDB без RTTI. Переустановите с флагами
  из шага 1, обязательно добавив `--no-cache-dir` и (если уже стоит битая версия)
  `--force-reinstall` — иначе pip подставит уже собранное колесо повторно.
- **Отношение времени чтения в `write_read_path.py` близко к 1.0x или даже меньше** —
  фоновый поток компакции LevelDB не детерминирован по времени: если он успел
  доработать ещё до первого замера, разница пропадёт. Это не баг демо, а
  особенность фоновой компакции — при повторном запуске обычно видна разница
  в 2-4 раза.
- **`IOError: lock ...`** при повторном запуске сразу после сбоя предыдущего — база
  в `/tmp` не была закрыта корректно. Удалите каталог руками (`rm -rf
  /tmp/lsm_tree_demo_*`) и запустите скрипт заново.
