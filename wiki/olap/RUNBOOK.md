# RUNBOOK: OLAP — звёздная схема, CUBE/ROLLUP и колоночное ускорение

Демо поднимает классическую звёздную схему в PostgreSQL (ROLAP: куб считается join'ом факта
и измерений на каждый запрос, не хранится отдельной структурой), показывает операции
slice/dice/roll-up/CUBE/pivot через обычный SQL, а затем сравнивает ту же агрегацию на
строковом движке (PostgreSQL) и на колоночном (DuckDB).

## Окружение

- PostgreSQL 14 или новее (демо прогонялось на 18.4), права на `CREATE DATABASE`.
- Python 3.10+, пакеты `psycopg[binary]`, `duckdb`, `pandas`.
- Клиенты `createdb`, `dropdb` в `PATH`.
- Замените адрес подключения на свой, если Postgres не на `localhost` — все скрипты
  подключаются штатными переменными окружения `PG*` / `.pgpass`, без хардкода хоста.

```bash
pip install "psycopg[binary]" duckdb pandas
```

## Шаг 1. Звёздная схема и данные

```bash
python3 db_setup.py
```

Пересоздаёт базу `olap_demo` (если существовала — удаляет и создаёт заново): три измерения
(`dim_date` — 731 день 2024-2025, `dim_product` — 60 товаров в 6 категориях, `dim_store` —
25 магазинов в 5 регионах) и факт `fact_sales` на 1 000 000 строк, сгенерированных прямо в
Postgre SQL (`generate_series` + `random()`, детерминированно через `setseed`).

Ожидаемый вывод:

```
fact_sales: 1 000 000 строк за ~10 с
dim_date=731, dim_product=60, dim_store=25, fact_sales=1000000
```

## Шаг 2. Операции над кубом

```bash
python3 cube_operations.py
```

Пять блоков вывода подряд: `SLICE` (срез по одному измерению), `DICE` (вырезка по
нескольким), `ROLL-UP` (иерархия итогов год → квартал → общий итог через
`GROUP BY ROLLUP`), `CUBE` (все сочетания категория x регион через `GROUP BY CUBE`),
`PIVOT` (сводная категория x квартал через `FILTER`). В `ROLL-UP` и `CUBE` строки итогов
помечены `grouping_level` — ненулевое значение и есть подсчитанный `GROUPING()`, отличающий
итоговую строку от обычной группы с совпадением по NULL.

## Шаг 3. ROLAP против колоночного движка

```bash
python3 columnar_compare.py
```

Выгружает денормализованный снимок факта (join с измерениями) из PostgreSQL, грузит его в
DuckDB как физическую таблицу и агрегирует одинаковый запрос («выручка и количество по
категории и кварталу») в обоих движках после прогревочного вызова каждого. Ожидаемая
картина на объёме в 1 млн строк: PostgreSQL укладывается в десятые доли секунды на тёплом
кэше, DuckDB — в единицы миллисекунд, ускорение на порядок. Первые пять строк результата
DuckDB печатаются в конце для примера, скрипт их с результатом PostgreSQL не сверяет.

## Если не так

- **`columnar_compare.py` не показывает ускорения или DuckDB медленнее Postgres.**
  Снимок из Postgres должен лечь в DuckDB как физическая таблица
  (`CREATE TABLE ... AS SELECT * FROM <DataFrame>`), а не как представление поверх
  зарегистрированного pandas DataFrame (`duck.register(...)` + `SELECT * FROM
  <зарегистрированное_имя>`) — DuckDB тогда каждый раз заново сканирует объект Python, и
  оверхед перекрывает выигрыш колоночного хранения.
- **`ROLLUP`/`CUBE` не подсвечивают итоговые строки.** Проверяйте `grouping_level`
  (`GROUPING()`), а не сравнение колонки с `NULL` — обычная группа тоже может иметь `NULL`
  в измерении, если такое значение реально встречается в данных.
- **`dropdb`/`createdb` не найдены.** Бинарники PostgreSQL часто не добавлены в `PATH`
  (например, Homebrew-сборка на macOS собирает их keg-only) — укажите полный путь до
  `bin`-каталога установки.
