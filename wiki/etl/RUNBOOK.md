# ETL-конвейер на Python: воспроизведение демо

Демо показывает классический ETL целиком: Extract читает сырую таблицу источника как есть,
Transform чистит и агрегирует данные в pandas — вне базы, Load полностью перезаписывает целевую
таблицу результатом (full load). Ключевая мысль, которую показывает код: между extract и load
данные лежат в процессе Python, а не в SQL внутри хранилища — это и есть staging area
классического ETL, в отличие от ELT, где трансформацию сделал бы SQL уже после загрузки.

## Окружение

| Компонент | Версия |
|---|---|
| Python | 3.12 |
| pandas | 3.0.5 |
| psycopg | 3.3.4 (пакет `psycopg[binary]`) |
| PostgreSQL | 18.x, локальный |

Что должно быть доступно: работающий сервер PostgreSQL на `localhost:5432` и пользователь,
которому разрешено создавать базы данных. Имя пользователя в скриптах — `techfriends`, замените
на своё. Все адреса локальные.

## Шаг 1. Поставить зависимости

```bash
python3 -m venv .venv
./.venv/bin/python3 -m pip install "pandas==3.0.5" "psycopg[binary]==3.3.4"
```

## Шаг 2. Подставить своего пользователя БД

В `db_setup.py` и `etl_pipeline.py` замените `user=techfriends` в строках `ADMIN_DSN`/`DSN` на
имя своего пользователя PostgreSQL. Если используете пароль, а не доверительную аутентификацию
по сокету, добавьте в DSN `password=<пароль>`.

## Шаг 3. Поднять источник (Extract-сторону)

```bash
./.venv/bin/python3 db_setup.py
```

Ожидаемый вывод:

```
база etl_demo создана
таблица raw_orders пересоздана, строк: 5030
  из них id с дублями: 30, строк с NULL в quantity/unit_price: 52
```

Скрипт идемпотентный: создаёт базу `etl_demo`, если её ещё нет, и каждый раз пересоздаёт таблицу
`raw_orders` заново — 5000 "чистых" строк плюс намеренные дефекты источника: 30 строк-дублей (как
при повторной выгрузке без сдвига offset), 52 строки с пропуском в `quantity` или `unit_price`, и
часть значений `region` с лишними пробелами или в другом регистре.

## Шаг 4. Прогнать сам конвейер

```bash
./.venv/bin/python3 etl_pipeline.py
```

Ожидаемый вывод — строка статистики трансформации и замер по стадиям:

```
extract: 5030 строк -> после очистки и фильтра status=completed: 3183 -> агрегировано в 898 строк
extract 0.015 с, transform 0.007 с, load 0.030 с, итого 0.052 с
```

Дальше — первые 10 строк итоговой таблицы `sales_summary` (регион, дата, число заказов, выручка).
Число строк после каждой стадии будет отличаться от примера — данные генерируются случайно при
каждом прогоне `db_setup.py`.

Как понять, что шаг прошёл: код возврата `0`, число агрегированных строк заметно меньше исходных
5030 (дубли и брак отсеялись), и в целевой таблице ровно 4 региона без разнобоя в написании —
это можно проверить отдельно:

```bash
psql -d etl_demo -tAc "SELECT DISTINCT region FROM sales_summary ORDER BY region;"
```

Ожидаемый вывод: `East`, `North`, `South`, `West` — ровно четыре строки, без вариантов с
пробелами или другим регистром.

## Шаг 5. Прогнать заново (full load)

```bash
./.venv/bin/python3 etl_pipeline.py
```

`load()` каждый раз выполняет `DROP TABLE` / `CREATE TABLE` перед вставкой — это и есть full
load: целевая таблица не сравнивается со старым состоянием, а перезаписывается целиком. Повторный
прогон безопасен и не накапливает дублей.

## Если не так

- **`connection refused` на localhost:5432.** Сервер PostgreSQL не запущен либо слушает другой
  порт. Проверьте `psql -c "select 1"` тем же пользователем, что указан в DSN.
- **`FATAL: role "techfriends" does not exist` (или похожее).** В `db_setup.py` и
  `etl_pipeline.py` не заменили `user=techfriends` на своего пользователя — см. шаг 2.
- **`No module named 'psycopg'`.** Ставился пакет `psycopg` без экстры `binary`, либо не тот
  venv активен. Проверьте, что запускаете именно `./.venv/bin/python3`, а не системный `python3`.
- **Итоговая таблица пустая или почти пустая.** `raw_orders` не пересоздана — сначала обязательно
  шаг 3 (`db_setup.py`), только потом шаг 4 (`etl_pipeline.py`).
