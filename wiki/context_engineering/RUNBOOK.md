# RUNBOOK: из чего состоит окно агента, отбор и компакция контекста на Ollama

## Окружение

| Что | Версия |
|---|---|
| Python | 3.12, только стандартная библиотека, venv не нужен |
| Ollama | 0.40.13, локальная установка или Docker из этой папки |
| Модель | `qwen2.5:7b` (4.7 ГБ, ID 845dbda0ea48, Q4_K_M) |

Все демо задают `num_ctx 8192` явно, `temperature 0` и `seed 42`. GPU не обязателен, но на CPU
прогон медленный: вывод ниже снят на 4 vCPU без GPU, где модель читает промпт со скоростью
около 9 токенов в секунду. Окно в 2 тысячи токенов без кэша читается 4-5 минут, все три демо
идут около 25 минут. На машине с GPU то же самое занимает секунды.

Адрес Ollama скрипты берут из `OLLAMA_URL`, по умолчанию `http://localhost:11434`.

## Шаг 1. Ollama и модель

Если Ollama стоит локально:

```bash
ollama pull qwen2.5:7b
ollama list
```

Если Ollama нет, её можно поднять в Docker из этой папки:

```bash
docker compose up -d
docker exec context-ollama ollama pull qwen2.5:7b
docker exec context-ollama ollama list
```

Шаг прошёл, если в списке есть модель:

```
NAME          ID              SIZE
qwen2.5:7b    845dbda0ea48    4.7 GB
```

Первый вызов после загрузки модели в память на CPU идёт до 3 минут, это не зависание.

## Шаг 2. Из чего состоит окно агента

```bash
python3 01_context_budget.py qwen2.5:7b
```

Скрипт собирает окно одного шага агента поддержки интернет-магазина: системный промпт,
описания 12 инструментов, историю с двумя вызовами инструментов и их JSON-выводами, три
документа базы знаний и вопрос оператора. Слои добавляются по одному, после каждого скрипт
делает вызов с `num_predict=1` и читает `prompt_eval_count`, то есть сколько токенов промпта
модель на самом деле прочитала с учётом шаблона чата. Вывод на прогоне:

```
слой                     окно, ток   вклад   доля  из кэша
системный промпт                86      86     5%        3
+ инструменты (12)             862     776    44%       80
+ история с выводами          1566     704    40%      860
+ документы (3)               1754     188    11%     1566
+ вопрос                      1767      13     1%     1748
итого окно 1767 токенов из 8192: 22% num_ctx, вопрос пользователя 13 токенов
```

Как читать:

- **Описания инструментов заняли 44% окна.** Это больше, чем вся история с выводами
  инструментов, и в четыре раза больше, чем документы, ради которых окно и собиралось. Описания
  уходят в каждый вызов модели, даже если на этом шаге инструмент не нужен.
- **Вопрос пользователя это 13 токенов из 1767**, меньше процента. Всё остальное в окне
  собирает приложение, и это и есть предмет context engineering.
- **Столбец «из кэша»** показывает, сколько токенов Ollama взяла из кэша префикса прошлого
  вызова. `prompt_eval_count` в Ollama 0.40.13 считает всё окно, включая кэш, поэтому цифра
  окна полная. На втором шаге из кэша взяты 80 токенов, почти весь системный промпт: шаблон
  Qwen вставляет описания инструментов сразу за ним, и всё, что дальше, читается заново.

## Шаг 3. Отбор против «всё в окно»

```bash
python3 02_select_vs_dump.py qwen2.5:7b
```

База из 36 заметок дежурного инженера: 34 шумовые заметки про логи, порты и дежурства других
сервисов, одна устаревшая заметка про `ledger_v1` с портом 9100 и одна нужная (иголка): сервис
`ledger` отдаёт метрики на порту 9464. Вопрос «на каком порту сервис ledger отдаёт метрики
Prometheus». Режим `dump` кладёт в окно всю базу, иголка стоит в начале, в середине и в конце.
Режим `select` кладёт в окно только три лучшие заметки по BM25, функция написана прямо в
скрипте на стандартной библиотеке. Каждый вызов получает новую метку сессии в начале
системного промпта, чтобы кэш префикса не искажал время. Вывод на прогоне:

```
dump, начало     заметок 36  токенов промпта  2214  префилл  276.4 с  всего  280.2 с  верно да   ответ: 9464
dump, середина   заметок 36  токенов промпта  2214  префилл  313.1 с  всего  316.5 с  верно да   ответ: 9464
dump, конец      заметок 36  токенов промпта  2214  префилл  254.8 с  всего  257.7 с  верно да   ответ: 9464
BM25 top-3: Сервис ledger ведёт проводки по счетам клиент... | Сервис ledger_v1 выведен из эксплуатации в 20... | Сервис cart пишет логи в /var/log/cart и хран...
select, top-3    заметок  3  токенов промпта   260  префилл   23.2 с  всего   25.0 с  верно да   ответ: 9464
```

Как читать:

- **На окне в 2214 токенов модель нашла ответ во всех трёх позициях.** Деградацию от
  заполнения окна (context rot) этот прогон не показывает: окно занято на 27% от `num_ctx 8192`
  и на 7% от 32768 токенов, которые модель поддерживает по `/api/show`. Он её не доказывает и
  не опровергает.
- **Цена разная в разы.** Отбор дал в 8.5 раза меньше токенов промпта и в 11-13 раз меньше
  времени на их чтение при том же верном ответе. В облачном API та же разница уходит в счёт за
  входные токены и в задержку первого токена.
- **Устаревшая заметка попала в top-3** рядом с нужной: BM25 видит общие слова, а не
  актуальность. Модель её отбросила, но в реальной системе отбор надо дополнять метаданными
  (дата, статус документа), а не надеяться на модель.

## Шаг 4. Компакция истории

```bash
python3 03_compaction.py qwen2.5:7b
```

Агент-аналитик за шесть вызовов инструментов `run_sql` и `read_logs` собрал данные для отчёта
по ошибкам платежей. Требования к отчёту (CSV, разделитель точка с запятой, каталог
`/reports/payments`) пользователь дал в первом сообщении, а первый SQL-запрос вернул 1287
строк. Перед финальным вопросом история подаётся в трёх вариантах:

- `full`: вся история как есть;
- `clear`: выводы всех инструментов, кроме двух последних, заменены заглушкой «вывод
  инструмента очищен», сами вызовы и реплики остаются (tool result clearing);
- `summary`: история до двух последних шагов заменена резюме, которое написала та же модель по
  инструкции «сохрани требования пользователя, принятые решения и ключевые числа».

Каждому варианту задаются два вопроса: про требование из первого сообщения и про число из
вывода первого инструмента. Кэш префикса здесь не сбивается намеренно: видно, как очистка и
резюме переписывают начало истории и кэш перестаёт работать. Вывод на прогоне:

```
сжатие: прочитано 2138 токенов (из кэша 3), написано 65, 230.1 с
резюме: Сбор данных за 2026-10-26 по 2026-11-01. Ошибки: DECLINED 611, 5XX 116, FRAUD 158. Таймауты исключены.
full     требование  токенов промпта  2419  из кэша  2096  префилл   36.9 с  всего   47.1 с  верно да   ответ: Формат CSV, разделитель точка с запятой, каталог /reports/payments.
full     деталь      токенов промпта  2406  из кэша  2380  префилл    5.0 с  всего    7.1 с  верно да   ответ: 1287
clear    требование  токенов промпта   753  из кэша   209  префилл   46.8 с  всего   54.9 с  верно да   ответ: Формат CSV, разделитель точка с запятой, каталог /reports/payments.
clear    деталь      токенов промпта   740  из кэша   714  префилл    3.6 с  всего    4.8 с  верно нет  ответ: 885
summary  требование  токенов промпта   455  из кэша    54  префилл   44.7 с  всего   56.2 с  верно нет  ответ: Формат CSV, разделитель запятая, каталог /reports/payment_errors.
summary  деталь      токенов промпта   442  из кэша   416  префилл    4.2 с  всего    5.3 с  верно нет  ответ: 10
```

Как читать:

- **Очистка выводов инструментов сократила окно в 3.2 раза и сохранила требование:**
  сообщение пользователя она не трогает. Число 1287 жило только в выводе первого
  инструмента, его заглушка и стёрла. Модель не сказала «не знаю», а ответила 885, числом из
  более позднего вывода, который остался в окне.
- **Резюме сократило окно в 5.3 раза и потеряло оба факта**, хотя инструкция прямо просила
  сохранить требования и ключевые числа. В 65 токенов резюме попали коды ошибок, а формат
  отчёта и 1287 нет. На вопрос о требовании модель ответила уверенно и неверно: «разделитель
  запятая», каталог `/reports/payment_errors`. Это главный риск компакции: потеря детали не
  видна, модель достраивает её правдоподобной выдумкой.
- **Само сжатие стоит одного вызова модели по всей истории:** 2138 токенов прочитано, 230 с
  на CPU. Окупается оно только на длинной сессии, где сжатую историю потом читают много раз.
- **Кэш префикса.** У `full` второй вопрос почти весь взят из кэша (2380 из 2406), потому что
  окно отличается только последней репликой. Очистка и резюме переписывают начало истории,
  и первый вызов после них читает окно заново.

## Если не так

- **Числа токенов отличаются на единицы-десятки.** Счёт идёт после шаблона чата конкретной
  модели. Другая модель или другая версия Ollama с другим шаблоном даст другие абсолютные
  цифры, но соотношения слоёв и режимов сохраняются.
- **Ответы отличаются от приведённых.** `temperature 0` и `seed 42` дают повторимый прогон
  только на той же версии Ollama и той же сборке модели. Особенно чувствительно резюме в
  `03_compaction.py`: другая модель может сохранить требование и потерять другое. Важно не
  конкретное слово, а то, что потерю нужно проверять вопросами к деталям, а не на глаз.
- **Время префилла сильно больше или меньше.** Оно зависит от железа. На облачных машинах с
  burst-лимитом CPU скорость падает после часа нагрузки, на GPU префилл в 2 тысячи токенов
  идёт за доли секунды. Сравнивайте режимы между собой, а не с этими секундами.
- **Ответ обрезан или модель не видит начало заметок.** Проверьте, что `num_ctx` задан явно:
  без него Ollama берёт окно по умолчанию и молча обрезает длинный промпт, ошибки при этом нет.
- **`HTTP Error 500`, в `dmesg` видно `oom-kill` с `llama-server`.** Не хватает памяти на модель
  и KV-кэш. Закройте другие модели (`ollama stop <модель>`) или уменьшите `NUM_CTX` в скрипте.
- **`Connection refused`.** Ollama не запущена или слушает другой адрес, задайте
  `OLLAMA_URL=http://<адрес>:11434`.
