# RUNBOOK: пересчёт истории в Kappa Architecture на Kafka и SQLite

Пошаговый прогон демо к статье [Kappa Architecture](https://bigdataschool.ru/wiki/kappa_architecture/).
На каждом шаге: что делаем, команда, что должно быть в выводе и как понять, что шаг прошёл.
Ожидаемый вывод снят на прогоне 2026-11-14; времена и скорости на вашей машине будут другими,
а суммы, offset'ы и число событий совпадут, потому что генератор событий детерминирован по `--seed`.

## Окружение

| Что | Версия на прогоне | Минимум |
|---|---|---|
| ОС | Ubuntu 24.04.4 LTS, x86_64, AWS t3.xlarge (4 vCPU, 15.7 ГБ RAM) | любая с Docker |
| Docker / Compose | 29.1.3 / 2.40.3 | Compose v2 с `up --wait` |
| Apache Kafka | образ `apache/kafka:4.3.2`, KRaft | другие версии не проверялись |
| Python | 3.12.3 | 3.10 (в коде `int | None`) |
| confluent-kafka | 2.16.1 (librdkafka 2.16.0) | |
| SQLite | 3.45.1 из стандартной библиотеки Python | 3.24 (`ON CONFLICT DO UPDATE`), для подсчёта места нужен `dbstat` |

Брокер слушает `127.0.0.1:59093`. Если порт занят, поменяйте его в `docker-compose.yml` (две строки:
`EXTERNAL://:59093` и `ports`) и задайте `export KAFKA_BOOTSTRAP=127.0.0.1:<порт>` перед запуском скриптов.

Свободного места нужно около 100 МБ: лог из 630 тыс. событий занимает 76 МБ.

## Шаг 1. Поднять Kafka

```bash
docker compose up -d --wait
docker compose exec -T kafka /opt/kafka/bin/kafka-topics.sh --version
```

Ожидаем: `Container kappa-architecture-kafka  Healthy` и `4.3.2`. Healthcheck ждёт, пока брокер начнёт
отвечать на запросы, поэтому после `--wait` можно сразу писать в топик.

## Шаг 2. Окружение Python

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -c "import confluent_kafka as k; print(k.version(), k.libversion())"
```

Ожидаем версию `2.16.1` и librdkafka `2.16.0`.

## Шаг 3. История: 600 тыс. событий в лог

```bash
.venv/bin/python produce_events.py --count 600000 --seed 1
```

Скрипт создаёт топик `kappa_architecture_orders` на 3 партиции с `retention.ms=-1` и `retention.bytes=-1`:
лог хранится бессрочно, иначе пересчитывать историю будет не из чего. Ключ сообщения это клиент, поэтому
все события одного клиента лежат в одной партиции. В среднем 10% событий это возвраты.

```
топик kappa_architecture_orders создан: 3 партиции, {'retention.ms': '-1', 'retention.bytes': '-1'}
записано 600000 событий (id 1..600000), из них возвратов 60000, за 6.6 с, 91322 событий/с
```

Строка `Failed to acquire idempotence PID ... Coordinator load in progress: retrying` в начале нормальна на
свежем брокере: продюсер с идемпотентностью ждёт, пока координатор транзакций загрузится, и повторяет запрос сам.

## Шаг 4. Джоба v1 и первое подключение приложения

```bash
.venv/bin/python stream_job.py --version v1 --exit-when-caught-up
.venv/bin/python switch_serving.py --to v1
```

Джоба v1 стартует в новой группе `kappa_architecture_job_v1`, сохранённых offset'ов у неё нет, и по
`auto.offset.reset=earliest` она читает лог с начала. Раз в секунду печатается лаг: голова лога (high
watermark) минус позиция джобы.

```
[v1] группа kappa_architecture_job_v1, сохранённые offset'ы: p0@нет, с начала лога, p1@нет, с начала лога, p2@нет, с начала лога
[v1 +  3.2 с] обработано    5000, лаг  595000
...
[v1] догнал голову лога за 9.6 с (лаг 0), обработано 600000
[v1] итог: обработано 600000 за 11.1 с, скорость догоняния 93512 событий/с, offset'ы группы: p0@198668, p1@205342, p2@195990
```

Первые 3 с уходят на вступление в consumer group, скорость догоняния считается от первого прочитанного события.

`switch_serving.py --to v1` создаёт view `orders_by_customer`, из которого читает приложение, и сверяет
таблицу с пересчётом напрямую из лога. Здесь видна ошибка v1:

```
лаг джобы v1: 0
orders_by_customer_v1: клиентов 5000, выручка 151 542 954.14, расходится с пересчётом из лога у 5000 клиентов
пересчёт из лога: клиентов 5000, выручка 121 259 103.30
пример, клиент c01101: orders_by_customer_v1 = 30 816.04, пересчёт = 24 231.32
view orders_by_customer: было «нет», стало → orders_by_customer_v1
```

## Шаг 5. Живой поток и пересчёт v2 рядом с работающей v1

Три процесса одновременно. Удобнее в трёх терминалах; одной командой фоном так:

```bash
mkdir -p logs
.venv/bin/python -u produce_events.py --count 30000 --first-id 600001 --seed 2 --rate 2000 > logs/live_producer.log 2>&1 &
.venv/bin/python -u stream_job.py --version v1 --caught-up-lag 1000 --idle-exit 5 > logs/v1_live.log 2>&1 &
sleep 3
.venv/bin/python -u stream_job.py --version v2 --caught-up-lag 1000 --idle-exit 5 > logs/v2_replay.log 2>&1 &
wait
cat logs/live_producer.log logs/v1_live.log logs/v2_replay.log
```

Продюсер 15 с пишет живой поток по 2000 событий в секунду. v1 продолжает со своих сохранённых offset'ов.
v2 это та же программа с исправленной логикой (возврат вычитается) в новой группе
`kappa_architecture_job_v2`: она читает лог с нуля в свою таблицу `orders_by_customer_v2`, догоняет
голову и дальше обрабатывает живые события наравне с v1. При живом потоке лаг редко бывает ровно нулём,
поэтому «догнал» здесь значит лаг не больше 1000 событий, то есть полсекунды потока. Оба процесса
выходят после 5 с без новых событий.

```
записано 30000 событий (id 600001..630000), из них возвратов 3029, за 15.0 с, 2000 событий/с
[v1] группа kappa_architecture_job_v1, сохранённые offset'ы: p0@198668, p1@205342, p2@195990
[v1 +  1.1 с] обработано    2400, лаг     262
...
[v1] итог: обработано 30000 за 23.5 с, offset'ы группы: p0@208641, p1@215498, p2@205861
[v2] группа kappa_architecture_job_v2, сохранённые offset'ы: p0@нет, с начала лога, p1@нет, с начала лога, p2@нет, с начала лога
[v2 +  1.0 с] обработано   65000, лаг  543400
[v2 +  4.1 с] обработано  385000, лаг  229471
[v2 +  7.4 с] обработано  621000, лаг     271
[v2] догнал голову лога за 7.4 с (лаг 271), обработано 621000
...
[v2] итог: обработано 630000 за 20.9 с, скорость догоняния 86132 событий/с, offset'ы группы: p0@208641, p1@215498, p2@205861
```

Как понять, что шаг прошёл: итоговые offset'ы групп v1 и v2 совпадают, у v2 обработано 630000 событий,
у v1 30000 новых.

## Шаг 6. Переключение приложения на v2 и удаление v1

```bash
.venv/bin/python switch_serving.py --to v2 --drop-old
```

Скрипт отказывается переключать, если лаг группы v2 не нулевой (выход с кодом 2 и строкой `ОТКАЗ`).
Дальше сверка обеих таблиц с пересчётом из лога, место в SQLite, пока живут обе версии, переключение
view одной транзакцией и удаление таблицы и consumer group v1.

```
лаг джобы v2: 0
orders_by_customer_v1: клиентов 5000, выручка 159 144 877.52, расходится с пересчётом из лога у 5000 клиентов
orders_by_customer_v2: клиентов 5000, выручка 127 315 274.50, расходится с пересчётом из лога у 0 клиентов
пересчёт из лога: клиентов 5000, выручка 127 315 274.50
пример, клиент c01101: orders_by_customer_v1 = 32 094.02, orders_by_customer_v2 = 25 509.30, пересчёт = 25 509.30
место в serving-БД: orders_by_customer_v1 192 КиБ, orders_by_customer_v2 188 КиБ | файл 388 КиБ
view orders_by_customer: было «CREATE VIEW orders_by_customer AS SELECT * FROM orders_by_customer_v1», стало → orders_by_customer_v2
приложение читает orders_by_customer, клиент c01101: 25 509.30
удалены таблица orders_by_customer_v1 и consumer group kappa_architecture_job_v1
место после удаления: orders_by_customer_v2 176 КиБ | файл 180 КиБ
```

Размер таблиц в КиБ может отличаться на несколько страниц от прогона к прогону: он зависит от того,
какими пачками пришли строки.

## Шаг 7. Предел подхода: retention короче окна пересчёта

```bash
.venv/bin/python retention_limit.py
```

Отдельный топик на одну партицию с `retention.ms=10000` и `segment.ms=2000`. Брокер в этом стенде проверяет
retention раз в 5 с (`KAFKA_LOG_RETENTION_CHECK_INTERVAL_MS` в `docker-compose.yml`, по умолчанию 5 минут).
Пишутся две пачки по 3000 событий с паузой 6 с, вторая открывает новый сегмент. Через 10-15 с брокер удаляет
сегмент первой пачки. Скрипт поднимает retention до бессрочного, чтобы уцелела вторая пачка, и перепроигрывает
лог новой группой с `earliest`.

```
топик kappa_architecture_orders_short_retention: 1 партиция, {'retention.ms': '10000', 'segment.ms': '2000'}
записано 2 пачки по 3000: лог offset'ы 0..5999, честная выручка 1231574.18
через 16 с: начало лога сдвинулось на offset 3000, в логе осталось 3000 событий из 6000
retention.ms=-1 выставлен: лог offset'ы 3000..5999, удалённое не вернулось
пересчёт с earliest: первый offset 3000, прочитано 3000 событий, выручка 628791.48
потеряно при пересчёте: 3000 событий, 602782.70 выручки; ошибок от Kafka: 0
```

Как понять, что шаг прошёл: первый offset пересчёта 3000, а не 0, и ни одной ошибки. Скрипт при каждом
запуске удаляет и создаёт свой топик заново, его можно запускать повторно.

## Шаг 8. Уборка

```bash
docker compose down -v
rm -f serving.db serving.db-wal serving.db-shm
rm -rf logs
```

## Если не так

- **`BufferError: Local: Queue full` в `produce_events.py`.** Так было бы без цикла с `producer.poll(0.1)`
  в коде: локальная очередь librdkafka по умолчанию держит 100 тыс. сообщений. Проверьте, что запускаете
  файл из этой папки, а не свою упрощённую копию.
- **v1 на шаге 4 печатает `обработано 0` и сразу выходит.** Группа v1 уже прочитала лог в прошлом запуске
  и продолжает со своих offset'ов. Для прогона с нуля: `docker compose down -v`, удалить `serving.db*`,
  начать с шага 1.
- **`ОТКАЗ: джоба v2 не догнала лог`.** Шаг 5 не дошёл до конца или упал. Посмотрите `logs/v2_replay.log`:
  в последней строке `итог` offset'ы v2 должны совпасть с головой лога из первой строки `switch_serving.py`.
- **`database is locked`.** SQLite открыт в режиме WAL с таймаутом 30 с; ошибка значит, что базу держит
  посторонний процесс, например открытый `sqlite3 serving.db` с незакрытой транзакцией.
- **`no such table: dbstat`.** Ваш SQLite собран без `SQLITE_ENABLE_DBSTAT_VTAB`, подсчёт места в
  `switch_serving.py` не сработает. Остальные шаги от этого не зависят.
- **На шаге 7 начало лога не сдвинулось за 90 с.** Брокер поднят без `KAFKA_LOG_RETENTION_CHECK_INTERVAL_MS`
  и проверяет retention раз в 5 минут. Пересоздайте контейнер из `docker-compose.yml` этой папки.
- **Скорость догоняния сильно ниже.** На стенде прогона она менялась от 44 до 93 тыс. событий/с для одного и
  того же лога из 600 тыс. событий. Для сути демо важно соотношение: пересчёт идёт в десятки раз быстрее
  живого потока в 2000 событий/с, поэтому v2 его догоняет.
