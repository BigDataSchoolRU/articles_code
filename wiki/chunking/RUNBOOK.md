# RUNBOOK: как стратегия и размер чанка меняют поиск в RAG

## Окружение

| Что | Версия |
|---|---|
| Python | 3.12 |
| Сплиттеры LangChain | `langchain-text-splitters` 1.1.3 (`langchain-core` 1.7.6) |
| Сплиттеры LlamaIndex | `llama-index-core` 0.14.25, `llama-index-embeddings-ollama` 0.10.0 |
| Токенизатор | `tiktoken` 0.14.0, кодировка `cl100k_base` |
| Ollama | 0.40.13, локальная установка или Docker из этой папки |
| Модель эмбеддингов | `nomic-embed-text` (274 МБ, ID 0a109f422b47, 768 измерений, окно 2048 токенов) |

LLM в демо не участвует: качество поиска считается по эталонным подстрокам, поэтому вывод
воспроизводим от запуска к запуску. Вывод ниже снят на Ubuntu 24.04, 4 vCPU без GPU, Ollama в
Docker. На такой машине первое демо идёт около 10 секунд, второе около 10 минут: корпус
индексируется заново для каждой из 18 конфигураций, и каждая индексация это 25-35 секунд
эмбеддингов на CPU.

Скрипты обращаются к Ollama по адресу `http://localhost:11434` и читают `corpus/` и
`questions.jsonl` рядом с собой, запускать их можно из любого каталога.

## Шаг 1. Пакеты

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/pip check
.venv/bin/python -c "import langchain_text_splitters, llama_index.core; print(llama_index.core.__version__)"
```

Шаг прошёл, если `pip check` пишет `No broken requirements found.`, а последняя команда
печатает `0.14.25`.

`SentenceSplitter` и `SemanticSplitterNodeParser` из LlamaIndex режут текст на предложения
токенизатором NLTK. Данные NLTK (`punkt_tab`, `stopwords`) LlamaIndex докачивает сам при первом
вызове в свою папку `llama_index/core/_static/nltk_cache`, нужен доступ в интернет.

## Шаг 2. Ollama и модель эмбеддингов

Если Ollama стоит локально:

```bash
ollama pull nomic-embed-text
ollama list
```

Если Ollama нет, её можно поднять в Docker из этой папки:

```bash
docker compose up -d
docker exec chunking-ollama ollama pull nomic-embed-text
docker exec chunking-ollama ollama list
```

Шаг прошёл, если в списке есть модель:

```
NAME                       ID              SIZE
nomic-embed-text:latest    0a109f422b47    274 MB
```

Что смотреть в выводе:

- **Умолчания.** У LangChain `chunk_size=4000` и `chunk_overlap=200` считаются функцией `len`,
  то есть в символах. У `SentenceSplitter` из LlamaIndex те же 200 перекрытия считаются в токенах.
  Метод `from_tiktoken_encoder` без аргументов берёт кодировку `gpt2`, а не `cl100k_base`.
- **Ловушка единиц.** Одни и те же числа `chunk_size=256` и `chunk_overlap=32` дают 11 чанков
  в символах, 5 в токенах `cl100k_base` и 12 в токенах `gpt2`. Русский текст в `gpt2` занимает
  в 2.5 раза больше токенов, чем в `cl100k_base`, поэтому чанки выходят мелкими.
- **Граница.** `TokenTextSplitter` режет ровно по числу токенов и попадает посреди слова в шести
  границах из восьми, а иногда посреди самой буквы: кириллический символ занимает два байта UTF-8, и
  на разрезе остаётся символ-заменитель U+FFFD. Рекурсивный сплиттер и `SentenceSplitter` режут
  по абзацам и предложениям.
- **Окно модели эмбеддингов.** Весь корпус длиннее окна `nomic-embed-text`. С `truncate=false`
  Ollama отвечает ошибкой 400, а по умолчанию молча обрезает вход до 2048 токенов: хвост
  документа в вектор не попадает, и ошибки нет ни в ответе, ни в логе.

## Шаг 4. Стратегии и размеры чанка на поиске

```bash
.venv/bin/python 02_retrieval_eval.py
```

Скрипт режет все восемь документов каждой стратегией, индексирует чанки через `nomic-embed-text`
с префиксом `search_document:`, вопросы с префиксом `search_query:`, ранжирует чанки по
косинусной близости и считает метрики. Стратегии:

| Стратегия | Как режет |
|---|---|
| `fixed` | `TokenTextSplitter`, ровно N токенов, граница не смотрит на текст |
| `recursive` | `RecursiveCharacterTextSplitter.from_tiktoken_encoder`, абзацы, строки, слова |
| `markdown` | `MarkdownHeaderTextSplitter` по `#` и `##`, длинный раздел дорезается рекурсивно, заголовки документа и раздела дописываются в начало чанка |
| `sentence` | `SentenceSplitter` из LlamaIndex, целые предложения до N токенов |
| `semantic` | `SemanticSplitterNodeParser` из LlamaIndex, граница там, где падает близость соседних предложений (`buffer_size=1`, порог 95-й перцентиль) |
| `whole` | документ целиком одним чанком |

Перекрытие везде N/8. Колонки:

- `hit@1`, `hit@3`: доля вопросов, у которых эталонная подстрока целиком лежит в одном из
  первых 1 или 3 найденных чанков;
- `MRR@10`: средний обратный ранг первого чанка с ответом среди первых десяти;
- `hit@512ток`: найденные чанки склеиваются по рангу и обрезаются до 512 токенов, как если бы
  под контекст LLM было отведено ровно столько; доля вопросов, ответ на которые попал в эти 512 токенов;
- `разрезано`: у скольких вопросов ответ не лежит целиком ни в одном чанке, граница прошла по нему;
- `контекст top-3`: сколько токенов в среднем уходит в LLM, если отдать ей три чанка;
- `длиннее окна`: сколько чанков не влезло бы в окно модели эмбеддингов.

Что смотреть в выводе:

- По `hit@3` выигрывают крупные чанки, но это нечестное сравнение: три чанка по 708 токенов это
  2233 токена контекста против 261 у рекурсивного разбиения на 128 токенов. Документы в корпусе
  короче 1024 токенов, поэтому при N=1024 каждый документ целиком становится одним чанком, и
  поиск сводится к выбору трёх документов из восьми.
- При равном бюджете контекста (`hit@512ток`) лучший результат у рекурсивного разбиения на 128
  токенов, а документы целиком и чанки на 512-1024 токена отстают.
- `fixed` на 128 токенах хуже остальных стратегий того же размера по всем метрикам: разрезанные
  посреди слова чанки хуже ложатся в эмбеддинги.
- Разделы регламентов короче 256 токенов, поэтому `markdown` при N от 256 и выше не дорезает
  ничего и даёт одни и те же 43 чанка.
- `semantic` тратит на разбиение больше минуты: он считает эмбеддинг каждого предложения, а
  остальные стратегии режут текст за доли секунды.
- Вопросов 24, один вопрос это 0.04 в любой из долей. Разница в 0.04-0.08 между
  конфигурациями это один-два вопроса, а не закономерность.

## Если не так

- **`LookupError: Resource 'stopwords' not found` с припиской `Refused, writable by other accounts`.**
  NLTK 3.10 не читает данные из каталога, доступного на запись группе или всем. Так бывает, если
  venv создан при `umask 0002`. Лечится снятием прав и повторной загрузкой данных:
  `chmod -R go-w .venv`, затем
  `.venv/bin/python -c "import nltk; [nltk.download(p, download_dir='.venv/lib/python3.12/site-packages/llama_index/core/_static/nltk_cache', force=True) for p in ('stopwords', 'punkt_tab')]"`.
- **`urllib.error.URLError: Connection refused`.** Ollama не запущена или слушает другой порт.
  Проверка: `curl http://localhost:11434/api/version`.
- **`model "nomic-embed-text" not found`.** Модель не скачана, шаг 2.
- **Цифры `hit` и `MRR` другие.** Проверьте, что стоит `nomic-embed-text` с ID 0a109f422b47 и
  что префиксы `search_document:` и `search_query:` не убраны из кода: без них качество поиска
  у этой модели падает. Другая модель эмбеддингов даст другие абсолютные цифры. На этом русском
  корпусе абсолютный уровень `nomic-embed-text` невысокий, поэтому сравнивать имеет смысл
  конфигурации между собой, а не с цифрами из чужих бенчмарков.
- **Разное число чанков.** Проверьте версии сплиттеров из `requirements.txt` и кодировку
  `cl100k_base`: с умолчательной `gpt2` чанки выйдут в 2.5 раза мельче.
