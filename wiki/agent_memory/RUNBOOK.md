# RUNBOOK: кратковременная и долговременная память агента в LangGraph на Ollama

## Окружение

| Что | Версия |
|---|---|
| Python | 3.12 |
| LangGraph | `langgraph` 1.2.20, `langgraph-checkpoint` 4.3.1, `langgraph-checkpoint-sqlite` 3.1.3 |
| LangChain | `langchain-core` 1.7.6, `langchain-ollama` 1.1.0 |
| Векторный поиск в SQLite | `sqlite-vec` 0.1.9, ставится зависимостью `langgraph-checkpoint-sqlite` |
| Ollama | 0.40.13, локальная установка или Docker из этой папки |
| Модель агента | `qwen2.5:7b` (4.7 ГБ, ID 845dbda0ea48, Q4_K_M) |
| Модель эмбеддингов | `nomic-embed-text` (274 МБ, ID 0a109f422b47, 768 измерений) |

Все вызовы модели идут с `temperature 0`, `seed 42`, `num_ctx 4096` и коротким ответом
(`num_predict` 40-60). Вывод ниже снят на Ubuntu 24.04, 4 vCPU без GPU, Ollama в Docker. На
такой машине один ответ идёт 3-15 секунд, а все три демо вместе около двух минут, если
модели уже загружены в память. На GPU то же самое идёт за секунды.

Адрес Ollama скрипты берут из `OLLAMA_URL`, по умолчанию `http://localhost:11434`. Каждый
скрипт пишет рядом с собой свой файл SQLite (`short_term.sqlite`, `long_term.sqlite`,
`forget.sqlite`) и удаляет его в начале следующего запуска.

## Шаг 1. Пакеты

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/pip list | grep -Ei "langgraph|langchain|sqlite-vec"
```

Шаг прошёл, если в списке есть `langgraph 1.2.20`, `langgraph-checkpoint-sqlite 3.1.3`,
`langchain-ollama 1.1.0` и `sqlite-vec 0.1.9`.

## Шаг 2. Ollama и две модели

Если Ollama стоит локально:

```bash
ollama pull qwen2.5:7b
ollama pull nomic-embed-text
ollama list
```

Если Ollama нет, её можно поднять в Docker из этой папки:

```bash
docker compose up -d
docker exec agent-memory-ollama ollama pull qwen2.5:7b
docker exec agent-memory-ollama ollama pull nomic-embed-text
docker exec agent-memory-ollama ollama list
```

Шаг прошёл, если в списке есть обе модели:

```
NAME                       ID              SIZE
nomic-embed-text:latest    0a109f422b47    274 MB
qwen2.5:7b                 845dbda0ea48    4.7 GB
```

В `docker-compose.yml` стоит `OLLAMA_MAX_LOADED_MODELS: "2"`. Агент на каждой реплике
сначала ищет по памяти (эмбеддинг запроса), потом отвечает (генерация). При лимите в одну
модель Ollama выгружает `qwen2.5:7b` ради эмбеддинга, и каждый следующий ответ ждёт повторной
загрузки модели агента, на CPU это десятки секунд. Первый вызов после старта Ollama тоже
идёт долго, до минуты: модель читается с диска в память.

## Шаг 3. Кратковременная память: история треда в checkpointer

```bash
.venv/bin/python 01_short_term.py qwen2.5:7b
```

Граф из одного узла `call_model` собран с `SqliteSaver`. Каждый вызов `graph.invoke` с
`thread_id` в конфиге дописывает реплику в состояние треда, а checkpointer сохраняет его в
`short_term.sqlite`. Модель получает всю историю треда в окне и поэтому «помнит» имя. Между
второй и третьей репликой скрипт закрывает соединение и собирает граф заново, как после
перезапуска процесса. Последней репликой тот же вопрос уходит в новый тред `anna_2`. Вывод на
прогоне:

```
--- процесс 1 ---
тред anna_1 | сообщений в состоянии  2 | токенов промпта   83 |  10.1 с
  > Привет! Меня зовут Анна, я пишу пайплайны на Airflow.
  < Здравствуйте, Анна! Я знаю, что вы пишете пайплайны на Airflow.
тред anna_1 | сообщений в состоянии  4 | токенов промпта  138 |   9.8 с
  > Как меня зовут и на чём я пишу пайплайны?
  < Вы зоветесь Анной и пишете пайплайны на Airflow.
--- процесс 2: новое соединение с тем же файлом, граф собран заново ---
тред anna_1 | сообщений в состоянии  6 | токенов промпта  178 |   5.0 с
  > Напомни, как меня зовут?
  < Вы зоветесь Анной.
тред anna_2 | сообщений в состоянии  2 | токенов промпта   69 |   4.8 с
  > Напомни, как меня зовут?
  < Вы не указали свое имя в этом разговоре.
чекпоинтов в базе: тред anna_1 — 9
чекпоинтов в базе: тред anna_2 — 3
get_state_history(anna_1): 9 снимков состояния, в последнем 6 сообщений
```

Что видно:

- **Помнит не модель, а состояние треда.** В треде `anna_1` имя доступно и после перезапуска
  процесса, потому что история лежит в файле. В треде `anna_2` того же графа имени нет.
- **Окно растёт с каждой репликой:** 83, 138, 178 токенов промпта на коротких репликах. Вся
  история треда читается моделью заново на каждом шаге, поэтому длинный тред однажды упрётся
  в `num_ctx` и в цену префилла.
- **Чекпоинт пишется на каждый шаг графа, а не на реплику.** Три вызова `invoke` в треде
  `anna_1` дали 9 чекпоинтов: вход, старт и узел модели. Через `get_state_history` их можно
  перебрать и вернуться к любому.

## Шаг 4. Долговременная память: Store между сессиями

```bash
.venv/bin/python 02_long_term.py qwen2.5:7b
```

Факты о пользователе вынесены из треда в `SqliteStore` с семантическим индексом
`{"embed": OllamaEmbeddings(model="nomic-embed-text"), "dims": 768, "fields": ["text"]}`.
Кто говорит, граф узнаёт из контекста запуска `context=Context(user_id=...)`, а не из
сообщений, и все записи пользователя лежат в пространстве имён `("memories", user_id)`.
На каждой реплике граф проходит три узла:

- `recall` ищет до трёх записей пользователя, близких к реплике по смыслу (`store.search`);
- `call_model` отвечает, подставив найденное в системный промпт;
- `write_memory` просит ту же модель выписать из реплики устойчивые факты и кладёт каждый в
  Store под новым ключом (`store.put`).

Три сессии: Анна представляется в треде `s1`, в новом треде `s2` спрашивает про свою базу,
Борис в треде `s3` задаёт тот же вопрос. Вывод на прогоне:

```
=== пользователь anna, тред s1 ===
  > Привет! Я Анна, пишу пайплайны на Airflow, а отчёты собираю в ClickHouse.
  recall: найдено 0 записей в ('memories', 'anna')
  write_memory: записано 2
    + Имя: Анна
    + Работа: пишет пайплайны на Airflow, собирает отчёты в ClickHouse
  < Здравствуйте Анна! Вы пишете пайплайны на Airflow и отчёты собираете в ClickHouse.
  время: recall 0.1 с, call_model 15.2 с (токенов промпта 112), write_memory 15.4 с

=== пользователь anna, тред s2 ===
  > В какой базе я собираю отчёты?
  recall: найдено 2 записей в ('memories', 'anna')
    score 0.715  Работа: пишет пайплайны на Airflow, собирает отчёты в ClickHouse
    score 0.611  Имя: Анна
  write_memory: записано 0
  < В ClickHouse.
  время: recall 0.1 с, call_model 6.6 с (токенов промпта 126), write_memory 10.0 с

=== пользователь boris, тред s3 ===
  > В какой базе я собираю отчёты?
  recall: найдено 0 записей в ('memories', 'boris')
  write_memory: записано 0
  < Не знаю.
  время: recall 0.1 с, call_model 3.8 с (токенов промпта 94), write_memory 1.1 с

=== содержимое Store после трёх сессий ===
('memories', 'anna'): 2 записей
  070ded37  Имя: Анна
  87ac4f5b  Работа: пишет пайплайны на Airflow, собирает отчёты в ClickHouse
```

Что видно:

- **Новый тред, та же память.** История `s1` в тред `s2` не попала, но факт про ClickHouse
  пришёл из Store поиском по смыслу вопроса, и агент ответил верно.
- **Изоляция держится на пространстве имён.** У Бориса в `("memories", "boris")` пусто, и
  агент честно ответил «не знаю», хотя ответ лежит в той же базе в соседнем пространстве.
- **Запись в горячем пути стоит отдельного вызова модели.** На первой реплике извлечение
  фактов шло 15.4 с, столько же, сколько сам ответ. На вопросе без фактов модель всё равно
  читает реплику и отвечает «НЕТ», это ещё 1-10 с на каждую реплику.
- **Гранулярность записей решает модель, а не код.** Инструкция просила факт на строку, а
  модель склеила Airflow и ClickHouse в одну запись «Работа: ...». Поиск её нашёл, но обновить
  один из двух фактов отдельно теперь нельзя.

## Шаг 5. Обновление, удаление и срок жизни

```bash
.venv/bin/python 03_forget.py qwen2.5:7b
```

Скрипт моделирует переезд пользователя из Самары в Казань и сравнивает два способа записать
изменение, затем удаляет факт и проверяет TTL. Вывод на прогоне (временные метки у вас будут
свои):

```
=== 1. append: изменение дописано новой записью ===
    score 0.736  [19043ed8]  Анна живёт в Самаре
    score 0.684  [e79b894a]  Анна переехала в Казань
    score 0.654  [63d20b59]  Анна пишет пайплайны на Airflow
  > В каком городе я живу?
  < Вы живете в Казани.  (3.3 с)

=== 2. upsert: у факта о городе один ключ ===
  get(city): Анна живёт в Казани, переехала из Самары
  created_at: 00:19:01 -> 00:19:02, updated_at: 00:19:01 -> 00:19:02
  записей в пространстве имён: 2
    score 0.743  [city]  Анна живёт в Казани, переехала из Самары
    score 0.654  [stack]  Анна пишет пайплайны на Airflow
  > В каком городе я живу?
  < Вы живете в Казани.  (3.2 с)

=== 3. delete: пользователь попросил забыть город ===
  get(city): None
  поиск по тому же вопросу:
    score 0.654  [stack]  Анна пишет пайплайны на Airflow

=== 4. TTL: временный факт со сроком жизни 0.05 мин (3 с) ===
  сразу: записей 2, get(trip) есть
  через 5 с, до очистки: записей 2, get(trip) есть
  sweep_ttl() удалил записей: 1
  после очистки: записей 1, get(trip) нет

InMemoryStore.supports_ttl = False, SqliteStore.supports_ttl = True
```

Что видно:

- **При дозаписи устаревший факт поднимается выше свежего.** «Живёт в Самаре» получил score
  0.736, «переехала в Казань» 0.684: вопрос «в каком городе я живу» ближе по словам к старой
  записи. Здесь модель разобралась сама по слову «переехала», но в окно ушли оба факта, и
  выбор между ними остался на модели.
- **Обновление по ключу оставляет один факт.** Запись `city` заменена, в пространстве имён
  две записи вместо трёх, и в окно уходит только актуальная версия.
- **Перезапись ключа это замена записи целиком.** `created_at` становится новым вместе с
  `updated_at` (в SqliteStore это `INSERT OR REPLACE`), поэтому дату, когда факт появился
  впервые, Store не хранит. Если она нужна, кладите её в само значение.
- **`delete` убирает запись и из поиска.** По вопросу о городе находится только факт про
  Airflow.
- **TTL в SqliteStore не скрывает просроченное при чтении.** Через 5 с при сроке 3 с запись
  всё ещё отдают и `get`, и `search`. Удаляет её только очистка: ручной `sweep_ttl()` или
  фоновый `start_ttl_sweeper()`. У `InMemoryStore` TTL нет вовсе (`supports_ttl = False`).
  Единица `ttl` в LangGraph это минуты.

## Если не так

- **Ответы модели отличаются от приведённых.** `temperature 0` и `seed 42` дают повторимый
  прогон только на той же версии Ollama и той же сборке модели. Особенно чувствителен
  `write_memory`: другая модель может выписать три отдельных факта вместо двух склеенных или
  записать что-то и из вопроса. Важно не точное слово, а то, что найдено и записано.
- **Каждый ответ идёт 40-60 с, а не 5-15.** Скорее всего, Ollama выгружает модель агента ради
  модели эмбеддингов. Проверьте `ollama ps` во время прогона: должны быть загружены обе. В
  Docker из этой папки за это отвечает `OLLAMA_MAX_LOADED_MODELS: "2"`, у локальной Ollama
  задайте ту же переменную окружения перед `ollama serve`.
- **`HTTP Error 500`, в `dmesg` видно `oom-kill` с `llama-server`.** Не хватает памяти на две
  модели и KV-кэш. Закройте другие модели (`ollama stop <модель>`) или уменьшите `num_ctx`.
- **Ошибка про `vec0` или про загрузку расширения SQLite на `store.setup()`.** Векторный
  индекс SqliteStore работает через расширение `sqlite-vec`: оно не встало, либо Python
  собран с SQLite без поддержки загружаемых расширений. Проверьте
  `.venv/bin/pip show sqlite-vec` и используйте Python из venv, а не системный.
- **`score` отличаются во втором-третьем знаке.** Это нормально для другой сборки модели
  эмбеддингов или другого процессора. Порядок записей важнее абсолютных чисел.
- **`Connection refused`.** Ollama не запущена или слушает другой адрес, задайте
  `OLLAMA_URL=http://<адрес>:11434`.
