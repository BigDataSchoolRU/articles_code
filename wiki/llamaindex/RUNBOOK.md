# RUNBOOK: базовый RAG-пайплайн на LlamaIndex + Ollama

Демо в два шага: как LlamaIndex режет документ на узлы (Node) при индексации,
и как выглядит полный RAG-запрос (индексация → retrieval → генерация ответа)
на локальных моделях через Ollama.

## Окружение

- Python 3.12
- Пакеты: `llama-index-core` 0.14.24, `llama-index-llms-ollama` 0.10.1,
  `llama-index-embeddings-ollama` 0.9.0
- Локальный сервер Ollama 0.32.13 на `http://localhost:11434` со скачанными
  моделями `qwen2.5:7b` (генерация ответа) и `nomic-embed-text` (эмбеддинги,
  768 измерений)

Установка:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install llama-index-core llama-index-llms-ollama llama-index-embeddings-ollama

# Ollama: https://ollama.com/download
ollama pull qwen2.5:7b
ollama pull nomic-embed-text
```

## Шаг 1. Проверить, что Ollama доступна и модели на месте

```bash
curl -s http://localhost:11434/api/tags | grep -E "qwen2.5:7b|nomic-embed-text"
```

Ожидаемый вывод: по строке на каждую модель. Если пусто — модель не скачана,
выполните `ollama pull <модель>` и повторите.

## Шаг 2. Разбиение документа на Node

```bash
python3 node_chunking_demo.py
```

Показывает дефолтные параметры `SentenceSplitter` (`chunk_size=1024`,
`chunk_overlap=200`) и разбивает более короткий тестовый документ уменьшенным
чанком (`chunk_size=256, chunk_overlap=40`), чтобы получить несколько узлов на
одном прогоне. Пример реального вывода:

```
Длина исходного документа: 1669 символов
Дефолтный chunk_size: 1024
Дефолтный chunk_overlap: 200

Документ разбит на 4 Node (chunk_size=256, chunk_overlap=40):
  Node 0: 486 символов
  Node 1: 566 символов
  Node 2: 481 символов
  Node 3: 190 символов
```

**Важно про единицы `chunk_size`.** Число в `chunk_size` — это токены
внутреннего токенизатора, не символы. На кириллическом тексте один токен
занимает заметно больше двух символов, поэтому узел с `chunk_size=256`
получается на 480-560 символов, а не на ~256. Планируя размер чанка под
контекст модели, ориентируйтесь на токены, а не на длину строки.

## Шаг 3. Полный RAG-запрос

```bash
python3 basic_rag_pipeline.py
```

Индексирует шесть коротких документов (регламенты внутри компании) и
отвечает на вопрос, используя только эти документы как контекст. Пример
реального вывода:

```
Индексация 6 документов заняла 0.91 с
Узлов (Node) в индексе: 6

Вопрос: Сколько времени действует доступ на запись к продуктивной базе данных?
Ответ (10.46 с): Доступ на запись к продуктивной базе данных действует на протяжении 30 дней.

Источники, которые ушли в контекст LLM (Retrieval):
  score=0.8180  [Доступ к продуктивным БД]  'Регламент доступа к продуктивным базам данных: доступ на чтение выдаёт'
  score=0.7605  [Оформление отпуска]  'Порядок оформления отпуска: заявление подаётся в кадровую систему не п'
```

Ответ верный (документ о доступе к БД действительно даёт 30 дней на запись),
но обратите внимание на второй источник: в контекст LLM попал нерелевантный
документ про отпуска с довольно высоким score 0.7605 — почти вплотную к
правильному 0.8180. Это не баг конкретного запроса, а следствие модели
эмбеддингов, см. раздел «Если не так».

## Если не так

- **`ConnectionError` / таймаут при обращении к Ollama.** Ollama не
  запущена. Запустите `ollama serve` и повторите.
- **Модель не найдена (`model not found`).** Модель не скачана в этот
  инстанс Ollama: `ollama pull qwen2.5:7b` или `ollama pull nomic-embed-text`.
- **Второй-третий источник в retrieval оказывается тематически случайным,
  а его score близок к правильному документу.** `nomic-embed-text` —
  асимметричная модель эмбеддингов: она рассчитана на разные векторы для
  запроса и для документа (префиксы `search_query: ` / `search_document: `),
  а интеграция `llama-index-embeddings-ollama` эти префиксы не подставляет
  автоматически. Без них сходство считается менее точно, и все документы
  ложатся плотнее друг к другу по score, чем должны — на маленьком корпусе
  это может поднять нерелевантный документ на второе место. Для более чистого
  retrieval нужен эмбеддинг-провайдер, который сам расставляет префиксы, либо
  свой класс эмбеддингов поверх `ollama`, добавляющий их вручную.
- **`get_nodes_from_documents` не даёт видимого перекрытия текста между
  соседними узлами, хотя `chunk_overlap` задан.** Сплиттер режет по границам
  предложений, а не механически по символам: если предыдущий узел закончился
  ровно на конце предложения, следующий начинается с нового предложения без
  дословного повтора хвоста. Перекрытие проявляется, только когда граница
  `chunk_size` разрезает многосоставный абзац посередине.
