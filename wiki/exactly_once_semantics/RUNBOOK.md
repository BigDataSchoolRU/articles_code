# Exactly-Once Semantics на Apache Kafka 4.3.0: демо-стенд

Пошаговая инструкция для тех, кто хочет повторить демо у себя. Один брокер Kafka в режиме
KRaft, топик из трёх партиций, идемпотентный producer и транзакционный producer с consumer,
читающим с разным `isolation.level`.

## Окружение

| Что нужно | Версия на прогоне |
|---|---|
| Docker с плагином Compose | сервер 29.7.2, Compose v5.3.1 |
| Образ Apache Kafka | `apache/kafka:4.3.0` |
| Python | 3.12.13 |
| `confluent-kafka` | 2.15.0 |

Брокер слушает `localhost:9092`. Если порт занят, поменяйте его в `docker-compose.yml`
(`ports` и `KAFKA_ADVERTISED_LISTENERS`) и константу `BROKER` в обоих скриптах.

Установка клиента:

```bash
python3 -m pip install confluent-kafka==2.15.0
```

## Шаг 1. Поднять брокер

```bash
docker compose up -d
docker compose ps
```

Контейнер `exactly_once_semantics_kafka` должен быть в состоянии `running`. Готовность брокера
проверяется списком топиков, ответ приходит через 10-20 секунд после старта:

```bash
docker exec exactly_once_semantics_kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --list
```

Транзакции требуют журнала состояния транзакций с фактором репликации не выше числа брокеров —
на этом одноброкерном стенде в `docker-compose.yml` он уже выставлен в 1
(`KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR`, `KAFKA_TRANSACTION_STATE_LOG_MIN_ISR`).
На кластере с несколькими брокерами так специально не занижают: реплика ниже 3 снижает
устойчивость координатора транзакций к падению узла.

## Шаг 2. Создать топик

Автосоздание топиков на стенде выключено намеренно.

```bash
docker exec exactly_once_semantics_kafka /opt/kafka/bin/kafka-topics.sh --create \
  --bootstrap-server localhost:9092 \
  --topic exactly_once_semantics_events --partitions 3 --replication-factor 1
```

## Шаг 3. Идемпотентный producer против ретрая

```bash
python3 idempotent_producer.py
```

Скрипт замораживает контейнер брокера командой `docker pause` на 6 секунд (моделирует его
временную недоступность), при этом отправляет сообщение с `enable.idempotence=True` и
`request.timeout.ms=2000` — короче паузы, поэтому запрос гарантированно уходит в ретрай на
уровне протокола, а не просто ждёт ответа. После разморозки брокер отвечает, доставка
завершается, и скрипт читает партицию заново, считая записи с ключом сообщения.

Ожидаемый вывод — ровно одна запись, несмотря на ретраи:

```
замораживаем брокер на 6 с и отправляем сообщение с idempotence=True
доставлено на оффсет 0 за 6.57 с (время близко к 6 с — доставка ждала ретраев, пока брокер был заморожен)
записей с ключом 'order-idempotent-demo' в логе: 1
дублей нет — ретраи под капотом идемпотентны
```

Скрипту нужны права на управление Docker (тот же пользователь, что поднимал `docker compose`).

## Шаг 4. Транзакционный producer и isolation.level

```bash
python3 transactional_producer.py
```

Скрипт открывает две транзакции: первая пишет по одной записи в партиции 1 и 2 и коммитится,
вторая пишет запись в партицию 1 и откатывается (имитация сбоя обработки после записи, но до
завершения бизнес-логики). Дальше топик читается дважды: consumer с `isolation.level=
read_committed` и consumer с `isolation.level=read_uncommitted`.

Ожидаемый вывод: `read_committed` видит только две закоммиченные записи, `read_uncommitted` —
все три, включая запись из отменённой транзакции:

```
транзакция 1 закоммичена: записи в партициях (1, 2)
транзакция 2 отменена: запись в партиции 1 помечена aborted

isolation.level=read_committed: прочитано записей 2, ключи ['committed', 'committed']
  запись из отменённой транзакции видна: False

isolation.level=read_uncommitted: прочитано записей 3, ключи ['aborted', 'committed', 'committed']
  запись из отменённой транзакции видна: True
```

## Шаг 5. Погасить стенд

```bash
docker compose down        # контейнер снести, данные оставить
docker compose down -v     # снести вместе с данными топика
```

## Если не так

**`idempotent_producer.py` зависает дольше 25 секунд или падает `RuntimeError`.** Скрипт не смог
разморозить контейнер (например, у процесса нет прав на Docker) или брокер не поднялся заново
после паузы. Проверьте `docker ps` — контейнер должен быть `Up`, а не `Paused`, и при необходимости
разморозьте руками: `docker unpause exactly_once_semantics_kafka`.

**Повторный запуск `idempotent_producer.py` не показывает дубли, хотя ожидались.** Это ожидаемое
поведение, а не баг: демонстрируется как раз отсутствие дублей. Каждый повторный запуск добавляет
в партицию 0 ещё одну запись с тем же ключом на новом оффсете — счётчик считает только последний
запуск, потому что читает с начала партиции и совпадения по ключу могут накопиться от прошлых
прогонов. Для чистой проверки удалите и создайте топик заново (шаг 2).

**`transactional_producer.py` падает на `init_transactions()` с таймаутом.** Журнал состояния
транзакций (`__transaction_state`) создаётся брокером автоматически при первом обращении и может
не успеть выйти из-под инициализации сразу после старта контейнера — подождите 10-15 секунд после
шага 1 и повторите.

**`KafkaError{code=INVALID_PRODUCER_EPOCH}` при повторном запуске `transactional_producer.py`.**
`transactional.id` в скрипте фиксированный, и координатор транзакций закрепляет за ним растущий
номер эпохи. Повторный запуск с тем же `transactional.id` — штатный сценарий (именно так продюсер
переживает свой собственный перезапуск без дублей), эта ошибка означает, что где-то ещё работает
другой процесс с тем же `transactional.id` одновременно.

**Ошибка подключения `Connection refused`.** Брокер ещё стартует. Подождите и повторите список
топиков из шага 1.
