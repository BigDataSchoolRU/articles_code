# RUNBOOK: Star schema и Snowflake schema в PostgreSQL 18

Пошаговый прогон демо к статье [Star schema](https://bigdataschool.ru/wiki/star_schema/).
Один контейнер PostgreSQL 18.6, две схемы в одной базе: `star` и `snowflake`. Факты и значения
атрибутов в них одинаковые, отличается только устройство измерений. Сценарии написаны на чистом
SQL и выполняются через `psql` внутри контейнера.

## Окружение

| Компонент | Версия |
|---|---|
| PostgreSQL | 18.6, образ `postgres:18.6` |
| Docker | с плагином Compose, проверено на Docker 29.1.3 и Compose 2.40.3 |
| ОС стенда | проверено на Ubuntu 24.04, x86_64, 4 vCPU |

Сервер слушает `127.0.0.1:55439`, пользователь, пароль и база `demo`/`demo`/`dwh`. Если порт занят,
поменяйте его в `docker-compose.yml`: сценарии ходят в базу через `docker compose exec`, порт им не
нужен. Том займёт около 260 МБ.

В `docker-compose.yml` сервер стартует с двумя параметрами. `shared_buffers=256MB` нужен, чтобы
обе таблицы фактов по 115 МБ целиком лежали в кэше и замеры времени не зависели от чтения с
диска. `max_wal_size=256MB` не даёт журналу при загрузке 4 млн строк разрастись до гигабайта.

Время выполнения запросов у вас будет другим: оно зависит от процессора и числа параллельных
воркеров. Число строк, суммы, md5 результатов, размеры таблиц, число JOIN и объём WAL совпадут,
если шаги идут по порядку на чистом томе.

## Шаг 1. Поднять сервер

```bash
docker compose up -d --wait
docker compose exec -T pg psql -U demo -d dwh -XAtc "SELECT version()"
```

Ожидаемо:

```
 Container star-schema-pg  Healthy
PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2) on x86_64-pc-linux-gnu, compiled by gcc (Debian 14.2.0-19) 14.2.0, 64-bit
```

Все шаги разом запускает `./star_schema_demo.sh all`, по одному `./star_schema_demo.sh star`,
`snowflake`, `queries`, `rename`. Шаги зависят друг от друга, поэтому по одному их запускайте по
порядку.

## Шаг 2. Star schema

```bash
./star_schema_demo.sh star
```

Скрипт создаёт схему `star`. В ней четыре измерения с суррогатными ключами (`dim_date` на 731 день
2024-2025 годов, `dim_product` на 12 000 товаров, `dim_store` на 400 магазинов, `dim_customer` на
100 000 покупателей) и таблица фактов `fact_sales` на 2 млн строк. Гранулярность факта: одна строка
на позицию чека. В факте только ключи измерений и две аддитивные меры, `quantity` и `amount`.

Иерархии лежат прямо в строке измерения. У товара это `subcategory_name` и `category_name`, у
магазина `city_name` и `region_name`. Данные генерирует `random()` от `setseed(0.42)`, поэтому при
каждом прогоне на чистой базе получаются те же строки.

Внешние ключи факта ставятся после загрузки одним `ALTER TABLE`. На загрузке это заметно. В нашем
пилотном прогоне с ключами в `CREATE TABLE` вставка шла 80 секунд, потому что на каждую строку
уходило четыре проверки. Загрузка без ключей с последующим `ALTER TABLE` укладывается примерно в
10 секунд.

Ожидаемо в конце:

```
INSERT 0 2000000
Time: 6042.830 ms (00:06.043)
...
ALTER TABLE
Time: 3551.209 ms (00:03.551)
...
     таблица      |  строк
------------------+---------
 star.fact_sales  | 2000000
 star.dim_product |   12000
 star.dim_store   |     400
```

## Шаг 3. Snowflake schema на тех же данных

```bash
./star_schema_demo.sh snowflake
```

Схема `snowflake` строится из `star` через `SELECT DISTINCT`. Измерение товара превращается в
цепочку `dim_product` → `dim_subcategory` → `dim_category`, измерение магазина в цепочку
`dim_store` → `dim_city` → `dim_region`. Дату и покупателя скрипт копирует без изменений: в них нет
иерархии, которую стоило бы выносить. Таблица фактов копируется целиком, потому что снежинка меняет
только измерения.

Ожидаемо, размеры таблиц вместе с индексами:

```
   схема   |     таблица     |  строк  | размер
-----------+-----------------+---------+---------
 star      | dim_customer    |  100000 | 9976 kB
 star      | dim_date        |     731 | 96 kB
 star      | dim_product     |   12000 | 2024 kB
 star      | dim_store       |     400 | 96 kB
 star      | fact_sales      | 2000000 | 115 MB
 snowflake | dim_category    |      12 | 80 kB
 snowflake | dim_city        |      40 | 80 kB
 snowflake | dim_customer    |  100000 | 9976 kB
 snowflake | dim_date        |     731 | 96 kB
 snowflake | dim_product     |   12000 | 1504 kB
 snowflake | dim_region      |       8 | 80 kB
 snowflake | dim_store       |     400 | 80 kB
 snowflake | dim_subcategory |     120 | 88 kB
 snowflake | fact_sales      | 2000000 | 115 MB

   схема   | таблиц | размер вместе с индексами
-----------+--------+---------------------------
 star      |      2 | 2120 kB
 snowflake |      6 | 1912 kB
```

Нормализация сэкономила около 200 КБ на измерениях, а таблица фактов в обеих схемах весит 115 МБ.
Объём хранилища определяет факт, а не измерения.

## Шаг 4. Одна выборка на двух схемах

```bash
./star_schema_demo.sh queries
```

Тексты запросов лежат во временной таблице `demo_queries`, чтобы результат, планы и замеры шли
ровно по одному SQL. На звезде запрос соединяет факт с тремя измерениями, на снежинке с семью
таблицами.

Сначала печатаются пределы планировщика (значения по умолчанию в 18.6, `shared_buffers` в
страницах по 8 КБ):

```
              name               | setting
---------------------------------+---------
 from_collapse_limit             | 8
 geqo                            | on
 geqo_threshold                  | 12
 join_collapse_limit             | 8
 max_parallel_workers_per_gather | 2
 shared_buffers                  | 32768
```

Пять верхних строк результата на звезде:

```
  category_name  |    region_name    |  revenue   | units
-----------------+-------------------+------------+-------
 Игрушки         | Северо-Западный   | 1389857.24 |  8208
 Спорт           | Северо-Кавказский | 1379861.88 |  8198
 Книги           | Южный             | 1370338.02 |  8075
 Продукты        | Дальневосточный   | 1360402.65 |  7805
 Бытовая техника | Дальневосточный   | 1358912.21 |  7971
```

Результаты совпадают. Отпечаток считается как md5 всех строк, отсортированных как текст:

```
       запрос        | rows | total_revenue |               md5
---------------------+------+---------------+----------------------------------
 star                |   96 |  125438593.05 | 6c49277e535078937bf25f37376c36d5
 snowflake_date_last |   96 |  125438593.05 | 6c49277e535078937bf25f37376c36d5
 snowflake           |   96 |  125438593.05 | 6c49277e535078937bf25f37376c36d5
```

Дальше идут два полных плана `EXPLAIN (ANALYZE, BUFFERS)`. В обоих факт читается одним
`Parallel Seq Scan`, а измерения входят через `Hash Join`. Каждое измерение целиком помещается в
хеш-таблицу: товары занимают 769 КБ на звезде и 597 КБ на снежинке. Звезда даёт три узла
`Hash Join`, снежинка семь, и каждый из них прогоняет через себя 83 192 строки факта на каждый из трёх процессов (ведущий и два воркера).

Замер, прогрев и 5 прогонов на каждый запрос, медианы:

```
   схема   | tables | join_nodes | planning_ms | execution_ms | min_ms | max_ms | shared_hit | shared_read
-----------+--------+------------+-------------+--------------+--------+--------+------------+-------------
 star      |      4 |          3 |       0.476 |        302.3 |  288.0 |  352.3 |      15244 |           0
 snowflake |      8 |          7 |       1.156 |        389.1 |  378.0 |  427.8 |      15058 |           0
```

Все страницы взяты из кэша (`shared_read 0`). Буферов на снежинке даже немного меньше, потому что
справочники компактнее. Разница во времени, около 30%, уходит на четыре лишних `Hash Join`, а
планирование дольше в 2.4-2.8 раза. В двух наших прогонах подряд медианы были 302 мс на звезде и
389-401 мс на снежинке.

### Порядок JOIN выбирает планировщик

Третий запрос `snowflake_date_last` тот же самый, только измерение даты с фильтром по кварталу
стоит в тексте последним. В снежинке 8 таблиц, это ровно `join_collapse_limit`. Планировщик
переставляет соединения сам и ставит фильтр по дате первым, как в обычном запросе. С
`join_collapse_limit = 1` он соединяет таблицы ровно в порядке текста, и все 2 млн строк факта
проходят через шесть `Hash Join` до того, как фильтр по дате их отсечёт:

```
                     ->  Hash Join
                           Hash Cond: (f.date_key = d.date_key)
                           ->  Hash Join
                                 Hash Cond: (ci.region_key = r.region_key)
                                 ...
                                                               ->  Parallel Seq Scan on fact_sales f
```

```
         вариант         | tables | join_nodes | planning_ms | execution_ms | min_ms | max_ms
-------------------------+--------+------------+-------------+--------------+--------+--------
 join_collapse_limit = 8 |      8 |          7 |       1.151 |        424.6 |  404.0 |  442.6
 join_collapse_limit = 1 |      8 |          7 |       0.561 |       1572.4 | 1533.3 | 1803.8
```

С лимитом 1 планирование короче, потому что перебирать порядки не нужно, а выполнение почти в
четыре раза дольше. Во втором прогоне было 488 мс против 1881 мс.

### Удаление лишнего JOIN

`LEFT JOIN` к измерению, из которого запрос не берёт ни одной колонки, PostgreSQL выбрасывает из
плана. Ключ измерения уникален, значит соединение не может ни размножить, ни отфильтровать строки:

```
 Finalize Aggregate
   ->  Gather
         Workers Planned: 2
         ->  Partial Aggregate
               ->  Parallel Seq Scan on fact_sales f
```

С `INNER JOIN` то же соединение остаётся, хотя внешний ключ гарантирует, что пара найдётся всегда:

```
               ->  Parallel Hash Join
                     Hash Cond: (f.customer_key = c.customer_key)
                     ->  Parallel Seq Scan on fact_sales f
                     ->  Parallel Hash
                           ->  Parallel Index Only Scan using dim_customer_pkey on dim_customer c
```

## Шаг 5. Цена переименования категории

```bash
./star_schema_demo.sh rename
```

Категорию «Электроника» переименовывают в «Электроника и гаджеты» в обеих схемах. Объём WAL
считается по разнице `pg_current_wal_lsn()` до и после `UPDATE`:

```
UPDATE star.dim_product SET category_name = 'Электроника и гаджеты' WHERE category_name = 'Электроника';
UPDATE 1000
 WAL на звезде
---------------
 2287 kB

UPDATE snowflake.dim_category SET category_name = 'Электроника и гаджеты' WHERE category_name = 'Электроника';
UPDATE 1
 WAL на снежинке
-----------------
 1072 bytes
```

На звезде название категории записано в каждой из 1000 строк товара, на снежинке в одной строке
справочника. Выручка новой категории после переименования в обеих схемах одинакова:

```
   схема   |   revenue
-----------+-------------
 star      | 10357272.08
 snowflake | 10357272.08
```

## Шаг 6. Убрать стенд

```bash
docker compose down -v
```

## Если не так

- **`Container star-schema-pg  Error` или порт занят.** Поменяйте порт в `docker-compose.yml`,
  сценариям он не нужен.
- **`FATAL: the database system is shutting down` на первом запросе.** Healthcheck без
  `-h 127.0.0.1` отвечает «готов» ещё во время `initdb`. В `docker-compose.yml` проверка уже идёт
  по TCP; если вы её меняли, верните `-h 127.0.0.1`.
- **`function random(integer, integer) does not exist`.** Вариант `random(min, max)` появился в
  PostgreSQL 17. На более старой версии замените его на `1 + floor(random() * max)::int`.
- **Суммы и md5 не совпадают с RUNBOOK.** Данные одинаковы только на чистом томе и при запуске
  шагов по порядку: `docker compose down -v`, затем `up` и `all`.
- **`shared_read` больше нуля, время скачет.** Таблицы не поместились в кэш: проверьте, что сервер
  поднялся с `shared_buffers=256MB` (`SHOW shared_buffers`), и запустите шаг 4 ещё раз.
- **Объём WAL на звезде другой.** Первое изменение страницы после контрольной точки пишет в журнал
  её полный образ, поэтому цифра зависит от того, когда прошла последняя контрольная точка.
  Соотношение «тысяча строк против одной» от этого не меняется.
- **На снежинке в шаге 4 план с другим порядком JOIN.** Порядок хеш-соединений выбирается по
  статистике. Если вы меняли объёмы данных, запустите `ANALYZE` и сравните ещё раз.
