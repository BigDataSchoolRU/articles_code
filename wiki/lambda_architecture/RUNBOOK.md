# RUNBOOK: Lambda Architecture

Демо к статье [Lambda Architecture](https://bigdataschool.ru/wiki/lambda_architecture/) на
bigdataschool.ru. Пять шагов показывают все три слоя архитектуры на игрушечном потоке
просмотров страниц: batch layer пересчитывает представление целиком, speed layer считает
дельту поверх свежих событий, serving layer объединяет оба ответа.

## Окружение

- Docker с плагином Compose (проверено на Docker 29.7.2, Compose v5.3.1)
- Python 3.12+, пакеты `confluent-kafka` (проверено на 2.15.0) и `duckdb` (проверено на 1.5.5)
- Порт `9092` (Kafka) должен быть свободен на хосте
- Все адреса ниже — `localhost`, подставлять свои не нужно

Установка Python-зависимостей:

```bash
pip install confluent-kafka==2.15.0 duckdb==1.5.5
```

## Шаг 1. Поднять Kafka

```bash
docker compose up -d
```

Готовность брокера проверяется списком топиков, он отвечает через несколько секунд после старта:

```bash
docker exec lambda_architecture_kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --list
```

Пустой ответ без ошибки означает, что брокер поднялся и топиков ещё нет. Автосоздание
выключено намеренно: топик создаёт `event_producer.py`.

## Шаг 2. Записать «исторический» трафик (пакет 1)

```bash
python3 event_producer.py 1
```

Ожидаемый вывод:

```
=== пакет 1: 10 событий, ts 1000-1009 ===
топик lambda_architecture_events создан
в Kafka записано событий: 10, оффсеты 0-9
мастер-датасет дополнен: master_dataset.jsonl
```

Каждое событие уходит сразу в двух направлениях: в топик Kafka (вход speed layer) и строкой в
append-only файл `master_dataset.jsonl` (вход batch layer). Это и есть точка ветвления Lambda
Architecture на два параллельных пути.

## Шаг 3. Прогнать batch layer

```bash
python3 batch_layer.py
```

Ожидаемый вывод:

```
пересчитано по 10 событиям мастер-датасета за 0.730 с
watermark (последний учтённый ts): 1009
batch_view:
  /blog: 3 просмотров (по ts <= 1008)
  /docs: 11 просмотров (по ts <= 1009)
  /home: 12 просмотров (по ts <= 1006)
  /pricing: 7 просмотров (по ts <= 1007)
```

`batch_view` строится заново из **всего** мастер-датасета, а не дописывается по последним
строкам — это и делает batch layer медленным, но точным. `watermark` (1009) фиксирует границу:
всё с `ts <= 1009` уже учтено, дальше это работа speed layer.

## Шаг 4. Записать «свежий» трафик и прогнать speed layer

Пакет 2 имитирует события, случившиеся уже после того, как batch layer отработал:

```bash
python3 event_producer.py 2
python3 speed_layer.py
```

Ожидаемый вывод `speed_layer.py`:

```
прочитано из Kafka событий: 13, новее watermark 1009: 3, за 6.28 с
speed_view (дельта поверх batch_view):
  /home: +9 просмотров
  /pricing: +3 просмотров
```

`speed_layer.py` каждый раз перечитывает лог Kafka с начала новой consumer-группой (все 13
событий, что уже накопились в топике) и сам решает по watermark, какие из них batch ещё не
видел — 3 события из пакета 2. Реальных вычислений тут на доли секунды, а 6+ секунд уходят на
таймауты опроса брокера (см. «Если не так»).

## Шаг 5. Получить ответ serving layer

```bash
python3 serving_layer.py
```

Ожидаемый вывод:

```
watermark batch_view: 1009

=== ответ только от batch layer (устаревший, события после watermark не видны) ===
  /blog: 3
  /docs: 11
  /home: 12
  /pricing: 7

=== ответ serving layer: batch_view + speed_view ===
  /blog: 3
  /docs: 11
  /home: 21
  /pricing: 10

=== сверка: честный пересчёт по всему мастер-датасету ===
  /blog: 3
  /docs: 11
  /home: 21
  /pricing: 10

serving layer совпал с честным пересчётом: True
просмотров недосчитал бы ответ только от batch layer: 12
```

Ключевая строка — последняя: если бы клиент читал только `batch_view`, он бы не досчитался 12
просмотров, случившихся после последнего прогона batch layer. Serving layer закрывает этот
разрыв объединением `batch_view` и `speed_view`, и merge совпадает с честным пересчётом по
всему датасету — при таких небольших объёмах его можно посчитать напрямую и сверить.

## Шаг 6. Погасить стенд

```bash
docker compose down        # контейнер снести, данные оставить
docker compose down -v     # снести вместе с данными топика
```

## Если не так

**`speed_layer.py` выполняется 5+ секунд, хотя событий всего 13.** Так и задумано: скрипт ждёт
`IDLE_LIMIT=5` пустых опросов подряд (по секунде каждый), чтобы понять, что дошёл до конца
лога. Само чтение и агрегация 13 событий занимают доли секунды, всё остальное время — это
таймаут ожидания, а не вычисления.

**Повторный запуск даёт числа больше ожидаемых.** Топик и `master_dataset.jsonl` накапливают
данные между запусками. Для чистого прогона удалите оба состояния и поднимите стенд заново:

```bash
docker compose down -v
rm -f master_dataset.jsonl lambda_view.duckdb
docker compose up -d
```

**`batch_layer.py` падает с "нет мастер-датасета".** Он ожидает, что `event_producer.py`
запускался хотя бы раз до него — сначала шаг 2, потом шаг 3.

**`speed_layer.py` падает с "нет batch_meta".** Watermark пишет `batch_layer.py`. Без него
speed layer не может определить, какие события уже учтены, поэтому последовательность шагов
фиксированная: сначала batch, потом speed.

**Ошибка подключения `Connection refused`.** Брокер ещё стартует после `docker compose up -d`,
подождите и повторите проверку из шага 1.
