# RUNBOOK: Sparse Mixture-of-Experts — top-k router, capacity factor, auxiliary loss

Локальное демо на чистом PyTorch, без Docker, без внешних API и без скачивания
весов настоящей модели. Игрушечный MoE-слой (8 экспертов, каждый — обычный
двухслойный FFN) показывает механику, которую в проде масштабируют до
десятков и сотен экспертов: top-k роутинг, capacity factor с token dropping и
auxiliary loss, балансирующий нагрузку экспертов.

## Окружение

- Python 3.10+ (демо написано и прогнано на 3.12.13)
- PyTorch (демо прогнано на 2.13.0, CPU достаточно, GPU не нужен)

## Шаг 1. Виртуальное окружение и зависимости

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install torch
```

Ожидаемый результат: `pip install` завершается без ошибок. Версия PyTorch —
любая актуальная 2.x, демо не использует свежий API.

## Шаг 2. Top-k роутер: top-1 против top-2

```bash
python3 topk_router.py
```

Скрипт строит батч из 16 случайных токенов и слой из 8 экспертов, затем
прогоняет один и тот же батч через top-1 (как в Switch Transformer) и top-2
(как в GShard) роутинг.

Ожидаемый результат — для каждого режима печатается распределение токенов по
экспертам, форма выхода `(16, 64)` и доля активных параметров на токен
относительно общих параметров слоя:

```
--- top-1 (Switch Transformer) ---
активные параметры на токен: 17,088 из 133,120 (12.8%)

--- top-2 (GShard) ---
активные параметры на токен: 33,664 из 133,120 (25.3%)
```

Как понять, что шаг прошёл: доля для top-2 примерно вдвое больше, чем для
top-1 — на каждый токен считается вдвое больше экспертов, а не потому что
слой стал больше. Числа детерминированы (`torch.manual_seed(42)`), поэтому
распределение токенов по экспертам и проценты должны совпасть с примером
выше при том же PyTorch 2.x на CPU.

## Шаг 3. Capacity factor, token dropping и auxiliary loss

```bash
python3 capacity_and_aux_loss.py
```

Скрипт прогоняет батч из 32 токенов через top-1 роутинг с двумя значениями
`capacity_factor` (1.0 и 1.25) сначала со случайным (сбалансированным)
роутером, затем со специально смещённым — один эксперт получает завышенный
логит, имитируя коллапс роутинга.

Ожидаемый результат:

```
=== Сбалансированный роутер (случайная инициализация) ===
capacity_factor=1.0: лимит на эксперта=4, дропнуто токенов=8 из 32
capacity_factor=1.25: лимит на эксперта=5, дропнуто токенов=5 из 32
auxiliary loss (alpha=0.01): 0.010505

=== Смещённый роутер (collapse: один эксперт доминирует) ===
capacity_factor=1.0: лимит на эксперта=4, дропнуто токенов=11 из 32, ...
capacity_factor=1.25: лимит на эксперта=5, дропнуто токенов=9 из 32, ...
auxiliary loss (alpha=0.01): 0.019086
```

Как понять, что шаг прошёл: при коллапсе дропов больше, чем у сбалансированного
роутера при том же `capacity_factor`, а auxiliary loss примерно вдвое выше —
именно за неравномерную нагрузку экспертов этот loss и штрафует.

## Если не так

- **`ModuleNotFoundError: No module named 'torch'`** — venv не активирован
  или `pip install torch` не выполнялся в этом окружении.
- **Числа не совпадают с примерами выше** — проверьте версию PyTorch: разные
  мажорные версии могут по-разному инициализировать веса `nn.Linear` при
  одном и том же `manual_seed`. Сама механика (доли активных параметров,
  рост дропов при коллапсе) должна воспроизводиться на любой версии 2.x.
- **`дропнуто токенов=0` на обоих capacity_factor** — на очень маленьком
  батче или при большом `capacity_factor` лимит на эксперта может оказаться
  достаточным для всех токенов; это не ошибка, увеличьте `NUM_TOKENS` в
  скрипте или уменьшите `capacity_factor`, чтобы увидеть дропы явно.
- **`UserWarning: Failed to initialize NumPy: No module named 'numpy'`** —
  безобидное предупреждение torch в окружении без NumPy, на результат не
  влияет; `pip install numpy` его уберёт, но для этого демо не обязательно.
