# Event Streaming на Apache Kafka 4.3.0: демо-стенд

Пошаговая инструкция для тех, кто хочет повторить демо у себя. Один брокер Kafka в режиме
KRaft, топик из трёх партиций, продюсер и несколько групп потребителей.

## Окружение

| Что нужно | Версия на прогоне |
|---|---|
| Docker с плагином Compose | сервер 29.7.2, Compose v5.3.1 |
| Образ Apache Kafka | `apache/kafka:4.3.0` |
| Python | 3.12.13 |
| `confluent-kafka` | 2.15.0 |

Брокер слушает `localhost:9092`. Если порт занят, поменяйте его в `docker-compose.yml`
(`ports` и `KAFKA_ADVERTISED_LISTENERS`) и в константе `BROKER` обоих скриптов.

Установка клиента:

```bash
python3 -m pip install confluent-kafka==2.15.0
```

## Шаг 1. Поднять брокер

```bash
docker compose up -d
docker compose ps
```

В выводе `ps` контейнер `event_streaming_kafka` должен быть в состоянии `running`. Готовность
брокера проверяется списком топиков, он отвечает через 10-20 секунд после старта:

```bash
docker exec event_streaming_kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --list
```

Пустой ответ без ошибки означает, что брокер поднялся и топиков ещё нет. Автосоздание топиков
на стенде выключено намеренно: топик создаёт скрипт с нужным числом партиций.

## Шаг 2. Записать события

```bash
python3 producer.py
```

Ожидаемый вывод: топик `orders` создан на три партиции, записано 8 событий, дальше карта
`ключ -> партиция:оффсет`. Проверьте главное свойство: все события одного магазина лежат в одной
партиции, потому что партицию выбирает хеш ключа. Оффсеты внутри партиции идут подряд с нуля.

```
топик orders создан, партиций: 3
записано событий: 8 за 0.024 с
  msk-01 -> 0:0
  omsk-08 -> 1:0
  ekb-03 -> 2:0
```

## Шаг 3. Прочитать лог разными группами

```bash
python3 consumer_groups.py
```

Скрипт проходит пять сценариев подряд, каждый со своим заголовком:

1. Группа `analytics` читает лог с начала и фиксирует оффсеты. Ожидается 8 событий.
2. Группа `billing` читает тот же топик и тоже получает 8 событий. Чтение не разрушает данные,
   группы независимы.
3. Группа `analytics` подключается повторно и получает 0 новых событий: её позиция хранится на
   брокере.
4. Новая группа `audit_replay` поднимает из лога всю историю целиком. Это и есть replay.
5. Два потребителя в одной группе `delivery` делят три партиции между собой, например `[0, 1]`
   и `[2]`. Партиция достаётся ровно одному потребителю группы.

Прогон занимает около полутора минут, и почти всё это время скрипт ждёт таймауты опроса и
ребалансировку групп, а не обрабатывает данные.

## Шаг 4. Посмотреть состояние снаружи

Конец лога по каждой партиции:

```bash
docker exec event_streaming_kafka /opt/kafka/bin/kafka-get-offsets.sh \
  --bootstrap-server localhost:9092 --topic orders
```

Позиции групп и отставание:

```bash
docker exec event_streaming_kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --all-groups
```

У групп `analytics` и `billing` `CURRENT-OFFSET` совпадает с `LOG-END-OFFSET`, а `LAG` равен
нулю. Группа `audit_replay` в выводе есть, но без оффсетов: она читала историю и ничего не
фиксировала.

## Шаг 5. Погасить стенд

```bash
docker compose down        # контейнер снести, данные оставить
docker compose down -v     # снести вместе с данными топика
```

## Если не так

**Скрипт молчит и ничего не читает.** Потребитель ждёт назначения партиций, а координатор
группы отвечает не мгновенно. В `consumer_groups.py` пустой опрос до назначения не считается
концом лога именно поэтому. Если убрать эту проверку, первое событие теряется: `poll` до
назначения успевает вернуть его и результат уходит в никуда.

**Повторный запуск даёт неожиданные цифры.** Топик и коммиты групп остаются от прошлого раза,
продюсер дописывает ещё 8 событий, а `analytics` продолжает со старого оффсета. Для чистого
прогона удалите топик и группы:

```bash
docker exec event_streaming_kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --delete --topic orders
docker exec event_streaming_kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --delete --group analytics
```

**Все события уходят в одну партицию.** Так и работает хеш ключа: на восьми событиях от четырёх
магазинов равномерности ждать не стоит. Ключи в `producer.py` подобраны так, чтобы задеть все
три партиции.

**`Could not find or load main class kafka.tools.GetOffsetShell`.** Начиная с Kafka 4.x класс
переехал, вместо `kafka-run-class.sh` используется готовый скрипт `kafka-get-offsets.sh`.

**Ошибка подключения `Connection refused`.** Брокер ещё стартует. Подождите и повторите список
топиков из шага 1.
