# RUNBOOK: Durable Execution на DBOS

Демо к статье про Durable Execution (bigdataschool.ru/wiki/durable_execution/). Показывает
ядро паттерна на библиотеке DBOS: workflow из трёх шагов переживает жёсткий крах процесса
(`kill -9`, не пойманное исключение) и на следующем запуске программы восстанавливается сам,
без единой строки кода вида «продолжи вот отсюда». По побочным эффектам каждого шага видно,
что уже выполненные шаги не повторяются.

## Окружение

- Python 3.12
- `dbos` 2.31.0, `psycopg[binary]` 3.3.4
- PostgreSQL 14+ (демо проверено на 18.4), доступный по TCP на localhost:5432, роль с правом
  создавать базы

Установка:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install dbos "psycopg[binary]"
```

Подставьте своего пользователя PostgreSQL в `DEMO_DSN` внутри `workflow_recovery_demo.py`
и в `ADMIN_DSN`/`DEMO_DSN` внутри `db_setup.py` (в демо использован `techfriends` с доверительной
аутентификацией по сокету — на вашей машине это, скорее всего, другое имя роли).

## Шаг 1. Подготовка базы

```bash
python3 db_setup.py
```

Что должно быть в выводе:

```
база durable_execution_demo готова, таблица side_effects создана
```

Скрипт идемпотентен: можно запускать повторно, база каждый раз пересоздаётся с нуля. Своя
служебная схема `dbos` (журнал workflow и шагов) создаётся и мигрируется автоматически при
первом запуске `workflow_recovery_demo.py` — отдельно готовить её не нужно.

## Шаг 2. Контрольный прогон без сбоя

```bash
python3 -u workflow_recovery_demo.py start
```

Что должно быть в выводе (порядок миграций и сервисных INFO-строк DBOS в консоли не приводим,
это шум библиотеки, не относящийся к демо):

```
PID=<число>
шаг 1: списываем оплату
шаг 2: резервируем товар на складе
шаг 3: отправляем подтверждение клиенту
workflow завершился без сбоя (контрольный прогон)
```

Как понять, что шаг прошёл: все три строки шагов присутствуют по порядку, процесс завершился
кодом 0. Это контроль того, что окружение и подключение к базе работают, прежде чем переходить
к сценарию с крахом.

## Шаг 3. Крах посреди workflow

Пересоздайте базу (шаг 1 обнулит workflow-идентификатор `order-42`, который использует демо),
затем запустите workflow в фоне и убейте процесс через 2 секунды — на этом окне между шагом 2
и шагом 3 workflow намеренно ждёт (`DBOS.sleep`), чтобы было куда прицелиться:

```bash
python3 db_setup.py
python3 -u workflow_recovery_demo.py start &
PID=$!
sleep 2
kill -9 $PID
wait $PID 2>/dev/null
```

Что должно быть в выводе перед `kill -9`:

```
PID=<число>
шаг 1: списываем оплату
шаг 2: резервируем товар на складе
```

Строки шага 3 быть не должно — процесс убит до него. Проверьте побочные эффекты напрямую в базе:

```bash
psql -d durable_execution_demo -c \
  "SELECT step_name, count(*) FROM side_effects GROUP BY step_name ORDER BY step_name;"
```

Ожидаемый результат: по одной строке на `charge_payment` и `reserve_inventory`, строки
`send_confirmation` нет вообще.

## Шаг 4. Восстановление на следующем запуске

```bash
python3 -u workflow_recovery_demo.py recover
```

Что должно быть в выводе:

```
шаг 3: отправляем подтверждение клиенту
статус workflow после восстановления: SUCCESS
побочные эффекты по шагам: {'charge_payment': 1, 'reserve_inventory': 1, 'send_confirmation': 1}
```

Как понять, что шаг прошёл: в выводе есть только `шаг 3` — шаги 1 и 2 не печатаются заново,
потому что DBOS не выполняет их повторно, а подставляет уже сохранённый результат. Итоговый
счётчик побочных эффектов — ровно единица на каждый шаг, несмотря на крах между шагом 2 и
шагом 3.

## Если не так

- **`Recovering 0 workflows` вместо `Recovering 1 workflows`.** Между шагом 3 и шагом 4 прошло
  больше времени, чем `DBOS.sleep` в workflow, и восстановленный workflow уже успел
  доработать и завершиться до вашей проверки — гонка с проверкой, не ошибка демо. Уменьшите
  паузу между `kill -9` и запуском `recover`, либо смотрите на счётчики `side_effects`, они
  корректны в любом случае.
- **В выводе шага 3 не видно строк `PID=...` и `шаг 1/2`.** Python буферизует stdout, когда
  он не подключён к терминалу, и `kill -9` может убить процесс до того, как буфер сбросится
  на диск. Демо запускает интерпретатор с флагом `-u` (`python3 -u ...`) именно для того,
  чтобы этого не происходило; без `-u` вывод может быть неполным, но сама база данных всё
  равно покажет правильные счётчики.
- **Повторный `start` с той же базой падает или ведёт себя странно.** Workflow-идентификатор
  `order-42` в демо фиксированный, а PostgreSQL-роль DBOS хранит для него законченный
  статус. Перед повторным сценарием краха всегда пересоздавайте базу командой `db_setup.py`.
- **`psql: could not connect to server`.** PostgreSQL не запущен или слушает не на 5432 —
  проверьте `pg_isready -h localhost -p 5432` и правильность DSN в обоих скриптах.
