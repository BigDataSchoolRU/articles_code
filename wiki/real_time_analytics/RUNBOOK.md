# Real-Time Analytics на Kafka и DuckDB: демо-стенд

Пошаговая инструкция, чтобы повторить измерение задержки «событие → доступный агрегат» у себя.
Один брокер Kafka (KRaft, без реестра схем) принимает поток заказов, потребитель сразу пишет
каждое событие в DuckDB и пересчитывает агрегат по категориям.

## Окружение

| Что нужно | Версия на прогоне |
|---|---|
| Docker с плагином Compose | сервер 29.7.2, Compose v5.3.1 |
| Образ Apache Kafka | `apache/kafka:4.3.0` |
| Python | 3.12.13 |
| `confluent-kafka` | 2.15.0 |
| `duckdb` | 1.5.5 |

Брокер слушает `localhost:9092`. Если порт занят, поменяйте его в `docker-compose.yml`
(`ports` и `KAFKA_ADVERTISED_LISTENERS`) и константу `BROKER` в обоих Python-файлах.

Установка зависимостей:

```bash
python3 -m pip install confluent-kafka==2.15.0 duckdb==1.5.5
```

## Шаг 1. Поднять брокер

```bash
docker compose up -d
docker compose ps
```

Контейнер `real_time_analytics_kafka` должен быть в состоянии `running`. Готовность брокера
проверяется списком топиков, он отвечает через 10-20 секунд после старта:

```bash
docker exec real_time_analytics_kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --list
```

Пустой ответ без ошибки означает, что брокер поднялся и топиков ещё нет.

## Шаг 2. Запустить потребителя первым

```bash
python3 consumer_realtime.py
```

Потребитель сам создаёт топик `real_time_analytics_events` (одна партиция, автосоздание на
стенде выключено), поднимает файл DuckDB `realtime_analytics.duckdb` рядом со скриптом и ждёт
события. Дождитесь строки:

```
топик real_time_analytics_events создан
группа получила партиции [0], жду события
```

Пока этой строки нет, не запускайте продюсера — события, отправленные до назначения партиций,
не потеряются в самом Kafka, но собьют картину задержки: часть из них потребитель вычитает
одной пачкой сразу после назначения, а не по одному в реальном времени.

## Шаг 3. Запустить продюсера вторым (в другом терминале)

```bash
python3 producer.py
```

Скрипт отправляет 30 событий заказов по одному, с паузами 0.05-0.3 с между ними — это и
имитирует непрерывный поток, а не пачку. Ожидаемый вывод:

```
отправлено событий: 30 из 30 за 4.79 с
```

## Что покажет потребитель

В терминале с `consumer_realtime.py` на каждое событие печатается строка с задержкой между
моментом события (`event_time` в самом сообщении) и моментом, когда обновлённый агрегат по
категориям стал доступен запросу к DuckDB:

```
событие  1 (electronics): задержка 0.347 с
событие  2 (clothing): задержка 0.224 с
...
событие  5 (electronics): задержка 0.013 с
...
событие 30 (clothing): задержка 0.012 с

обработано событий: 30
задержка событие -> доступный агрегат: мин 0.011 с, среднее 0.038 с, макс 0.347 с

итоговый агрегат по категориям:
  books        сумма    756.95  заказов 6
  clothing     сумма   1171.69  заказов 5
  electronics  сумма   3098.90  заказов 11
  grocery      сумма   1918.64  заказов 8
```

Первые 3-4 события идут с повышенной задержкой (сотни миллисекунд), дальше она падает до
единиц-десятков миллисекунд и там и остаётся. Это разогрев внутреннего цикла опроса брокера у
клиента, а не задержка самой обработки: как только клиент выходит на рабочий режим, каждое
новое событие становится частью агрегата практически сразу.

## Шаг 4. Погасить стенд

```bash
docker compose down        # контейнер снести, данные топика остаются в контейнере
docker compose down -v     # снести вместе с данными
rm -f realtime_analytics.duckdb   # локальная база демо, пересоздаётся сама при следующем запуске
```

## Если не так

**Потребитель падает на первом опросе с `UNKNOWN_TOPIC_OR_PART`.** Топик ещё не создан —
`consumer_realtime.py` создаёт его сам при старте, ошибка означает, что до этого не дошло:
проверьте, что брокер поднят (шаг 1).

**Задержка первых событий больше секунды, а не долей секунды.** Продюсер запустили до того, как
потребитель напечатал «жду события». Остановите оба скрипта, удалите топик и группу и повторите
шаги 2-3 по порядку:

```bash
docker exec real_time_analytics_kafka /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --delete --topic real_time_analytics_events
docker exec real_time_analytics_kafka /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --delete --group realtime_analytics_dashboard
```

**Повторный запуск потребителя падает или агрегат выглядит неожиданно.** Файл
`realtime_analytics.duckdb` от прошлого прогона мешает: `consumer_realtime.py` удаляет и
пересоздаёт его сам при старте, но если файл открыт другим процессом (например, `duckdb`
CLI), удаление не пройдёт. Закройте посторонние подключения к файлу и запустите снова.

**Ошибка подключения `Connection refused`.** Брокер ещё стартует. Подождите 10-20 секунд и
повторите список топиков из шага 1.
