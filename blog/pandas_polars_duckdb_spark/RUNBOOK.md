# RUNBOOK: pandas, Polars, DuckDB и PySpark на одном датасете под бюджетом 2048 МБ

## Окружение

- Linux (скрипты ограничивают процесс двумя ядрами через `os.sched_setaffinity`; на macOS это ограничение пропускается).
- Python 3.11 или новее (этого требует pandas 3.0).
- Java 11 или 17 для PySpark 3.5.7: команда `java` в `PATH` или выставленный `JAVA_HOME`. Без Java варианты Spark не запускаются, а помечаются `SKIP` / `skip: no java`; остальные движки работают.
- Свободно: 4 ГБ RAM и около 6 ГБ диска (датасеты, результаты и сброс DuckDB во временный каталог).
- Docker не нужен: лимит 2048 МБ эмулируется сторожем, который суммирует RSS дерева процессов и убивает его при превышении, как это сделал бы cgroup.

Переменные окружения:

- `JAVA_HOME` — только если `java` не находится в `PATH`.
- `POLARS_MAX_THREADS` и `SPARK_LOCAL_IP` скрипты выставляют сами, задавать их не нужно.

Ключи и внешние сервисы не нужны.

## Шаг 1. Виртуальное окружение и пакеты

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -c "import pandas, polars, duckdb, pyspark; print(pandas.__version__, polars.__version__, duckdb.__version__, pyspark.__version__)"
java -version
```

В выводе: `3.0.6 1.44.2 1.5.5 3.5.7` и версия Java 11 или 17. Шаг прошёл, если импорт не упал. Если `java -version` отвечает `command not found`, Spark-часть будет пропущена; чтобы её получить, поставьте JDK 17 из пакетного менеджера ОС.

## Шаг 2. Генерация данных

```bash
.venv/bin/python 01_gen_data.py
```

В выводе три строки: `data/products.parquet` на 20,000 строк, `data/orders_small.parquet` на 6,000,000 строк и `data/orders_large.parquet` на 30,000,000 строк, у каждого размер на диске в МБ, плюс схема фактов. Повторный запуск печатает `уже есть, пропуск`. Шаг прошёл, если все три файла на месте.

## Шаг 3. Память pandas: диск против RAM

```bash
.venv/bin/python 02_pandas_memory.py
```

В выводе таблица: размер DataFrame для всех колонок, для 6 колонок задачи, для 3 колонок и для `dtype_backend=pyarrow`, с множителем к размеру файла. Ожидаем, что все колонки занимают в разы больше файла, `columns=[...]` резко уменьшает объём, а `dtype_backend=pyarrow` почти не меняет картину. Внизу экстраполяция на `data/orders_large.parquet` против бюджета 2048 МБ. Шаг прошёл, если таблица напечатана целиком.

## Шаг 4. Одна задача в одном движке

```bash
.venv/bin/python 03_engine_task.py duckdb small
.venv/bin/python 03_engine_task.py spark_tuned small
```

В выводе строка с временем, числом групп (`групп 40`), числом заказов и выручкой, затем строка `RESULT {...}`. У Spark отдельно показан старт сессии. Результат лежит в `results/duckdb_small.parquet` и `results/spark_tuned_small.parquet`. Шаг прошёл, если число заказов и выручка у двух движков совпадают. Без Java вторая команда печатает `SKIP spark_tuned: java не найдена` и выходит с кодом 3.

## Шаг 5. Матрица: 7 вариантов движков на двух размерах

```bash
.venv/bin/python 04_bench_matrix.py
```

На small каждый вариант запускается три раза, в таблицу идёт медиана; на large один раз. В итоговой таблице колонки `status`, `wall`, `task`, `пик RSS`, `заказов`. Ожидаем: на small все `ok`; на large pandas, скорее всего, получит `OOM>2048MB`, DuckDB и Polars streaming проходят с меньшим пиком памяти; у Spark `wall` больше `task` на время старта сессии. Без Java у `spark_default` и `spark_tuned` статус `skip: no java`, в сверку они не входят. Строки `сверка результатов` должны сказать `совпадают у всех успешных`. Таблица сохраняется в `results/bench.csv`, логи каждого запуска в `results/logs/`. Шаг прошёл, если таблица и сверка напечатаны.

## Шаг 6. Polars: eager, lazy и streaming на large

```bash
.venv/bin/python 05_polars_streaming.py
```

Сначала печатается оптимизированный план: в узле чтения Parquet строка `PROJECT 4/9 COLUMNS` показывает, что берутся не все колонки. Потом таблица из четырёх режимов с временем и пиковым RSS. Ожидаем, что `eager_all_columns` тратит памяти больше всех (или получает `OOM>2048MB`), а `lazy_streaming` и `sink_parquet_streaming` держат пик ниже, чем `lazy_in_memory`. Шаг прошёл, если у lazy-режимов число строк одинаковое (20000).

## Шаг 7. DuckDB: сброс на диск и лимит temp-каталога

```bash
.venv/bin/python 06_duckdb_spill.py
```

Таблица из трёх случаев сортировки `data/orders_large.parquet` (30,000,000 строк). Ожидаем: в случае `sort_mem_400mb` пик `temp` больше, чем в `sort_mem_1200mb`, а пик RSS ниже; третий случай `sort_mem_400mb_tmp_64mb` (с ограничением `max_temp_directory_size`) заканчивается `error` с пометкой `ожидаемо` и текстом ошибки DuckDB. Шаг прошёл, если первые два случая `ok` и скрипт вернул код 0.

## Шаг 8. Ловушка часового пояса в PySpark

```bash
.venv/bin/python 07_spark_timezone_trap.py
```

В выводе тип колонки `ts` в Spark, значение литерала `F.lit(datetime(2024, 3, 1))` в сессии UTC (ожидаем `2024-02-29 21:00:00`) и таблица: эталон pyarrow, наивный фильтр Spark с ненулевой разницей и исправленный фильтр с разницей `+0`. Шаг прошёл, если последняя строка: `исправленный фильтр совпадает с эталоном`. Без Java печатается только эталон pyarrow и строка `SKIP: java не найдена`.

## Шаг 9. Полный прогон одной командой

```bash
.venv/bin/python selfcheck.py
cat .status
```

Весь вывод попадает в `run_output.txt`, блоки начинаются строками `DEMO 01_gen_data.py` и так далее, после каждого блока `exit code N`. Вторая строка вывода сообщает версию Java или что она не найдена и Spark будет пропущен. В `.status` одна строка `<код> <время UTC>`, код 0 означает, что все демо прошли. С флагом `--detach` прогон уходит в фон, и готовность видна по появлению `.status`.

## Если не так

- В выводе `SKIP` или `skip: no java` у Spark: Java не найдена. Поставьте JDK 11 или 17 и либо добавьте `java` в `PATH`, либо выставьте `JAVA_HOME`, затем повторите шаги 4, 5 и 8.
- `JAVA_GATEWAY_EXITED` или `Java gateway process exited` при найденной Java: версия не подходит для Spark 3.5 (например, слишком новая). Переключите `JAVA_HOME` на JDK 17.
- `Python worker failed to connect back` или предупреждение про hostname у Spark: проверьте, что `SPARK_LOCAL_IP` не переопределён чем-то кроме `127.0.0.1`.
- Spark на small получает `OOM>2048MB`: на вашей JVM накладные расходы выше. Это честный результат для local mode; для сравнения уменьшите `spark.driver.memory` в `03_engine_task.py` или поднимите `BUDGET_MB` в `04_bench_matrix.py` и укажите это при публикации цифр.
- Машина целиком уходит в swap или OOM-killer убивает процессы до сторожа: в системе меньше 4 ГБ свободной памяти. Закройте лишнее или сгенерируйте меньший large: `01_gen_data.py --large-rows 15000000`.
- `06_duckdb_spill.py` падает в первых двух случаях с ошибкой записи: не хватает места на диске для `data/duckdb_tmp`. Освободите 2–3 ГБ.
- `сверка результатов: РАСХОДЯТСЯ`: откройте логи в `results/logs/` и сравните фильтр по `ts`; чаще всего виноват часовой пояс (см. шаг 8).
- `collect(engine="streaming")` ругается на неизвестный engine: установлена не та версия Polars, проверьте `pip show polars` против `requirements.txt`.
- Время сильно скачет между повторами: файлы ещё не в кэше ОС или параллельно работает другая нагрузка. Запустите шаг 5 повторно.
