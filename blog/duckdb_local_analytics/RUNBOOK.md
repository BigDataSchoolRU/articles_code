# DuckDB для локальной аналитики: как повторить демо

## Окружение

- Linux или macOS, Python 3.12, 4 ядра и от 4 ГБ RAM.
- Около 1,5 ГБ свободного места: Parquet, CSV, файл SQLite и временные файлы spill.
- Сервер БД, Docker и сеть для самих запросов не нужны.
- Переменные окружения выставлять не нужно: демо не обращаются к внешним сервисам.

Все команды выполняются из каталога с демо. Данные пишутся в `data/`.

## Шаг 1. Виртуальное окружение и версии

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python versions_check.py
```

В выводе: `duckdb==2.0.0 [ok]`, `pandas==2.3.3 [ok]`, `pyarrow==22.0.0 [ok]`, строки `threads = N` и `memory_limit = ...`.
Шаг прошёл, если у всех трёх пакетов стоит `[ok]` и код выхода 0.

## Шаг 2. Синтетический набор в Parquet и CSV

```bash
.venv/bin/python generate_data.py
```

В выводе: `Строк: 5 000 000`, `Столбцов: 11, row groups в Parquet: 41`, размеры `orders.parquet` и `orders.csv`.
Шаг прошёл, если в `data/` лежат оба файла и CSV заметно больше Parquet (на прогоне 388.5 MB против 65.0 MB).
Для слабой машины можно уменьшить набор: `--rows 1000000`, тогда цифры дальше будут другими.

## Шаг 3. SQL прямо по файлам

```bash
.venv/bin/python query_files.py
```

В выводе две строки вида `--- parquet: 0.599 с, 250 групп, тип результата pandas.core.frame.DataFrame` и такая же для csv, затем типы столбцов, которые вывел `read_csv`.
Шаг прошёл, если последняя строка `Сверка parquet и csv: группы совпали=True, counts совпали=True`, а разница выручки близка к нулю.

## Шаг 4. EXPLAIN ANALYZE и pushdown

```bash
.venv/bin/python explain_pushdown.py
```

В выводе полные планы и ключевые строки. Для запроса A в блоке сканирования видны только два столбца из 11 и `Row Groups Scanned: 41 / 41`. Для запроса B с фильтром по дате `Row Groups Scanned` близко к `1 / 41`, а `Data Read` в разы меньше. Затем время запроса B с оптимизатором по умолчанию и с `disabled_optimizers='filter_pushdown'`.
Шаг прошёл, если строка `Результаты совпали: True` и время без filter_pushdown больше.

## Шаг 5. Тот же агрегат в SQLite

```bash
.venv/bin/python sqlite_compare.py
```

В выводе таблица из четырёх строк: DuckDB по файлу, DuckDB по таблице в памяти, DuckDB в один поток и SQLite с временем загрузки и запроса.
Шаг прошёл, если `Результаты DuckDB и SQLite совпали: True`. Загрузка в SQLite занимает порядка десяти секунд, это нормально.

## Шаг 6. Конкурентный доступ к файлу .duckdb

```bash
.venv/bin/python concurrent_write.py
```

В выводе три блока. В первом и втором второй процесс получает ошибку блокировки вида `IOException: IO Error: Could not set lock on file`, текст урезан до пути. В третьем строка `Один процесс, 4 потока с отдельными cursor: строк в t = 803 (ожидалось 803)`.
Шаг прошёл, если в третьем блоке числа совпали.

## Шаг 7. memory_limit и out-of-core

```bash
.venv/bin/python memory_limit.py
```

В выводе таблица по лимитам `none`, `256MB`, `20MB`: успех, время, пик spill и пик RSS. С лимитом 256MB запрос проходит, на прогоне spill остался нулевым. С 20MB запрос падает с ошибкой нехватки памяти, это ожидаемо.
Шаг прошёл, если `none` и `256MB` показывают `True`, а `20MB` показывает `False`.

## Шаг 8. Всё одним прогоном

```bash
.venv/bin/python selfcheck.py
cat run_output.txt
cat .status
```

В `run_output.txt` первой строкой дата и версия python3, дальше блоки `========== [N/7] имя_демо.py ==========` с выводом и кодом выхода каждого демо. В `.status` одна строка: число упавших демо и время UTC.
Шаг прошёл, если `.status` начинается с `0`. С флагом `--detach` прогон уходит в фон, результат смотрите в тех же файлах.

## Если не так

- `[ОЖИДАЛОСЬ 2.0.0]` на шаге 1: в venv другая версия, пересоздайте `.venv` и поставьте пакеты из `requirements.txt`.
- Шаг 2 падает с ошибкой записи: нет места на диске или нет прав на каталог `data/`.
- На шаге 4 нет строк `Data Read` или `Row Groups Scanned`: смотрите полный план выше, в другой версии DuckDB метрики могут называться иначе.
- На шаге 4 запрос B сканирует все 41 row group: Parquet перезаписан неупорядоченным, перезапустите `generate_data.py`.
- На шаге 6 второй процесс открыл файл без ошибки: файл открыт с другой файловой системы без блокировок, например сетевой; перенесите каталог на локальный диск.
- На шаге 7 падает и `256MB`: мало места для spill в `data/spill/` или включён очень маленький лимит RAM у контейнера.
- На шаге 7 таблица пустая или код выхода дочернего процесса ненулевой: модуль `resource` есть только на Linux и macOS, на Windows этот шаг не работает.
- Цифры времени отличаются от статьи: это нормально, они зависят от диска, числа ядер и фоновой нагрузки.
