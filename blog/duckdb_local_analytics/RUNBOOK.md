# RUNBOOK: DuckDB для локальной аналитики без сервера БД

## Окружение

- Linux или macOS, Python 3.10–3.13. На Windows всё, кроме замера пикового RSS в шаге 7 (нет модуля `resource`).
- Свободно 3 ГБ на диске: Parquet, CSV, файл SQLite и временные файлы spill.
- От 4 ГБ RAM.
- Docker, сервер БД и сетевой доступ к внешним сервисам не нужны. Сеть нужна только для `pip install`.
- Переменные окружения выставлять не нужно: ни ключей, ни токенов демо не использует.

Все команды выполняются из папки с демо. Скрипты сами находят свои файлы, поэтому каталог запуска на результат не влияет.

## Шаг 1. Чистый venv и версии

Ставим точные версии из `requirements.txt` и проверяем, что движок действительно 2.0.0.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python versions_check.py
```

В выводе: строки `duckdb 2.0.0 [ok]`, `pandas 2.3.3 [ok]`, `pyarrow 22.0.0 [ok]`, затем `pragma_version.library_version = v2.0.0` и текущие `threads` и `memory_limit`. Последняя строка: `Все версии совпадают с requirements.txt`.

Шаг прошёл, если код выхода 0 (`echo $?`).

## Шаг 2. Синтетический набор в Parquet и CSV

Генерируем 5 млн заказов средствами DuckDB и пишем один набор в два формата.

```bash
python generate_data.py
```

В выводе: время генерации и записи, размеры `orders.parquet` и `orders.csv` в MB, во сколько раз CSV больше Parquet, и первые три строки набора со столбцами `order_id, ts, region, category, amount, qty, customer_id, note`.

Шаг прошёл, если в папке `data/` появились `orders.parquet`, `orders.csv` и `rows.txt`. Для быстрой пробы на слабой машине: `python generate_data.py --rows 1000000`, остальные шаги тогда перегенерируют набор на 5 млн при первом запуске.

## Шаг 3. SQL прямо по файлам

Один и тот же агрегат через `read_parquet` и `read_csv`, результат сразу в pandas DataFrame.

```bash
python query_files.py
```

В выводе: схема, которую `read_csv` определил сам (`ts` как `TIMESTAMP`, `amount` как `DOUBLE`), затем два блока `--- parquet: N с` и `--- csv: N с` с топ-10 групп по выручке. Тип результата `pandas.core.frame.DataFrame`. Ниже строка сверки и агрегат по регионам, посчитанный SQL-запросом поверх DataFrame.

Шаг прошёл, если в сверке `группы совпали=True, counts совпали=True`, а код выхода 0. Время по CSV заметно больше, чем по Parquet: CSV приходится парсить целиком.

## Шаг 4. EXPLAIN ANALYZE и pushdown

Смотрим, какие столбцы и строки движок реально читает из Parquet.

```bash
python explain_pushdown.py
```

В выводе: число столбцов (8) и групп строк в файле, min/max `order_id` первых групп, затем полный план запроса A и выжимка из него. В узле скана Parquet ищите перечень `Projections` (только нужные столбцы) и `Filters` (условия на `region` и `ts`, переданные в скан). Для запроса B (диапазон `order_id`) в плане видно число строк после скана, а в конце время с оптимизатором по умолчанию и с `disabled_optimizers='filter_pushdown'`.

Шаг прошёл, если план напечатан, в выжимке есть строки со сканом Parquet и фильтрами, код выхода 0. Формат дерева плана зависит от версии, поэтому сверяйте по смыслу, а не по символам рамки.

## Шаг 5. Тот же агрегат в SQLite

Загружаем те же 5 млн строк в файл SQLite и сравниваем время одного `GROUP BY`.

```bash
python sqlite_compare.py
```

В выводе: версии DuckDB и SQLite, число загруженных строк и размер `orders.sqlite`, таблица из четырёх вариантов (DuckDB по Parquet, DuckDB по таблице, DuckDB в одном потоке, SQLite) со временем загрузки и запроса, отношение SQLite к DuckDB. Загрузка в SQLite занимает десятки секунд, это нормально.

Шаг прошёл, если строка `Результаты трёх вариантов совпали: True` и код выхода 0. Цифры относятся к вашей машине и этому набору.

## Шаг 6. Второй процесс пишет в файл .duckdb

Проверяем модель конкурентного доступа к одному файлу базы.

```bash
python concurrent_write.py
```

В выводе шесть сценариев. В первом второй процесс получает ошибку блокировки файла: строка `ERROR mode=rw ...` с типом исключения и текстом про lock. Во втором видно, пускает ли DuckDB читателя, пока файл держит писатель. Третий показывает 803 строки после записи из четырёх потоков одного процесса. В четвёртом два процесса читают файл одновременно, в пятом запись при открытом читателе отклоняется, в шестом запись проходит, когда файл свободен.

Шаг прошёл, если в конце `Неожиданные исходы: нет` и код выхода 0. Точный текст ошибки из сценария 1 и есть материал для раздела про ограничения.

## Шаг 7. memory_limit и out-of-core

Тяжёлый `GROUP BY` на 5 млн уникальных ключей в трёх конфигурациях, каждая в отдельном процессе.

```bash
python memory_limit.py
```

В выводе три блока `===== memory_limit: ... =====` с фактическим значением лимита, топ-5 строк или текстом ошибки, затем сводная таблица: успех, время, пиковый объём временных файлов (spill) и пиковый RSS процесса. При лимите 256MB ожидаемо растёт spill и падает RSS по сравнению с запуском без лимита. При 20MB запрос либо проходит медленнее, либо падает с ошибкой нехватки памяти. Оба исхода фиксируйте как есть.

Шаг прошёл, если запуск без лимита успешен и код выхода 0.

## Прогон целиком

Все шаги по очереди в свежем `.venv`, вывод в `run_output.txt`, итог в `.status`.

```bash
python3 selfcheck.py
cat .status
```

В `.status` одна строка вида `0 2026-11-20T12:00:00Z`. Ноль значит, что все блоки завершились с кодом 0. В `run_output.txt` каждый блок начинается строкой `==== [n/9] ... ====` и заканчивается кодом выхода.

## Если не так

- `pip` не находит `duckdb==2.0.0`. Обновите pip (`python -m pip install -U pip`) и проверьте версию Python: колёса под совсем старые или слишком новые интерпретаторы могут отсутствовать.
- `versions_check.py` пишет `ОЖИДАЛАСЬ ...`. Вы запускаете не тот интерпретатор: активируйте `.venv` или вызовите `.venv/bin/python` явно.
- Ошибка разбора SQL в DuckDB 2.0. Новый PEG-парсер включён по умолчанию. Для диагностики выполните `SET enable_legacy_parser = true` и сравните. Лямбды в стиле `x -> x + 1` в 2.0 выключены, в демо их нет.
- `No space left on device` на шаге 2 или 7. Освободите место или уменьшите набор через `python generate_data.py --rows 1000000`.
- В шаге 4 нет строк `Filters` или `Projections`. Посмотрите полный план выше выжимки: названия полей узла скана в разных версиях отличаются.
- В шаге 4 отключение `filter_pushdown` выдаёт ошибку. Имя оптимизатора в вашей сборке другое, остальная часть шага от этого не зависит.
- В шаге 6 сценарий 1 неожиданно проходит. Скорее всего, файл лежит на сетевой файловой системе без поддержки блокировок. Перенесите папку на локальный диск.
- В шаге 7 лимит 20MB проходит без ошибки. Это не сбой: движок ушёл в spill. Уменьшите лимит в `CONFIGS` в `memory_limit.py`, если нужен пример отказа.
- В шаге 7 пиковый RSS равен `None`. Вы на Windows, модуля `resource` там нет, остальные замеры валидны.
- Шаг 5 идёт очень долго. Загрузка в SQLite построчная и зависит от диска. Проверьте, что `data/` не на сетевом томе.
